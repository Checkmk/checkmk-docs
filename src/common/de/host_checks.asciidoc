[#intro]
== Einleitung

Zustandsänderungen von Diensten im Monitoring können irreführend sein, wenn der dazugehörige Host inaktiv oder nicht erreichbar ist.
Aus diesem Grund sollte der Zustand des Hosts _vor_ den Zuständen der Dienste bekannt sein, und ein Zustand {DOWN} des Hosts sollte (dann irrelevante) Benachrichtigungen über Zustände von Diensten unterdrücken.
Überwacht man beispielsweise einen Host auch mit xref:active_checks#[aktiven Checks], würde die xref:notifications#state_host[Benachrichtigung] über einen nicht erreichbaren HTTP-Server womöglich auf die falsche Fährte schicken.

Leider ist in einer modernen IT-Umgebung nicht jeder Host direkt vom {CMK}-Server aus erreichbar.
{CMK} bietet auch für diese Hosts eine Reihe von Möglichkeiten, ihren Zustand sinnvoll zu bestimmen.
Dieser Artikel erklärt sie und ordnet sie ein.

Hier vorgestellte Einstellungen betreffen -- wenn nicht abweichend beschrieben -- die Regel [.guihint]#Setup > Hosts > Host monitoring rules > Host check command#.

.Mit der Regel [.guihint]#Host check command# legen Sie fest, wie bestimmt werden soll, ob ein Host als erreichbar gilt.

[#overview]
== Arten von Host-Checks

{CMK} bietet zwei Arten von Check per Ping und die Möglichkeit des Mappings beliebiger Services auf Host-Zustände.
ifdef::onprem[]
Daneben ist es möglich, beliebige Programme auszuführen, um Zustände von Hosts festzulegen.
endif::[]

[#ping]
=== Ping

Hosts, die mit IP-Adresse konfiguriert sind, werden regulär per Ping überprüft.
Das Verfahren ist relativ simpel und erfordert geringe Ressourcen:
Zur Prüfung, ob ein Host {UP} ist, werden einige ICMP-Pakete verschickt.
Die Hosts beantworten die Pakete mit ICMP-Echo-Replies, welche {CMK} empfängt.

Für die Umsetzung eines Pings existieren in {CMK} zwei Implementierungen:

[#check_icmp]
==== Klassischer Ping

ifdef::onprem[]
{cre-only}
Der Standardweg bei {RE} und optional bei den kommerziellen Editionen
endif::[]
ifdef::saas[]
Ein möglicher Weg bei {CE}
endif::[]
ist die Prüfung über einen separaten Subprozess.
Sie kann über die Einstellung [.guihint]#Ping (active check with ICMP echo request)# aktiviert werden.
Für jeden Host-Check wird dann ein Prozess `check_icmp` gestartet.
Dies entspricht einem xref:active_checks#[aktiven Check], der vom Monitoring-Kern disponiert werden muss.
Der Prozess sendet einige Pakete und wartet auf Antwort.
Bleibt die Antwort aus, wird ein von Null verschiedener _Exit Code_ zurückgegeben, was den Host als {DOWN} kennzeichnet.

Das Warten insbesondere auf ausstehende Pakete im Falle der Nicht-Erreichbarkeit bindet durchaus Ressourcen.
ifdef::onprem[]
Daher kann es bei {RE} in Kombination mit Hosts, die mit dem regulären xref:wato_monitoringagents#[{CMK}-Agenten] oder mit dem xref:agent_linux_legacy#ssh[Agenten via SSH] überwacht werden, sinnvoll sein, stattdessen den xref:check_mk[Zustand des Dienstes [.guihint]#Check_MK#] heranzuziehen.
endif::[]
ifdef::saas[]
Daher empfehlen wir diese Methode nur, wenn die Statistiken zu Roundtrips und Paketverlusten benötigt werden.
endif::[]


[#smartping]
==== Smart Ping

ifdef::onprem[]
{cee-only} 
Smart Ping ist ein Feature des xref:cmc#[{CMK} Micro Core] (CMC) und somit den kommerziellen Editionen vorbehalten.
endif::[]

ifdef::onprem[]
Der CMC
endif::[]
ifdef::saas[]
Der xref:cmc#[{CMK} Micro Core] (CMC)
endif::[]
führt Host-Checks standardmäßig mit einem Verfahren namens _Smart Ping_ aus.
Smart Ping basiert auf einer internen Komponente namens `icmpsender`, die ihre eigene Ping-Implementierung verwendet.
Da {CMK} mit CMC nicht auf ein externes gestartetes Programm angewiesen ist, muss nicht für jede Prüfung per Ping ein neuer Prozess gestartet werden.

// ES: fehlende ifdefs, lieber mit "Verhalten des klassischen Ping" vergleichen
Das Standardverhalten von `icmpsender` unterscheidet sich deutlich vom Verfahren in {RE}.
Anstelle mehrerer Pakete in schneller Folge, auf die gewartet wird, sendet `icmpsender` nur _ein_ ICMP-Paket pro Host alle sechs Sekunden (das Intervall ist mit dem Regelsatz [.guihint]#Normal check interval for host checks# konfigurierbar).
Dieses Verhalten reduziert die Ressourcennutzung deutlich.
// und den Datenverkehr deutlich.

Für den Empfang ist die CMC-Komponente `icmpreceiver` zuständig.
Sie entscheidet anhand eingehender Antworten (_Echo Replies_), ob ein Host {UP} oder {DOWN} ist.
Kommt ein Paket an, gilt der Host als {UP}.
Wurde länger als 15  Sekunden kein Paket von einem Host empfangen, wird dieser Host als {DOWN} markiert.
Das Timeout können Sie mit dem Regelsatz [.guihint]#Settings for host checks via Smart PING# ändern -- die erwähnten 15 Sekunden ergeben sich aus zweieinhalb Check-Intervallen zu je sechs Sekunden.



Die Komponente `icmpreceiver` wertet auch eingehende TCP-Pakete mit den Flags SYN (_synchronization_) und RST (_reset_, Zurücksetzen einer Verbindung) aus.
Wenn sie solche Pakete empfängt, wird der betreffende Host als {UP} betrachtet.
// Dieser Mechanismus kann zu schwankenden (_flapping_) Zuständen von Hosts in Infrastrukturen führen, in denen ICMP-Verkehr nicht erlaubt ist, TCP-Verkehr aber schon.

ifdef::onprem[]
[TIP]
====
Der `icmpreceiver` wird jedes SNMP-Paket ignorieren, da SNMP nicht über TCP, sondern über UDP kommuniziert.
====
endif::[]

[#ping_metrics]
==== Metriken für Ping

Eine Besonderheit klassischer Checks über ICMP mit der Einstellung [.guihint]#Ping (active check with ICMP echo request)# ist, dass sie in einer dem Host zugeordneten Metrik resultiert, die Paketverlust und Zeitdauer des _Roundtrips_ abbildet.
Das Vorhandensein dieser Daten kann in einigen Fällen zusätzliche wertvolle Einblicke in die Qualität einer Netzwerkanbindung liefern.

Da Smart Ping zur Reduzierung des Overheads keine _Sequence Number_ auswertet, kann mit dieser Methode keine Messung der Laufzeit eines ICMP-Requests und keine Bestimmung verlorener Pakete stattfinden.
Falls Sie auf diese Daten angewiesen sind, aktivieren Sie für betreffende Hosts [.guihint]#Ping (active check with ICMP echo request)# oder konfigurieren Sie _zusätzlich_ zu Smart Ping den aktiven Check [.guihint]#Check hosts with ping (ICMP echo request)#.


[#check_mk]
=== Zustand des Dienstes Check_MK

Mit der Einstellung [.guihint]#Use the state of the Check_MK service# legen Sie fest, dass ein Host {UP} sein soll, wenn [.guihint]#Check_MK# auf {OK} ist und {DOWN} in allen anderen Fällen.
Diese Einstellung sollten Sie verwenden, wenn überwachte Hosts in einem Netzwerk mit _Zero Inbound Traffic_ liegen und Monitoring-Daten per xref:glossar#push_mode[Push-Modus] zum {CMK}-Server schicken.

ifdef::onprem[]
Bei Nutzung von {RE} kann diese Einstellung die Leistung durch ausbleibende Host-Checks vor Versand von Notifications verbessern, allerdings steigt möglicherweise die Zahl von _falsch positiven_ Host-Notifications etwas.
endif::[]

[#other_service]
=== Zustand eines anderen Dienstes

Über die Einstellung [.guihint]#Use the status of the service...# können Sie einen beliebigen Dienst definieren, der den Host-Zustand bestimmt.
Wenn ein überwachter Host per SSH vom Monitoring-Server aus erreichbar ist, können Sie beispielsweise [.guihint]#Setup > Services > Other services > Check SSH service# verwenden, um einen Handshake mit dem SSH-Server zu testen.
Schlägt dieser fehl, mag ein Host zwar theoretisch erreichbar sein, erfordert aber in jedem Fall Aufmerksamkeit, bevor andere Probleme angegangen werden.

ifdef::onprem[]
[#custom_command]
=== Ein Befehl bestimmt den Zustand

Weit reichende Freiheit haben Sie mit [.guihint]#Use a custom check plug-in#.
Hier können Sie einen beliebigen Befehl angeben und jeder von Null verschiedene _Exit Code_ wird als {DOWN} gewertet.
Befehle können Monitoring-Plugins sein oder einfache Shell-Befehle.
Wenn Sie beispielsweise eine Agentenausgabe als Datei auf xref:datasource_programs#[_irgendeine kreative_ Art und Weise] zum Monitoring-Server bringen und dort auslesen, kann die Prüfung auf Vorhandensein oder eine minimale Dateigröße mittels `test` Rückschlüsse auf den Host-Zustand geben.
endif::[]


[#always_up]
=== Betrachte einen Host immer als UP

Die Einstellmöglichkeit [.guihint]#Always assume host to be up# ist dann sinnvoll, wenn ein bestimmter Host im Monitoring gar nicht „real“ ist, sondern lediglich als Container für eine Ansammlung von Diensten dienen soll.
Das kann beispielsweise im Cloud- oder Cluster-Monitoring der Fall sein, wo Daten per xref:glossar#piggyback[Piggyback] eingeholt werden und solche Hosts xref:dcd#[dynamisch] erzeugt werden.
Diese Einstellung ist daher Standard, wenn ein Host explizit ohne IP-Adresse konfiguriert ist ([.guihint]#No IP#).

[#performance]
== Erneute Host-Checks bei Service-Problemen

Host-Checks dienen -- wie eingangs erwähnt -- nicht nur der Kontrolle, ob ein Host {UP} oder {DOWN} ist.
Ihr zweiter Zweck ist, vor dem Versand von Benachrichtigungen zu aktiven Checks zu ermitteln, ob nicht der Host-Zustand Ursache für den Service-Zustand ist.
Erst danach wird die passende Benachrichtigung ausgelöst.

Performance und Zuverlässigkeit unterscheiden sich dabei zwischen xref:reschedule[aktiv ausgelösten Host-Checks] und xref:passive_alive[Host-Checks per Smart Ping].

[#reschedule]
=== Aktiver Host-Check

// ES: Hier fehlen ifdefs für den ganzen Abschnitt. Trennung sauberer beschreiben, Abhängigkeit vom Monitoring-Kern explizit machen
Das Standardverhalten ist, nach einem fehlgeschlagenen aktiven Check einen Host-Check auszulösen und dann zu entscheiden, ob über Host- oder Service-Zustand benachrichtigt wird.

Das Verfahren unterscheidet sich hierbei im Detail zwischen {RE} und den kommerziellen Editionen (bei Verwendung des {CMK} Micro Core, aka CMC):

* In {RE} werden Resultate von Host-Checks für einige Sekunden zwischengespeichert.
Diese Zwischenspeicherung soll die erneute Ausführung eines Host-Checks verhindern, wenn die letzte erst einige Sekunden zurückliegt.
Sie kann jedoch zu fehlerhaften Benachrichtigungen führen, wenn der Host beim Host-Check vor einigen Sekunden noch {UP} war, nun aber {CRIT} eines HTTP-Checks seine Ursache in danach aufgetretenen Netzwerkproblemen hat.
Ist das zwischengespeicherte Resultat veraltet, wird unmittelbar ein neuer Host-Check durchgeführt, was Ressourcen bindet (Erstellung eines Prozesses).
* Die kommerziellen Editionen starten sofort einen Prozess.
Da hierfür ein _Active Check Helper_ verwendet wird, ist der Ressourcenbedarf geringer als bei {RE}.

[#passive_alive]
=== Passiver Host-Check per Smart Ping

// ES: ifdef (Hexagon)
{cce-only}
Ist Smart Ping konfiguriert, kann der Monitoring-Kern sich passiv verhalten und muss keinen Check aktiv auslösen.
Der `icmpsender` sendet kontinuierlich im Intervall von sechs Sekunden und der `icmpreceiver` lauscht dauerhaft auf ICMP-Echo-Replies und TCP-RST-Pakete.

Ist der Host tatsächlich nicht erreichbar, wartet der CMC die konfigurierte Zeitspanne ab (regulär 2,5 Intervalle, also 15 Sekunden) und verschickt dann eine Benachrichtigung zum Host-Zustand {DOWN}.
Hier eben mit 15 Sekunden Verzögerung, aber ohne, dass ein neuer Prozess gestartet werden musste.

Gehen jedoch Lebenszeichen des Hosts ein, kann sofort zum Service benachrichtigt werden.
Ein Beispiel aus der Praxis: Sie haben einen aktiven Check für SSL-Zertifikate konfiguriert.
Schlägt dieser fehl, weil der Webserver nicht aktiv ist, dann geht einige Millisekunden _nach_ Start des aktiven Checks ein TCP-RST-Paket ein.
Dieses Paket signalisiert {CMK}, dass der Host zwar eine Verbindung auf Port 443 verweigert hat, dies aber nur kann, weil er {UP} ist.
In diesem Fall kann sofort zum Service-Zustand benachrichtigt werden.

Das gleiche Prinzip wird bei der Benachrichtigung zu Netzwerkausfällen angewandt, wenn xref:notifications#parents[Parent-Hosts] definiert sind:
Gehen Lebenszeichen eines Switches ein, kann zu Hosts benachrichtigt werden, die über diesen Switch erreichbar sind.


ifdef::onprem[]
[#smartping_advantages]
==== Resultierende Vorteile

Durch dieses Verfahren ergibt sich eine Reihe von Vorteilen von Smart Ping verglichen mit aktiven Host-Checks:

* Nahezu vernachlässigbare CPU-Last durch Host-Checks: Es können selbst ohne besonders leistungsfähige Hardware Zigtausende von Hosts überwacht werden.
* Kein Ausbremsen des Monitorings durch blockierende aktive Host-Checks, falls Hosts {DOWN} sind.
* Keine Fehlalarme zu Services bei nicht aktuellem zwischengespeicherten Host-Zustand.
endif::[]


ifdef::onprem[]
[#troubleshooting]
== Problembehandlung

Wie bei Service-Checks können auch bei Host-Checks Feinheiten Ihrer Systemumgebung oder Firewall-Konfiguration Anpassungen erforderlich machen.
endif::[]


ifdef::onprem[]
[#nagios_caching]
=== Caching-Intervall bei {RE}

Die Zwischenspeicherung des letzten Host-Checks bei {RE} kann zu falschen Benachrichtigungen zu Service-Problemen führen, wenn eigentlich zu Host-Problemen benachrichtigt werden müsste.
Die Dauer der Zwischenspeicherung können Sie bei {RE} nur global über die Einstellungen des Monitoring-Kerns anpassen.
In welchen Konfigurationsdateien Änderungen vorzunehmen sind, zeigt der xref:core_tuning#[Artikel zum Tuning des Monitoring-Kerns].

Beachten Sie, dass die Reduzierung auf Null (sofortige erneute Ausführung des Host-Checks) nur vorgenommen werden sollte, wenn die Zahl aktiver Checks in Ihrem Monitoring klein ist.
endif::[]


ifdef::onprem[]
[#smartping_firewall]
=== Firewall-Probleme bei Smart Ping

[#tcp_rst_by_fw]
==== Firewall sendet selbst TCP-RST-Pakete

Es gibt Firewalls, die TCP-Verbindungspakete an nicht erreichbare Hosts nicht verwerfen, sondern mit einem TCP-RST-Paket beantworten. 
In solch einem Fall darf die Firewall als _Absender_ dieser Pakete nicht sich selbst eintragen, sondern muss die IP-Adresse des Ziel-Hosts angeben. 
Smart Ping wird dieses Paket als Lebenszeichen werten und somit zu Unrecht annehmen, dass der Ziel-Host erreichbar ist.

In solchen Situation haben Sie die Möglichkeit, mit [.guihint]#Global settings > Monitoring core > Tuning of Smart PING# die Option [.guihint]#Ignore TCP RST packets when determining host state# zu aktivieren.
// ES: Spricht irgendwas dagegen, _immer_ alle TCP-RST-Pakete zu ignorieren? Wundert mich, dass das kein Standardverhalten ist.
// Oder Sie wählen für die betroffenen Hosts als Host-Check einen klassischen Ping mit `check_icmp`.

[#icmp_blocked]
==== Umgebungen ohne ICMP

Ist in Ihrer Umgebung ICMP vollständig blockiert, werden Sie mit Hosts konfrontiert sein, die schnell zwischen {UP} und {DOWN} hin- und her wechseln (xref:notifications#flapping[_flapping_]).
In diesem Fall sorgt TCP-Verkehr bei der Agentenabfrage oder der Durchführung der aktiven Checks zu {UP}, der kurze Timeout von 15 Sekunden aber schnell wieder zu {DOWN}.
Wählen Sie in solchen Fällen nicht Smart Ping, sondern andere in diesem Artikel beschriebene Methoden zur Bestimmung des Host-Zustandes.
endif::[]
