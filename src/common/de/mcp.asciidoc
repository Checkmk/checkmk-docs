[#intro]
== Einleitung

"Analysiere die RAM-Auslastung der Hosts am Standort München in den letzten 6 Stunden."
Eine solch typische Aufgabenstellung lässt sich in {CMK} ganz traditionell mit einem Blick auf ein entsprechend erstelltes Dashboard oder einen individuell gestalteten Graphen erledigen.
Mit dem Einzug eines MCP-Servers geht dies nun auch über einen KI-Assistent mit natürlicher Sprache und ad-hoc ohne etwaige Vorabeiten.

Über das link:https://de.wikipedia.org/wiki/Model_Context_Protocol[Multi Context Protocol (MCP)^] können Sie beliebige kompatible Client an {CMK} anbinden, beispielsweise ChatGPT, Claude oder LibreChat.
Auch das verwendete LLM liegt ganz in Ihrer Hand, seitens {CMK} gibt es hier keinerlei Vorgaben.

Der MCP-Server liefert Status, historische Daten, Konfigurationen, Verfügbarkeiten und so weiter -- und das ausschließlich mit Lese-Rechten.
Sie können den Zugriff auf diese KI-Schnittstelle also auch Dritten ohne Risiko gewähren.

Die Einrichtung ist grundsätzlich trivial: Der Server muss in {CMK} aktiviert und im Client registiert werden, der sich wiederum via OAuth am Server authentifizieren muss.

Im Folgenden lesen Sie, wie genau der MCP-Server mit ausgewählten Clients eingerichtet wird, welche Voraussetzungen geschaffen werden müssen und was Sie damit erreichen können.

[#requrirements]
== Voraussetzungen
Folgende Voraussetzungen müssen erfüllt sein:

* Kommerzielle Edition von {CMK} ab 2.5.0p13
* MCP-Client mit link:https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http[Streamable HTTP^]-Unterstützung
* Weboberfläche per HTTPS erreichbar

Besonderes Augenmerk gilt dem letzen Punkt: Die Absicherung per HTTPS ist notwendig, da die Authentifizierung über OAuth läuft, das wiederum TLS benötigt.

{CMK} kann mit link:https://checkmk.com/werk/22264[Werk #22264] als OAuth-Authorization-Server fungieren.
Das heißt, Clients können sich über den OAuth-Endpunkt (`/.well-known/oauth-authorization-server/oauth-mysite`) dynamisch registrieren.
Die Authorisierung läuft über einen Bestätigungsdialog im Browser -- ein Eingreifen von Admin-Seite ist nicht notwendig.
Das daraus entstehende Token verfügt über dieselben Lese- und/oder Schreib-Rechte wie das authorisierende Nutzerkonto und hat eine Ablaufzeit von 48 Stunden.
Das erste {CMK}-Feature, das den neuen OAuth-Dienst nutzt: der MCP-Server.


In der Praxis stehen die Chancen gut, dass die TLS-Verbindung bereits vor dem Instanz-Apache-Server terminiert wird, beispielsweise durch irgendeine Art von Proxy- oder auch schlicht den System-Apache-Server.
In diesem Fall muss die terminierende Anwendung `X-Forwarded-Proto: https` senden.
Somit läuft zwar die Verbindung zwischen {CMK}/MCP-Server und terminierender Komponente über HTTP, aber der Server weiß, dass die Anfrage vom Client aus korrekt HTTPS-gesichert gestellt wurde.
Eine beispielhafte Apache-Konfiguration finden Sie im Artikel xref:omd_https.html#configsample[Weboberfläche per HTTPS absichern.]

[IMPORTANT]
====
Wichtig: Wenn Sie von einer älteren {CMK}-Version aktualisiert haben, müssen Sie die Apache-Konfiguration Ihrer Instanz mit `sudo omd update-apache-config mysite` neu starten.
Andernfalls wird Apache den MCP-Endpunkt nicht finden und OAuth-Verbindungsfehler melden.
====

[#settingup]
== MCP-Server einrichten
Sobald die Voraussetzungen stehen, ist die Einrichtung in drei Schritten erledigt.

Aktivieren Sie zunächst den MCP-Server unter [.guihint]#Setup > General > Global settings > AI features > Enable MCP server#.

Registrieren und authentifizieren Sie den MCP-Server anschließend in Ihrem Client mit folgender URL: `pass:[https://myserver/mysite/check_mk/mcp]`.


Die Registierung ist im Grunde immer gleich, kann aber auf unterschiedliche Arten vorgenommen werden, etwa über die grafischen Oberflächen, die Kommandozeile oder Config-Dateien.
Folgend finden Sie jeweils ein Beispiel:

[.tabs]
====
Claude (CLI)::
+
--
MCP-Server per CLI registrieren:

[{shell}]
----
claude mcp add --transport http mycheckmkmcp `pass:[https://myserver/mysite/check_mk/mcp]`
----

Authentifizieren:

[{shell}]
----
claude mcp 
----

Wählen Sie die erstellte Verbindung und anschließend [.guihint]#Authenticate#.

Hinweis: Die Kommandozeilenschnittstelle steht in allen bezahlten Claude-Konten zur Verfügung.
In der kostenlosen Claude-Version lassen sich MCP-Server in der grafischen Nutzeroberfläche registrieren/Authentifizieren.
--
ChatGPT (GUI)::
+
--
Im ChatGPT-Desktop-Client können Sie den Server unter [.guihint]#Bearbeiten > Einstellungen > Integrationen > >Plugins > MCP# hinzufügen.
Sie müssen lediglich folgende Angaben machen:

* Beliebiger Name
* Typ: Streaming HTTP
* URL: `pass:[https://myserver/mysite/check_mk/mcp]`

Authentifizieren:

Nach der Registrierung finden Sie den Knopf [.guihint]#Authentifizieren# direkt an der Verbindung selbst.

--
LibreChat (YAML)::
+
--
LibreChat erlaubt auch die Konfiguration über über YAML-Dateien:

.librechat.yaml
[{file}]
----
    version: 1.2.1
    
    mcpSettings:
      allowedAddresses:
        - "myserver.mynetwork.lan:443"
    
    mcpServers:
      checkmk:
        type: streamable-http
        url: "https://myserver.mynetwork.lan/mysite/check_mk/mcp"
        requiresOAuth: true
----
		
Authentifizieren:

Wählen Sie anschließend die erstellte Verbindung in der LibreChat-Oberfläche, um die Authentifizierung zu starten.

--
MCP Inspector/Skript::
+
--

Wenn Sie den MCP-Endpunkt manuell aufrufen, also beispielsweise per Skript oder das Standard-Testwerkzeug link:https://github.com/modelcontextprotocol/inspector[MCP Inspector^], können Sie die Authentifizierung über einen entsprechenden Header vornehmen: `Authorization: Bearer <automation_user> <secret>`.

In MCP Inspector wählen Sie dazu die Vorlage [.guihint]#Streamable HTTP#, geben die Registrierungs-URL `pass:[https://myserver.mynetwork.lan/mysite/check_mk/mcp]` an und fügen über die Einstellungen einen [.guihint]#Custom Header# mit folgendem Inhalt hinzu:

* Key: Authorization
* Value: Bearer myautomationuser mypassword

Sobald die Verbindung aktiviert wird, startet die OAuth-Authentifizierung.

--
====

Die eigentliche Authentifizierung ist dann unabhängig vom genutzten Client immer gleich: In einem neuen Browser-Tab öffnet sich der OAuth-Dialog, um die Verbindung zu bestätigen -- natürlich durch einen entsprechend berechtigten Nutzer.

[#usagedata]
== Nutzungsdaten teilen

Rein optional können Sie die Übertragung von MCP-Nutzungsdaten an {CMK} aktivieren.
Das hilft uns, die Nutzung des MCP-Features besser zu verstehen und es zu verbessern.
Sie finden die Einstellung unter [.guihint]#Setup > General > Global settings > AI features > Send MCP usage data to {CMK}#.
Die Daten werden als OpenTelemetry-Traces an `pass:[https://mcp-analytics.checkmk.com:54829]` geschickt -- sofern eine Firewall oder ein Proxy zwischengeschaltet ist, müssen Host und Port entsprechend freigegeben werden.

Und natürlich werden keinerlei Prompts und sonstige Inhalte geteilt!

[cols="1,3", options="header"]
|===
|Datentyp
|Verwendungszweck

|Tool- und Ressourcen-Aufrufe
|Die vom Client aufgerufene MCP-Methode und der Name des angesprochenen Tools oder der Ressource, zum Beispiel `tools/list` oder ein Aufruf von `get_services`. Im Fehlerfall der Name der internen Fehlerklasse (`cmk.mcp.error.kind`), der Aufschluss darüber gibt, was schiefgelaufen ist, ohne die Anfrage des Benutzers aufzuzeichnen.

|Antwortzeit
|Wie lange die Site für die Antwort benötigt hat, gemessen pro Anfrage und pro internem REST-Aufruf, zusammen mit dem jeweiligen Status.

|Antwortgröße
|Die Größe der Antwort, die zeigt, wie viele Daten eine Anfrage zurückgegeben hat.

|KI-Client
|Der User-Agent des aufrufenden Clients (`cmk.mcp.client.user_agent`), anhand dessen wir erkennen können, ob eine Anfrage von Claude Code, Claude Desktop, einer IDE oder einem anderen MCP-Client stammt.

|Session-ID
|Eine zufällige, pro Sitzung erzeugte Kennung (`mcp.session.id`), die die zu einer Konversation gehörenden Anfragen zusammenfasst. Sie enthält keine Benutzeridentität.

|Protokollversion
|Die Version des Model Context Protocol, auf die sich Client und Server geeinigt haben. Sie zeigt uns, welche Protokollversionen in der Praxis verwendet werden.
|===

[#usage]
== {CMK} per KI-Assistent abfragen
Sobald die Verbindung steht, hier ein Tipp für Ihre erste Anfrage: `Welche Tools stehen zur Verfügung?`
MCP arbeitet mit einzelnen Tool-Definitionen, beispielsweise `get_hosts` zur Abfrage der Hosts.
Initial arbeitet der MCP-Server mit 13 separaten Tools, wird aber kontinuierlich erweitert -- daher ergäbe es wenig Sinn, die Tools hier einzeln aufzulisten.
Fragen Sie einfach die KI!

Generell müssen Sie sich auch nicht unbedingt um einzelne Tools kümmern: Clients wie ChatGPT und Claude entscheiden eigenständig, welche Tools für Anfragen benötigt werden.
Aber Sie können sich sehr wohl mit einzelnen Tools beschäftigen und zum Beispiel in LibreChat Agenten einrichten, denen nur `get_hosts` oder nur `get_availability` zur Verfügung stehen.
Wenn Sie beispielsweise mit API-Tokens statt Pauschalangeboten arbeiten, ließe sich so der Token-Verbrauch optimieren.

[TIP]
====
Ein kleiner Tipp zum Thema Kosten:
Sofern Sie Pauschalangebote wie ChatGPT oder Claude Code nutzen, sind Sie allenfalls von Token-Limits betroffen, nicht von individuellen Kosten.
Verwenden Sie aber zum Beispiel eine Kombination wie LibreChat + OpenAI-API-Tokens, können Anfragen schnell unerwartet kostspielig werden -- wenn ein teures LLM wie GPT-6 Astra verwendet wird, können selbst in kleinen Monitoring-Systeme mehrere Euro für eine Handvoll Anfragen anfallen.
Mit einem Kosten-Nutzen optimierten Modell wie GPT-5.6 Terra können für einzelne, nicht gecachte Anfragen immerhin noch ein, zwei Cent anfallen.
Für reale Tests sollten Sie daher auf ein kontrolliertes Budget oder Pauschalangebote setzen.
====

Natürlich können Sie die KI-Schnittstelle nutzen, um sich eine Übersicht über das Monitoring, einzelne Netzwerksegmente oder Geschäftsanwendungen zu verschaffen.
Entwickelt haben wir den MCP-Server aber vor allem für die _Root-Cause-Analyse_ (RCA) -- hierzu ein paar Beispiele aus der Praxis.

[#example_problems]
=== Beispiel: Service nicht verfügbar
Eine simple Ausgangssituation: Auf einem internen {CMK}-Server sind immer wieder kurzfristige Ausfälle, lange Ladezeiten und teils Abstürze zu verzeichnen.
Das reguläre Monitoring zeigt schnell, dass es immer wieder zu Engpässen beim Arbeitsspeicher kommt -- von hier aus müsste ein Admin manuell untersuchen, was dafür verantwortlich ist und ob es mit den Ausfällen zusammenfällt.
Über den KI-Assistenten haben im wesentlichen ein paar kurze Prompts für Aufklärung gesorgt -- hier ein Abriss des Workflows:

* Prompt: Finde Probleme auf `myserver`.
** Antwort: Arbeitsspeicher ist ausgelastet.
* Prompt: Ist das der Grund für Service-Ausfälle und längere Wartezeiten?
** Antwort: Indirekt ja -- intensives Swapping führ zu CPU-Auslastung.
* Prompt: Teils reagiert das System nicht mehr und muss neu gestartet werden -- analyisere Vorfälle vor Neustarts.
** Antwort: Vor Neustarts ist intensive Speicherauslastung zu verzeichnen, gefolgt von hoher Swapping-Aktivität, die zur Auslastung der CPU-Kerne führt.
* Prompt: Lösungsvorschlag?
** Antwort: Physischen Arbeitsspeicher um mindestens 8 Gigabyte erhöhen.
	
In diesem Fall hat das reguläre Monitoring vor allem eines gezeigt: Hohe Auslastung des Arbeitsspeichers.
Über die KI wurde aber schnell klar, dass für die langsamen Antwortzeiten die CPU-Auslastung verantwortlich ist -- die wiederum durch RAM-Knappheit und folgende Swapping-Aktivitäten ausgelöst wurde.
Dieselbe Erkenntnis hätte sich in {CMK} selbst ebenfalls gewinnen lassen -- beispielsweise über einen individuellen Graphen, der gleichzeitig RAM- und CPU-Auslastung sowie Swapping-Aktivitäten visualisiert.
Das würde allerdings deutlich mehr Arbeit machen -- und es hätte bereits ein konkreter Verdacht bestehen müssen.
Per KI lassen sich in derlei einfachen Fällen schlicht unterschiedliche Status, Status-Wechsel, Metriken und Ereignisse (zum Beispiel aus Logs) in Zusammenhang bringen -- insbesondere die Auswertung von Zeitstempeln ist hier enorm hilfreich.

[#example_payment]
=== Beispiel: Payment-API fehlerhaft
Aber natürlich lässt sich mit dem KI-Assistenten auch deutlich pauschaler arbeiten.
Wieder ein Beispiel aus der Praxis, dieses mal aber mit einem deutlich komplexeren Problem und einer simpleren Herangehensweise:

- Vorfall: Zahlungsportal funktioniert nicht mehr.
- Prompt: Die Payment-API liefert Fehlermeldungen, finde die Ursache.
- Antwort: Datenbank XY funktioniert nicht.

In diesem Fall wurde eine komplexe Geschäftsanwendung analysiert, ein BI-Aggregat.
Eine solche Anwendung besteht gegebenenfalls aus Dutzenden Komponenten, wie Hosts, APIs, Netzwerkgeräten und Services.
Entsprechend vielfältig können Gründe für Probleme sein.
Hier wurde letztlich eine defekte Festplatte ausgemacht, deren eigenes Fehlermanagement noch keine Fehlerstatus provoziert hatte.
Die KI konnte Dutzende Fehlermeldungen einzelner Komponenten analysieren, Anschlussfehler ausschließen, letztlich die ursächliche Datenbank identifizieren -- und _mutmaßen,_ dass ein Hardware-Defekt dafür verantwortlich ist.

Die KI erledigt letztlich in beiden Fällen schlicht Arbeiten, die Admins auf die gleiche Art und Weise erledigt hätten -- insbesondere das Auffinden von Korrelationen über eine Zeitleiste spart hier viel Zeit.
