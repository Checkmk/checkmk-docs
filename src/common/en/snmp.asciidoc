[#intro]
== What is SNMP?

SNMP (_Simple Network Management Protocol_) is a network protocol that allows you to monitor certain types of devices with {CMK}, devices that do not support the installation of a {CMK} agent.
Devices such as routers, switches, firewalls, printers, appliances, UPSs, hardware sensors, and many others come already equipped with an alternative built-in monitoring interface from the manufacturer: an _SNMP agent_.
{CMK} can use SNMP to monitor such devices.

This article describes how you can easily add and configure SNMP-enabled hosts for monitoring.


[#snmp_instead]
=== SNMP Instead of the {CMK} Agent

By the way, there are also SNMP agents available for Windows and Linux.
However, it is not recommended to use them _instead_ of the {CMK} agent.
SNMP does not perform very well, and for monitoring, using SNMP agents the {CMK} server generally requires more CPU and memory per host than when it uses its own {CMK} agent.
Furthermore, the data provided via SNMP is incomplete.
ifdef::onprem[]
In some cases, however, monitoring via SNMP may be useful _in addition_ to the {CMK} agent.
See the section on xref:add_device[Adding devices to monitoring] for more information on this topic.
endif::[]

ifdef::saas[]
Monitoring SNMP devices with {CMK} is very simple.
endif::[]
If you just want to get started quickly with SNMP, the brief section on SNMP in xref:intro_setup_monitor#snmp[Beginner's Guide] will likely suffice.
This article, on the other hand, goes into much greater depth and covers all the details and special cases of SNMP monitoring with {CMK}.

ifdef::saas[]
[TIP]
====
{CE} requires the xref:relay#[{CMK} Relay] to monitor SNMP devices.
Install this on the same network as the SNMP device you want to monitor.
====
endif::[]

ifdef::onprem[]
[TIP]
====
{UE} allows for a second method of monitoring SNMP devices using the xref:relay#[{CMK} Relay].
Relays located on the same network as the SNMP devices to be monitored can also collect data from SNMP devices that the monitoring server cannot reach directly.
====
endif::[]


[#snmp_communication]
=== Two possible communication directions

ifdef::onprem[]
{CMK} uses a pull method for SNMP monitoring.
endif::[]
ifdef::saas[]
{CE} uses a pull method for SNMP monitoring.
endif::[]
SNMP terminology uses two terms for this that are unfortunately often confused: _Query_, and _Request_.
The difference lies in the protocol level:

* _Query_ refers to the user's perspective—that is, _which_ data is to be retrieved: “Hey, SNMP client, get me all available data on the ports of the switch in the broom closet at 27 Kellerstrasse!”
The term _Query_ is not included in the SNMP specification, but it appears in the documentation of many tools.
* _Request_ always refers to the specific way—that is, _how_ a device delivers data: “Hey, SNMP device, give me the available data for the OID `.1.3.6.1.2.1.1.1.0` and then tell me the next OID under which you have data!”
Technically, such a task is implemented, for example, as an _SNMP GETNEXT_ request, which the _SNMP manager_ sends to the device's _SNMP agent_.

What is viewed as a single _Query_ from the user's perspective can result in one, several, or even thousands of _Requests_ being generated, depending on what the device supports and how the SNMP library in use works internally.

In response to such a request,
ifdef::onprem[]
{CMK} or
endif::[]
the relay sends a UDP packet (port 161) containing an SNMP request to the device, asking it to provide specific data.
The device then responds with a UDP packet containing the data (or an error message).

[#snmp_traps]
But SNMP has a second variant: _SNMP traps._
These are unsolicited messages that devices send to configured addresses via UDP (port 162) using the push method.
Traps have many disadvantages compared to pull-based queries, which is why they are not widely used for monitoring.
ifdef::saas[]
For these reasons, the {CMK} Relay does not support receiving traps.
In the on-premises editions of {CMK}, traps can be received using the Event Console.
endif::[]
ifdef::onprem[]

.Some of the disadvantages of SNMP traps
[%collapsible]
====
* Traps are not reliable.
UDP packets can be lost.
There is no acknowledgment of receipt.
* In most cases, only _error_ messages are sent, but no _recovery_ messages.
As a result, the current status is unclear during monitoring.
* If thousands of switches send traps simultaneously (e.g., when an important upstream service is unavailable to them), the trap receiver cannot handle the load and may crash.
As a result, the monitoring system is overloaded precisely when it is needed most.
* If the trap receiver's IP address changes, all devices must be reconfigured.
* Traps are difficult to test.
Very few devices even have a function to send a generic test trap--let alone test actual error messages.
It is therefore difficult to predict whether an important trap will be processed correctly when the first such event occurs after a few months or years.

If you still want or need to work with traps, the xref:ec#snmp[Event Console] offers a solution:
It can receive traps and generate events from them.
The {CMK} Relay does not support receiving traps.
====
endif::[]


[#snmp_versions]
== SNMP Versions

The SNMP protocol is available in various versions.
These versions are not compatible with one another, so the monitoring system and the monitored device must always agree on which protocol version they are currently using.
{CMK} supports versions v1, v2c, and v3.
In practice, v2c is used in an estimated 99{nbsp}% of cases.
Here is an overview of all relevant versions of SNMP:

[cols="10,20,10,~",options="header"]
|===
|Version |Features |{CMK} |Practical implications
|*v1* | |Yes |Found only on very old devices (about 20 or more years old) that do not support v2c or whose v2c support is faulty.
|*v2c* |Bulk requests, +
64-bit counters |Yes |This is the standard in practice.
v2c is a 'light' version of v2, and the 'c' here stands for _community_, which serves as a password in SNMP.
The 64-bit counters are essential for monitoring switch ports with 1 Gbit/s and higher.
Bulk requests speed up monitoring by up to a factor of 10.
|*v2* |Security |No |Version 2 offers even better security options in addition to the features of v2c.
In practice, version 2 of SNMP is not used.
{CMK} therefore does not support this protocol version.
If you require security, use xref:snmp#v3[Version 3] instead. +
*Note:* Since the 'real' Version 2 is irrelevant, there might be references to v2 in {CMK}, but these always refer to v2c.
|*v3* |Security, +
contexts |Yes |xref:snmp#v3[Version 3] is used when SNMP traffic needs to be encrypted.
With v2c and v1, traffic is transmitted in plain text--including the community string.
In practice, Version 3 is less common because it requires significantly more processing power and the configuration effort is also considerably higher than with v2c.
The _contexts_ are a concept in which different information is visible within the same area of the SNMP data structure (OID), depending on the context ID.
This is used, for example, when partitioning Fibre Channel switches.
|===

[TIP]
====
SNMPv3 is applied--provided you have enabled the appropriate rule--exclusively to those hosts whose configuration contains SNMPv3-style credentials.

SNMPv2c is applied to those hosts for which the rule set [.guihint]#Enable SNMPv2c for hosts# has been enabled.
By default, this rule set is enabled and applies to hosts that are not explicitly configured for SNMPv1.
You can define exceptions by using a rule that takes precedence for other hosts.
====


[#enable_snmp]
== Preparing devices for monitoring

The first step is to prepare the actual device.
Every device that supports SNMP has a configuration option for this somewhere in its setup interface.
Make the following settings there:

. Go to the configuration for _active_ queries (SNMP GET).
Unfortunately, every manufacturer uses its own terminology.
Look for the settings that do _not_ configure traps and mention _SNMP community_ somewhere.
. Enable SNMP for _read-only_ (or _readable_) requests.

. If your SNMP device restricts access to specific IP addresses:
ifdef::onprem[]
Enter the IP addresses of your {CMK} servers as allowed IP addresses.
It may also be useful to include a test site of {CMK} here.
Important: If you are running multiple redundant {CMK} servers, do not forget to also specify the IP addresses that will be used after a failover.
Specifically with the {CMK} appliance, when operating in a cluster, it uses the IP address of the active node as the source IP address for outgoing connections--not the service IP address.
In a xref:distributed_monitoring#[distributed environment] or when using the xref:relay#[{CMK} relays], the IP address of the machine from which the device is being monitored is decisive.
endif::[]
ifdef::saas[]
Enter the address of the {CMK} relay being used as the allowed IP address.
endif::[]
. Assign a community if protocol versions v1 and v2c are used.

The _SNMP community_ is a type of password, with the difference being that SNMP does not use a username.
There is a convention that the community is set to `public`.
This is the default for many devices--including {CMK}.
Of course, one could argue that this is insecure and that a different community should be assigned.
However, with SNMP, the community is transmitted in plain text (except for xref:snmp#v3[SNMP Version 3]).
Anyone who can eavesdrop on the packets can therefore very easily determine the community.
On the other hand, you have limited access to read-only, and in most cases, the information that can be retrieved via SNMP is not very sensitive.

Furthermore, using _different_ communities across multiple devices makes management very cumbersome.
After all, these communities must then be maintained not only in the devices themselves but also in the monitoring system.
That is why, in practice, users usually use the same community everywhere--
or at least throughout a region, a department, a data center, and so on.


[#snmphost]
== Setting up SNMP in {CMK}

[#add_device]
=== Adding a device to {CMK}

Add the devices you want to monitor to {CMK} as hosts, as usual.
If you have organized your folder structure so that each folder contains only SNMP devices, you can configure the remaining settings directly within the folder.
This simplifies the process of later adding additional hosts and also helps to prevent errors.

ifdef::saas[]
In the [.guihint]#Basic settings# panel, you must first select the {CMK} relay that will be used to monitor the SNMP host.
endif::[]
ifdef::onprem[]
In {UE}, in the [.guihint]#Basic settings# box, you can select the {CMK} relay to be used for monitoring the SNMP host if it is not directly accessible from the {CMK} server.
endif::[]

Now, in the host's (or folder's) properties, in the [.guihint]#Monitoring agents# box, set the [.guihint]#{CMK} agent / API integrations# option to [.guihint]#No API integrations, no {CMK} agent#:

image::snmp_host_configuration.png[alt="Adding a host to monitoring via SNMP."]

In the same field, also enable the [.guihint]#SNMP# option and select [.guihint]#SNMPv2 or v3# as the SNMP protocol.
Selecting protocol version v1 is a last resort only for _very_ old devices.
You should only use this if you know that v2 is definitely not supported, or if the implementation on the device is defective (this can occur occasionally in practice).
SNMP version 1 is particularly slow because it does not support bulk access--the speed difference is significant.

The third setting is called [.guihint]#SNMP credentials#.
Here, you must first select a protocol version, since v2c and v3 differ from one another.
We explain version 3 in xref:snmp#v3[below].
If you do not have very high security requirements, v2c is the right choice; alternatively, you can place SNMP communication in a management VLAN to secure it.
SNMPv2c requires you to enter the community discussed above.

There is an alternative method for configuring SNMP credentials if you cannot simply inherit them via your folder structure: the xref:wato_rules#[rule set] [.guihint]#Setup > Agents > SNMP rules > SNMP credentials of monitored hosts#.
This allows you to assign credentials based on host tags, xref:labels#[labels], and similar properties.
The general rule is that a community defined directly on the host or folder always takes precedence over the rules.

ifdef::onprem[]
[%collapsible]
.[#snmp_cmk_agent]#Monitoring via SNMP and the {CMK} Agent?#
====
Occasionally, the question arises as to whether it would be possible--or even practical--to monitor Linux or Windows using SNMP instead of the {CMK} agent.
The answer is very simple: yes, it is possible; no, it's not advisable. Why?

* The monitoring data provided by the SNMP agent is very limited. Therefore, you'll need the {CMK} agent anyway for reasonably effective monitoring.
* The SNMP agent does not provide any useful data that the {CMK} agent wouldn't also provide.
* The SNMP agent is more cumbersome to set up.
* Last but not least, the SNMP protocol requires significantly more CPU and network resources than standard monitoring with {CMK}.

However, there are a few situations in which monitoring via SNMP _in addition_ to the {CMK} agent may be useful.
This can apply to both the {CMK} agent for xref:agent_linux#[Linux] and for xref:agent_windows#[Windows].
A typical example is when a tool provided by the server manufacturer is installed for a software or hardware component (such as a RAID controller) and only provides monitoring data via SNMP, as is the case with Fujitsu ServerView, for example.
In this case, you can, of course, collect additional monitoring data via SNMP, but also be sure to use sufficiently long polling intervals.
On Windows, it may also happen that polling via PowerShell is not possible--either due to the version of Windows being used or because there are no cmdlets available for the application.

If, in such a case, you want to monitor the Linux or Windows host using both the {CMK} agent _and_ SNMP, proceed as follows:
In the host's properties, under the [.guihint]#Setup# menu, set the [.guihint]#Monitoring agents#, set the [.guihint]#{CMK} agent / API integrations# option to a value that includes the {CMK} agent ([.guihint]#API integrations if configured, else {CMK} agent# or [.guihint]#Configured API integrations and {CMK} agent#).
In the same box, enable the [.guihint]#SNMP# option and set the value to [.guihint]#SNMPv2 or v3# or [.guihint]#SNMPv1#, as described above:

image::snmp_host_agent_and_snmp_configuration.png[alt="Adding a host to monitoring via the {CMK} agent and SNMP."]

Services that are available via both SNMP and the {CMK} agent (e.g., CPU utilization, file systems, network cards) are then automatically retrieved by the {CMK} agent rather than via SNMP.
This automatically prevents duplicate data transmission.
====
endif::[]


[#v3]
==== SNMPv3

SNMPv3 provides xref:security[encryption and true authentication].
It also introduces the xref:contexts[concept of _contexts_].
This allows a device to display different information at the same location in the SNMP tree--depending on which _context ID_ is included in the requests.

[#security]
===== Security

SNMPv3 supports various security levels:

[cols="15,~"]
|===
|`noAuthNoPriv` |No strong user-based authentication, no encryption.
The advantage over v2c is that the password is no longer transmitted in plain text but is hashed.
|`authNoPriv` |User-based authentication with a name ([.guihint]#Security name#) and password, but still no encryption.
|`authPriv` |User-based authentication as with `authNoPriv`.
In addition, all data is encrypted.
To do this, you must manually exchange a key and store it both in the device and in {CMK}.
|===

You configure the security level in the same place where you set the community, i.e., either in the host properties or, as a rule, in [.guihint]#SNMP credentials of monitored hosts#.
There, instead of [.guihint]#SNMP community#, select one of the three v3 levels and configure the necessary values:

image::snmp_credentials_v3.png[alt="Configuring SNMPv3 security settings."]


[#contexts]
===== Contexts

If you have a device that works with contexts, you will need two settings in {CMK}:

* First, the device must be queried using SNMPv3.
* Then you'll need a rule in the [.guihint]#SNMPv3 contexts to use in requests# rule set.
Here, select the check plug-in for which contexts should be enabled, and then select the list of contexts for which monitoring data should be retrieved.

Fortunately, situations where you need to work with contexts are very rare, because--unfortunately--the monitoring system cannot automatically recognize them.
Manual configuration of the contexts is always necessary.

[TIP]
====
Using multiple contexts on the same OID branches results in only the data from the first context being retrieved--and services being created for it.
If the data from such overlapping contexts is needed in full for monitoring, it is necessary to create one host per context.
====

[#services]
=== Service configuration

==== Special considerations for SNMP devices

After saving the host properties (and, optionally, the diagnostics), the next step is, as usual, a  xref:wato_services#[Service configuration].
There are a few special considerations here, because for SNMP devices, service detection occurs internally in a completely different way than for hosts monitored by the {CMK} agent.
For the latter, {CMK} can simply examine the agent's output and--with the help of the individual check plug-ins--identify the relevant
points.
With SNMP, a bit more work is required.
Although {CMK} could perform a complete dump of all SNMP data (SNMP walk) during discovery and search for relevant information within it,
there are devices for which a single discovery process would take several hours!

That is why {CMK} takes a more intelligent approach.
It first retrieves only the very first two data entries (OIDs) from the device: the `sysDescr` and `sysObjectID`.
This is followed by additional requests as needed.
Based on the results, each of the approximately 1,000 included SNMP check plug-ins then determines whether the device even supports that particular plug-in.
{CMK} refers to this phase as the _SNMP scan._
As a result, the software outputs a list of check plug-ins that serve as candidates for the actual service discovery.

The actual detection process then takes place in a second step.
The detected plug-ins use locally restricted SNMP requests to retrieve only the specific data they need and use this to identify the services to be monitored.
The data retrieved is exactly the same as what will later be collected regularly for monitoring purposes.

For devices on the LAN, the entire process usually doesn't take very long--taking several seconds is actually the exception.
However, if you're monitoring devices over WAN links with high latency, the entire scan can take several minutes.
Naturally, the scan also takes longer for switches with hundreds of ports.
It would be very inconvenient if you had to wait that long every time you opened the Services page.

Therefore, the setup normally skips the scan and performs detection using only the check plug-ins that are currently in use
on the host.
The SNMP walks are already available as cache files from normal monitoring, so detection doesn't take long.
While this allows you to find new entries from existing plug-ins (e.g., new switch ports, hard drives, sensors, VPNs, etc.), it won't detect entirely _new_ plug-ins.

The [.guihint]#Rescan# button forces an SNMP scan and subsequently retrieves fresh data via SNMP.
This also allows services from completely new plug-ins to be detected.
There may be a delay if devices respond slowly.


==== Standard services

No matter which device you're monitoring via SNMP, the configuration should include at least the following three services:

image::snmp_standard_services.png[alt="Display of the three standard services that every SNMP device should have."]

The first service in the image is a check that monitors the network ports.
The device must have at least one service--which must be active--otherwise, SNMP would not work.
Generally, {CMK} is preset to include all ports that are active (operational status 'up') at the time of service discovery in the monitoring.
You can configure this using the rule set [.guihint]#Setup > Services > Discovery rules > Network interface and switch port discovery#.

By the way, in the Beginner's Guide, you'll find a chapter with recommendations for xref:intro_finetune#switchports[Configuring Switch Ports].

The second service is called [.guihint]#SNMP Info# and displays the four most important pieces of information about the device: the values of the `sysDescr`, `sysName`, `sysLocation`, and `sysContact` fields.
It serves a purely informational purpose and is always {OK}.

And finally, there is the [.guihint]#Uptime# service, which shows you when the device was last rebooted.
This service is always {OK} by default; however, you can set lower and upper thresholds for uptime.

It is not uncommon for a larger SNMP device to cause

endif::[]
ifdef::saas[] 
a relative high fetcher utilization on the Relay.

For this reason, it is important that you familiarize yourself with the performance of monitored devices,
ifdef::onprem[] 
identify problematic devices, and proactively implement xref:core_tuning#[optimizations].
endif::[]
ifdef::saas[]

[#inline]
=== Inline SNMP

ifdef::onprem[]
{cee-only}
While {RE} implements SNMP queries in the traditional way using the `snmpget` and `snmpbulkwalk` commands, the commercial editions feature a built-in SNMP engine (_Inline-SNMP_) that executes SNMP queries very efficiently without creating additional processes.
This roughly halves the CPU load for SNMP processing.
And thanks to the shorter query times, the number of {CMK} processes required simultaneously is reduced, as is the memory usage.
The {CMK} Relay available in {UE} also supports both query methods.

If your {CMK} installation was set up using a very old commercial version or was migrated from {RE} to a commercial version, switch your SNMP devices to Inline-SNMP.
Only in the case of xref:defective[defective implementations] should you use the more robust `snmpget` or `snmpbulkwalk`.
endif::[]
ifdef::saas[]
The {CMK} Relay supports two query methods for SNMP:
the `snmpget` and `snmpbulkwalk` commands, and a built-in SNMP engine that executes SNMP queries very efficiently without creating additional processes.
The CPU load for SNMP processing is about half as high with this method, which is why it is used by default.

Only in the case of xref:defective[defective implementations] should you use the more robust `snmpget` or `snmpbulkwalk`.
endif::[]


[#check_intervals]
=== Check intervals for SNMP checks

If you are reaching the limits of your resources, or if querying a single device takes longer than 60 seconds, you can increase the interval at which {CMK} contacts the host(s).
Using the rule set [.guihint]#Normal check interval for service checks#, which you can apply specifically to the {CMK} services of hosts, you can extend the general interval from one minute to, for example, two, five, or ten minutes.

There is also a rule set specifically for SNMP checks: [.guihint]#Fetch intervals for SNMP sections#.
This rule set allows you to reduce the interval for _individual_ check plug-ins.
It is important to note that you can never set it to be shorter than the interval specified for general monitoring by the [.guihint]#Check_MK# service.

Overall, however, we recommend configuring monitoring so that the default interval of one minute can be maintained, and the polling interval is increased only in exceptional cases for individual hosts or checks.


[#timing_settings]
=== Timing settings for SNMP access

By default, {CMK} expects a response to an SNMP request within one second.
In addition, the monitoring software resends each request multiple times before giving up.
For devices that respond very slowly or are accessible via a very slow network, it may be necessary to change these parameters.
You can do this using the [.guihint]#Timing settings for SNMP access# rule set:

image::snmp_timing_settings.png[alt="Increasing the response timeout."]

Note that these settings apply to a _single SNMP request_.
A complete query of a host consists of many individual requests.
The total timeout is therefore a multiple of the settings specified here.


[#bulk_walk]
=== Bulk Walk: number of OIDs per bulk

By default, SNMP transmits ten responses in a single packet per `GetBulk` request.
Using the rule set [.guihint]#Bulk walk: number of OIDs per bulk#, you can test whether a higher value (such as 20 or 50) improves performance.
However, this will only be the case if large tables are being transferred to the host--for example, if it is a switch with a very large number of ports.

In practice, there may also be isolated cases where devices experience issues with the default value of ten OIDs per bulk.
In such cases, it may be advisable to reduce the number to five, for example.

.More isn't always better!
[%collapsible]
====
The fact that the performance of bulk requests drops off sharply when very large numbers of OIDs are transmitted is also due to the fact that SNMP fills packets with dummy data.
For example, if 20 OIDs were requested but the device only has 17 to provide, three are filled in.
With 50 OIDs, 33 would be padded.
Another factor is the memory requirements of the device being queried.
Less powerful devices, such as simple network printers, are more likely to handle smaller bulk sizes well.
====


[#limiting_ranges]
=== Limit SNMP OID ranges

ifdef::onprem[]
{cee-only}
endif::[]
{CMK} normally operates in such a way that it always retrieves information about all switch ports, even if not all of them are being monitored.
This is actually a good thing, because it is usually faster--selective information cannot be retrieved using the efficient bulk requests.
Furthermore, from our perspective, it's generally advisable to monitor all ports in order to identify defective ports or cables with high error rates.
If ports are not reliably {UP}, you can also configure the link status {DOWN} to be treated as {OK}.

However, there are isolated cases where switches have a very large number of ports and, for whatever reason, respond very slowly or process SNMP very inefficiently, making monitoring impossible when retrieving all port information.

For such cases,
ifdef::onprem[]
in the commercial editions
endif::[]
there is the [.guihint]#Bulk walk: limit SNMP OID Ranges# rule set.
This allows you to statically limit the list of queried data (e.g., ports).
In the rule's value, you specify which indices should be retrieved for each specific branch of the OID tree ([.guihint]#Section name#).

The identification can refer to generic or vendor-specific branches.
The default setting for switch ports is generic and is called [.guihint]#SNMP interface check with 64-bit counters (using v2c)#.
The following example shows a setting in which data is retrieved via SNMP only for the first two ports:

image::snmp_limit_oid_ranges.png[alt="Bulk walk: limit SNMP OID ranges."]

[TIP]
====
This filtering takes place _before_ service discovery and monitoring.
Depending on the setting for [.guihint]#Network interface and switch port discovery#, this does not automatically mean that these two ports are actually being monitored.
====


[#cursedhardware]
== Troubleshooting

The first RFCs for SNMP date back to 1988.
SNMP has been in widespread use since the mid-to-late 1990s.
Especially in the early years, many manufacturers implemented the protocol only partially or incorrectly, and even today, compliance with conventions is not guaranteed for every device.
{CMK} offers a range of measures to nonetheless extract monitoring data from such devices.

[#defective]
=== Defective SNMP implementations

There are devices where SNMP works to some extent, but certain parts of the protocol have not been implemented or have been implemented incorrectly.
A particularly common problem is implementations that have been tested with specific query tools but not for conformance to the specification.

ifdef::onprem[]
If problems occur with the commercial editions of {CMK}, one possible reason may be
endif::[]
ifdef::saas[]
One possible reason for problems may be
endif::[]
that the higher-performance xref:performance[inline SNMP implementation]—which is enabled by default there--relies more heavily on compliance with standards than `snmpget`.
If devices do not respond at all, or do not respond reliably, it sometimes helps to disable inline SNMP for the affected devices and thereby enable the somewhat more robust but significantly slower `snmpget`.

ifdef::onprem[]
For command-line testing, with certain options the `cmk` command provides the additional option `--snmp-backend`, which accepts the parameters `inline` (uses Inline-SNMP), `classic` (uses `snmpget`), or `stored-walk` (uses a stored xref:simulation[SNMP walks]) as a parameter.
If the command-line test was successful, you can use the rule set [.guihint]#Hosts using a specific SNMP backend# to set the [.guihint]#Use Classic backend# setting for hosts that should permanently avoid using inline SNMP.
endif::[]


==== No response to the `sysDescr` query

The most important way to identify SNMP devices is the string in the `sysDescr` field.
If a device does not respond to a query for this OID, that device is considered dead.

It will also fail to return any results in service discovery unless you intervene with a special configuration:
For the affected hosts, create a rule under [.guihint]#Setup > Agents > SNMP rules > Hosts without system description OID# with the option [.guihint]#Positive match (Add matching hosts to the set)#.
{CMK} will then simply assume that everything is fine and skip the `sysDescr` test.
Although check plug-ins that expect specific parts of this text will not be recognized, this is not an issue in practice, since the affected plug-ins were developed to account for this scenario.


==== SNMPv2c works, but bulk requests fail

Although some devices support version v2c (and will return a response to this in the diagnostic), the protocol lacks implementation of the `GetBulk` request command.
{CMK} uses this command to retrieve as much information as possible in a single request; it is therefore very important for performance.

On such a host, some simple SNMP checks will also work, such as [.guihint]#SNMP Info# or [.guihint]#Uptime#.
However, other services are missing--in particular, the network interfaces, which should actually be present on every device.

If you do have a host where this is the case, you can operate it using v2c, but without bulk requests.
For the affected hosts, use the rule [.guihint]#Setup > Agents > SNMP rules > Disable bulk walks#.


==== Devices that respond very slowly

There are devices where some SNMP queries take a very, very long time.
This is sometimes due to faulty implementations.
In such cases, it may help to switch back to SNMPv1 (which is usually much slower, but sometimes still faster than a faulty SNMPv2c).
Before you try this, however, you should check whether the manufacturer provides a firmware upgrade that resolves the issue.

A second possible cause is that the device has a large number of switch ports and, at the same time, a slow SNMP implementation.
If you only want to monitor a very small number of ports (e.g., just the first two), you can manually configure {CMK} to query data from individual ports only.
For details, see the section on xref:snmp#performance[Performance].


[#standard_services]
=== Only the standard services are detected

If you add an SNMP device to monitoring and {CMK} only detects the services [.guihint]#SNMP Info#, [.guihint]#Uptime#, and the interfaces, there could be several reasons for this:


==== There are no plug-ins

{CMK} provides about 1,000 check plug-ins for SNMP devices, but of course even this list is never complete.
As a result, it often occurs that {CMK} does not provide specific plug-ins for certain devices, and you can then only monitor the standard services mentioned above.
ifdef::onprem[]
Here are your possible options in such a situation:

* You may find what you're looking for on the link:https://exchange.checkmk.com[{CMK} Exchange^] website, where users can publish their own plug-ins.
* You can develop plug-ins yourself. You'll find an article on the topic of xref:devel_intro#[Developing extensions (plug-ins)] in this manual.
* You can contact our support team or one of our partners and commission the development of the appropriate plug-ins.
endif::[]
ifdef::saas[]
In this case, your only option is to suggest the development of a corresponding plug-in at link:https://ideas.checkmk.com/[ideas.checkmk.com^].
endif::[]


==== Plug-in detection is not working

Sometimes, a newer firmware update on a device can cause {CMK} plug-ins to no longer recognize the device--for example, because text in the device's system description has changed.
In this case, the existing plug-ins must be updated.
Create an xref:simulation[SNMP-walk] and contact our support team.


==== The device is not providing the required data

Some devices allow you to individually configure access to specific information areas in their SNMP settings.
Your device may be configured to provide the standard information but not the sections for device-specific services.

For a few devices, you must use SNMPv3 and xref:snmp#contexts[Contexts] to access the desired data.


[#no_response]
=== Devices that do not respond to SNMP at all

If not a single version of the SNMP protocol works, there are several possible causes:

ifdef::onprem[]
* The device is not reachable via IP at all.
You can check this with a ping test.
endif::[]
* The device does not support SNMP at all.
* SNMP is not configured correctly (enablement, allowed addresses, community).
* A firewall is blocking SNMP.
You need to enable UDP port 161 in both directions.

[#principle]
=== Principle of the SNMP walk

In certain situations, it can be useful to have a complete dump of all SNMP data from a monitored device written to a file (an _SNMP walk_).
ifdef::onprem[]
You can use this file later to simulate monitoring of the device on another {CMK} server, even if that server has no actual network connection to the device.
endif::[]

We make extensive use of this functionality in support and development to improve existing plug-ins and develop new check plug-ins.
This way our developers do not need access to your devices--only SNMP walks.

[#snmpwalks]
=== Creating a walk via the GUI
endif::[]
ifdef::saas[]
[#snmpwalks]
=== Creating a walk
endif::[]

You can create an SNMP walk directly via the GUI.
This function can be found in the [.guihint]#Check_MK# action menu for the service and also in the hosts' action menu (entry [.guihint]#Download SNMP walk#):

image::snmp_download_walk.png[alt="Downloading the SNMP walk from the host's action menu in the monitoring overview."]

In the best-case scenario, creating the walk takes a few seconds, but a few minutes is not uncommon.

To prevent the GUI from possibly being blocked indefinitely by such a task, a timeout of 15 minutes is set by default.
If necessary, you can increase this via [.guihint]#Setup > General > Global settings > Execution of checks > SNMP walk download timeout#.

Once the walk has been generated, you can download the file from the [.guihint]#Result# line.


ifdef::onprem[]
[#snmpwalk_cli]
=== Creating a walk using the command line

Alternatively, you can also create walks using the command line.
To do so, log in to the site from which the device is being monitored.
You can easily create the walk there using the command `cmk --snmpwalk` and specifying the monitored host (which must be configured for monitoring):

[{shell}]
----
{c-omd} cmk --snmpwalk switch23
----

You can also use the `-v` switch to see more detailed output about the progress:

[{shell}]
----
{c-omd} cmk -v --snmpwalk switch23
switch23:
Walk on ".1.3.6.1.2.1"...
3664 variables.
Walk on ".1.3.6.1.4.1"...
5791 variables.
Wrote fetched data to /omd/sites/mysite/var/check_mk/snmpwalks/switch23.
----

The file is then saved in the `var/check_mk/snmpwalks` directory and is named after the host.
It is a text file.
If you're curious, you can view it using `less`, for example (press the kbd:[Q] key to exit the program):

[{shell}]
----
{c-omd} less var/check_mk/snmpwalks/switch23
.1.3.6.1.2.1.1.1.0 Yoyodyne Frobolator 23 port L2 Managed Switch 
.1.3.6.1.2.1.1.2.0 .1.3.6.1.4.1.11863.1.1.3
.1.3.6.1.2.1.1.3.0 560840147
.1.3.6.1.2.1.1.4.0 Zoe Zhang pass:[<zoe@checkmk.com>]
.1.3.6.1.2.1.1.5.0 cmkswitch23
.1.3.6.1.2.1.1.6.0 Data Center 42
.1.3.6.1.2.1.1.7.0 3
.1.3.6.1.2.1.2.1.0 27
----

The `cmk --snmpwalk` command has several other useful options:

[cols="25,~",options="header"]
|===
|Option |Effect
|`--extraoid <OID>` |When {CMK} performs a walk on a host, it generally retrieves two subtrees from the SNMP data space. These are specified in the SNMP tree via so-called _OIDs_ (object identifiers). These are `MIB-2` and `enterprises`—that is, on the one hand, a standard scope that is standardized and identical for all SNMP devices, and on the other hand, a vendor-specific scope. With a correct implementation of SNMP, the device should send _all_ the data it provides. If that is not the case and you are looking for a specific scope, you can add its OID to the walk using this option, e.g., `cmk --snmpwalk --extraoid .1.2.3.4 switch23`. Don't forget the period at the beginning of the OID.
|`--oid` |This option works similarly to `--extraoid`, but retrieves _only_ the specified OID. This is useful for testing purposes. Note that the walk will then be incomplete.
|`-v` |The `v` stands for _verbose_ and provides some informative output while the walk is running.
|`-vv` |The `vv` here stands for _very verbose_ and provides significantly more information.
|===


[#use_saved_walks]
=== Using saved walks for simulation

If you now want to use this walk for a simulation on another (or the same) {CMK} site, place the walk file on that site in the `var/check_mk/snmpwalks` directory, naming it after the host.
Make sure the site user owns the file and that the permissions are set to `0600` (only the owner may read and write).

Now create a rule in the [.guihint]#Simulating SNMP by using a stored SNMP walk# rule set that applies to the host in question.

From now on, only the stored file will be used when monitoring the host.
There will be no further network access to the host--except for the ping for the host check and any configured active checks.
You can easily redirect these to the {CMK} server by setting the host to [.guihint]#IP address family: No IP#.
endif::[]
