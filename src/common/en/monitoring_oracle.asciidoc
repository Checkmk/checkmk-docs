[#introduction]
== Introduction

In this article, you will learn how to monitor Oracle databases using the new agent plugin `mk-oracle`.

If you are looking for information about the old agent plugin `mk_oracle`, please refer to the link:https://docs.checkmk.com/2.4.0/en/monitoring_oracle.html[article in the 2.4.0 branch of the User Guide].

With the xref:glossar.html#agent_plugin[agent plugin], you can not only retrieve tablespaces or the active sessions of a database, but also many other metrics.
You can find a complete list of monitoring options with our xref:glossar#check_plugin[check plugins] at link:https://checkmk.com/de/integrations?tags=oracle[Catalog of Check Plug-ins^].

The output of `mk-oracle` is identical to that of the old plugin, so the exact same check plugins can continue to be used.

[#how]
=== How does Oracle monitoring work with {CMK}?

To monitor Oracle instances and databases with {CMK}, the {CMK} agent and the `mk-oracle` agent plugin must be installed on the respective host.
The agent plugin requires a configuration file, which you must save as `mk-oracle.yml` in the xref:glossar#dir_conf[configuration directory].
In addition, the agent plugin relies on libraries from the Oracle Instant Client (OIC).
This must therefore also be available on the host.

[#prerequisites_oracle_host]
== Setting up prerequisites on the Oracle host

On every host where you want to monitor Oracle databases or instances, you must meet two prerequisites.

* The Oracle Instant Client (OIC) must be made available to the agent plugin.
For instructions on how to do this, see the xref:install_oic[corresponding chapter].
* The agent plugin `mk-oracle` must be granted access to your Oracle instances or databases. You have two different options for this.
** You can create a user and password on the host that is used exclusively for monitoring via {CMK}.
We explain this method in the chapter xref:create_user[Creating a Database User].
** Alternatively, you can use the xref:oracle_wallet[Oracle Wallet].

The agent plugin `mk-oracle` must be granted access to your Oracle instances or databases.

[.tabs]

[#tab_simple_user]#Simple database user#::
+

[#create_user]
If you want to set up a user for monitoring, we recommend using that user exclusively for {CMK}.

First, connect to your Oracle host and switch to the `oracle` user.

[{shell}]
----
{c-root} su - oracle
----

Finally, specify the instance to which `sqlplus` should connect:

[{shell}]
----
oracle@linux$ export ORACLE_SID=MYINST1
----

Start `sqlplus`.
Specify the role with which `sqlplus` should start.

[{shell}]
----
oracle@linux$ sqlplus / as sysdba
----

Now create a user that will be used exclusively for monitoring Oracle.
The privileges apply to all existing and future databases.

[{sql}]
----
sqlplus> create user checkmk identified by myPassword;
sqlplus> alter user checkmk set container_data=all container=current;
sqlplus> grant select_catalog_role to checkmk container=all;
sqlplus> grant create session to checkmk container=all;
sqlplus> exit
----

[#tab_wallet]#Wallet#::
+
--
[#oracle_wallet]
As an alternative to specifying the user directly with a password in a configuration file, you can also use the _Oracle Wallet_.
This has the advantage that you no longer need to store the credentials in plain text on both the {CMK} server and the Oracle host.
Even if you have adjusted the permissions of the configuration file on the Oracle host accordingly, the credentials have still left the server and are located on the {CMK} server, provided you are using the Agent Bakery.

The Oracle Wallet, in turn, stores the credentials in encrypted form on the host being monitored, so that they can be used without having to explicitly disclose any login information.
{CMK} can use this wallet, meaning that, in principle, only the database administrator (DBA) needs to know the credentials.
To do this, you—or the DBA—create a wallet on the relevant server and store it in the  in a file named `oracle_wallet`.

[{shell}]
----
{c-root} mkstore -wrl /etc/check_mk/oracle_wallet -create
----

The agent plugin will access this file later whenever it needs to establish a connection to an instance.
To ensure that the necessary user data can be found, you must enter it into the wallet once.
In the following example, you add the user `checkmk` for the instance `MYINST1`:

[{shell}]
----
{c-root} mkstore -wrl /etc/check_mk/oracle_wallet -createCredential MYINST1 checkmk myPassword
----


For the agent plugin to know where to look for the wallet, it must find two files.
The first file is `sqlnet.ora`, which specifies the location of the wallet.
The second file—`tnsnames.ora`—specifies the instance's address so that it can also be accessed via its alias.
To ensure the agent plugin finds these files, you can set the path on Linux, Solaris, and AIX using the `TNS_ADMIN` environment variable.
This is particularly useful if the files already exist.
Alternatively, you can also create them explicitly.
On Windows, you must specify these paths manually.

First, create the `sqlnet.ora` file.
The agent plugin will look for the access credentials in this file as a fallback, so you must specify the correct path to the wallet file you just created here.
Be sure to set the `SQLNET.WALLET_OVERRIDE` parameter to `TRUE`:

./etc/check_mk/sqlnet.ora
[{file}]
----
LOG_DIRECTORY_CLIENT = /var/log/check_mk/oracle_client
DIAG_ADR_ENABLED = OFF

SQLNET.WALLET_OVERRIDE = TRUE
WALLET_LOCATION =
 (SOURCE=
   (METHOD = FILE)
   (METHOD_DATA = (DIRECTORY=/etc/check_mk/oracle_wallet))
 
)
----

Now the plugin knows which credentials to use.
To ensure it connects to the correct address, create a file named `tnsnames.ora`.
You can find the exact syntax in the Oracle documentation, but as an example, the file might look like this:

./etc/check_mk/tnsnames.ora
[{file}]
----
MYINST1
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = 127.0.0.1)(PORT = 1521))
    
(CONNECT_DATA =
      (SERVER = DEDICATED)
      (SERVICE_NAME = MYINST1_ALIAS)
    )
  )
----


You can, of course, add additional access credentials to the wallet at a later time.
In that case, you may need to update the `tnsnames.ora` file.

Finally, change the permissions of the files and directories created manually in this section so that the access rights are set correctly when the program runs.
The agent plugin, which runs as `root`, changes
 to the owner of the Oracle binaries (e.g., `$ORACLE_HOME/bin/sqlplus`) before executing them.
Therefore, at least the group of the owner of the Oracle binaries requires read access to the manually created files in `/etc/check_mk/`.
In the following example, we assume that the group is `oinstall`.

The following commands change the group to `oinstall`:

[{shell}]
----
{c-root} chgrp oinstall /etc/check_mk/sqlnet.ora /etc/check_mk/tnsnames.ora
{c-root} chgrp -R oinstall /etc/check_mk/oracle_wallet
----

These commands then ensure that the group can read the `oracle_wallet` directory and its contents:

[{shell}]
----
{c-root} chmod g+x /etc/check_mk/oracle_wallet
{c-root} chmod -R g+r /etc/check_mk/oracle_wallet
----

Afterward, the permissions should look something like this:

[{shell}]
----
{c-root} tree -ugpR /etc/check_mk
[drwxr-xr-x root root ] /etc/check_mk
├── [drwxr-x--- root oinstall ] oracle_wallet
│ └── [-rw-r----- root oinstall ] cwallet.sso
│ └── [-rw-r----- root oinstall ] cwallet.sso.lck
│ └── [-rw-r----- root oinstall ] ewallet.p12
│ └── [-rw-r----- root oinstall ] ewallet.p12.lck
├── [-rw-r--r-- root oinstall ] sqlnet.ora
├── [-rw-r--r-- root oinstall ] tnsnames.ora
----

The command output shows only the relevant files and directories.

[#setup_custom_sqls]
== Setting Up Custom SQL Queries

{cce-only}
Custom SQL queries cannot be defined via the [.guihint]#Unified Oracle Plugin (Beta)# rule.
You must perform the necessary configuration directly on the host from which you monitor your Oracle instances and databases.

[#custom_sqls_why]
=== Why use custom SQL queries?

{CMK} already provides a large number of SQL queries via the agent plugin that you can use to monitor your database instances.
To ensure these queries are suitable for as wide a range of technical and content-related requirements as possible, they are kept general.

To meet the individual requirements of each company for monitoring a specific database, {CMK} the option to create your own custom SQL queries (_Custom SQLs_) and have the agent plugin execute them.
These are then automatically recognized and monitored as services in {CMK}.

You have two options for passing your queries to the agent plugin:

* Either write the queries directly into the configuration file `mk-oracle.yml`.
* Or, instead, specify in the configuration file where the agent plugin can find the files in which your custom SQL queries are stored.

The latter approach simplifies maintenance and also makes version control easier, since content is not mixed in with the plugin's configuration file.
However, if you are only dealing with a small number of queries anyway, you may want to skip the extra effort.

we will start with a simple example that is written directly into the plugin's configuration file.

[#custom_sqls_simple]
=== Setting Up Simple Custom SQL Queries

First, we will show you how to quickly get a result that returns real data from an Oracle instance.
This example is only meant to illustrate how easy it *can* be to integrate custom SQL queries.
Just how useful this exact query is in everyday work remains to be seen.

For now, we will pretend we are just feeling our way through things and run the SQL query as a test using the `sysdba` user in a test instance.


[{shell}]
----
oracle@linux$ sqlplus / as sysdba
----

[{sql}]
----
sqlplus> SELECT 'details:Free memory: ' || ROUND(SUM(bytes)/1024/1024, 2) || ' MB' FROM v$sgastat WHERE name = 'free memory';
'DETAILS:FREEMEMORY:'||ROUND(SUM(BYTES)/1024/1024,2)||'MB'
----------------------------------------------------------------
details:Free memory: 230.86 MB
----

We can ignore the header of this output—just as the agent plugin does.
What's important is the keyword `details` that we specified in the query.
The check plugin on the {CMK} server will extract the line that begins this way and use it to generate the [.guihint]#Summary# for the service.
But how does {CMK} know what the service is actually supposed to be called?
We specify the name of the service when we transfer the SQL query to the configuration for the agent plugin:

.mk-oracle.yml
[{yaml},highlight=10..12]
----
---
oracle:
  main:
    connection:
      hostname: localhost
    authentication:
      username: mymonitoringuser
      password: mypassword
      type: standard
    custom_metrics:
      - My service:
          
sql: "SELECT 'details:Free memory: ' || ROUND(SUM(bytes)/1024/1024, 2) || ' MB' FROM v$sgastat WHERE name = 'free memory'"
----

In this example, we see three things:

* To include custom SQL queries, you always need a key named `custom_metrics`.
* This is followed by a list (here: `My service`).
In YAML, such a list begins with a `-`.
The name of this list becomes part of the service name in {CMK} and can be chosen freely.
* Next comes the line containing the query.
It must begin with `sql:`, and the query itself must be enclosed in double quotes.
Also note here that the query *must not* end with a semicolon.

After you have inserted this line into the agent plugin's configuration file on your Oracle host, you can return to your {CMK} server.
There, perform a service discovery for the Oracle host.
You will then see this new service:

image::monitoring_oracle_custom_sql_discovery.png[]

The service name consists of several components:

* The name always begins with [.guihint]#ORA#.
* This is followed by the SID (here: [.guihint]#FREE#).
* The subsequent [.guihint]#SQL# indicates that this service was created by a custom SQL query.
* This is followed by the string you were able to choose freely in the configuration file, in uppercase letters.

In the Summary, you will already see data derived from the results of the SQL query.

There will certainly be cases where such a simple query is exactly what you need.
In that case, however, the service is likely still of little use.
That's why, in the chapter xref:custom_sqls_advanced[Advanced Custom SQL Queries], we will show you how to create a more comprehensive service in just a few steps.


[#custom_sqls_advanced]
=== Setting Up Advanced Custom SQL Queries

Building on the example in the chapter xref:custom_sqls_simple[Simple Custom SQL Queries] , we will now show you how to set up a service with a single metric in just a few steps.

To do this, it's a good idea to move the SQL query out of the agent plugin's configuration file.
Instead, specify a file after the `custom_metrics` key where the agent plugin can find your SQL queries.

.mk-oracle.yml
[{yaml},highlight=10..12]
----
---
oracle:
  main:
    connection:
      hostname: localhost
    authentication:
      username: mymonitoringuser
      password: mypassword
      type: standard
    custom_metrics:
      - My advanced service:
          
path: 'myadvancedservice.sql'
----

If you specify the file without an absolute path, the agent plugin searches several directories in a specific order.
We explain which directories these are and exactly what happens during this process in the xref:reference[Reference chapter] of this article.

Now, in the {CMK} agent's xref:glossar#dir_conf[configuration directory], create a subdirectory named `orasql` and create a file within it with the `.sql` extension, as specified after `path:`.

In this example, we assume that the configuration directory on a Linux host is `/etc/check_mk/`.
First, create the required `orasql` subdirectory.

[{shell}]
--- -
{c-root} mkdir /etc/check_mk/orasql
----

Next, create the file `myadvancedservice.sql` in that directory.
You can now much more conveniently include multi-line SQL queries in this file.
It is important to ensure that the keywords for the check plugin are included.

./etc/check_mk/orasql/myadvancedservice .sql
[{sql}]
----
SELECT 'details:Free memory: ' || REPLACE(ROUND(SUM(bytes) / 1024 / 1024, 2), ',', '.') || ' MB' FROM v$sgastat WHERE name = 'free memory'
UNION ALL
SELECT 'perfdata:free_ram_mb=' || REPLACE(ROUND(SUM(bytes) / 1024 / 1024, 2), ',', '.') FROM v$sgastat WHERE name = 'free memory'
UNION ALL
SELECT 'exit:0' FROM dual
----

In addition to the first line, which you already know from the simple example, there is now a line that begins with `perfdata`.
{CMK} will generate a metric from this and automatically create a graph.
You can also use the keyword `exit` to influence the status of the service.
In this example, we set this to `0`, which corresponds to the status {OK} .
The check plugin requires these keywords on the {CMK} server to generate services and metrics from the supplied data.
We explain the four keywords `details`, `perfdata`, `long`, and `exit` in detail in the chapter xref:format_and_prefixes[Output Formatting and Keywords].

Once you have set all this up and run a service discovery again, the old service will disappear, and a new one—whose name ends with [.guihint]#MY ADVANCED SERVICE#—will be found instead.

[#migrate_sql_queries]
=== Migration of User-Defined SQL Queries

The old agent plugin `mk_oracle` forwards user-defined SQL queries via the command-line tool `sqlplus`.
The `mk-oracle` plugin, on the other hand, executes SQL queries directly via the Oracle Instant Client driver.
This change in the execution model has two major consequences for existing SQL queries.

==== Basic limitations and execution model

===== No SQL*Plus commands

* Commands such as PROMPT, SET, COLUMN, SPOOL, EXEC/EXECUTE, or VAR/VARIABLE are features of the `sqlplus` client tool and are not part of the SQL database language.
They do not work under the OIC driver.
* No anonymous PL/SQL blocks: Anonymous blocks in the format `DECLARE/BEGIN {...} END;` cannot be executed directly as a script.
Only pure SQL statements are supported.

The agent plugin in migration mode checks every referenced SQL file and, if discrepancies are found, issues a warning in the terminal as well as in the generated configuration file.
Although the affected sections are migrated, you must manually adjust them; otherwise, the queries will fail at runtime.

===== Features of the new execution model

* Multiple statements: A `.sql` file can contain multiple, top-level SQL statements separated by semicolons.
These are executed sequentially, and their results are concatenated.
* Each returned result must comply with the specifications for xref:format_and_prefixes[Output formatting and keywords].

==== Removing SQL*Plus commands

Formatting commands and interactive commands from `sqlplus` have no equivalent in the Oracle Instant Client driver.
You must therefore delete them without replacement.
The agent plugin outputs each returned data row directly.

Next, we will first show an SQL file that still worked for `mk_oracle`:

[{sql}]
----
SET PAGESIZE 0
SET FEEDBACK OFF
COLUMN details FORMAT A80
PROMPT collecting session count ...
SELECT 'details:' || COUNT(*) || ' sessions' FROM v$session;
----

You must rewrite such a file for `mk-oracle` as follows so that it works with OIC:

[{sql}]
----
SELECT 'details:' || COUNT(*) || ' sessions' FROM v$session
----


==== Converting PL/SQL blocks to pure SELECT queries

In most cases, anonymous PL/SQL blocks can be replaced with standard SQL constructs:
* PL/SQL variables become WITH clauses (Common Table Expressions).
* `IF/ELSIF` conditions are replaced by CASE statements.
* `DBMS_OUTPUT.PUT_LINE` outputs are represented using `UNION ALL` or separate statements separated by semicolons.

In the following example, we show an SQL file that contains a PL/SQL block:

[{sql}]
----
SET SERVEROUTPUT ON
DECLARE
    invalid_count NUMBER;
BEGIN
    SELECT COUNT(*) INTO invalid_count
      FROM dba_objects
     WHERE status = 'INVALID';
    IF invalid_count > 10 THEN
        DBMS_OUTPUT.
 PUT_LINE('exit:2');
    ELSE
        DBMS_OUTPUT.PUT_LINE('exit:0');
    END IF;
    DBMS_OUTPUT.PUT_LINE('details:' || invalid_count || ' invalid objects');
END;
----

You must rewrite such a file into plain SQL for `mk-oracle`.
It could look something like this, for example:

[{sql}]
----
WITH invalid AS (
    SELECT COUNT(*) AS cnt
      FROM dba_objects
     
WHERE status = 'INVALID'
)
SELECT 'exit:' || CASE WHEN cnt > 10 THEN '2' ELSE '0' END FROM invalid
UNION ALL
SELECT 'details:' || cnt || ' invalid objects' FROM invalid
----


==== Moving complex PL/SQL logic into stored functions

If the logic absolutely requires PL/SQL (e.g., for loops, complex error handling, or temporary states), the logic must be moved into the database itself as a pipelined function.

To do this, you must set up the pipelined function once in your database:

[{sql}]
----
CREATE OR REPLACE FUNCTION checkmk_invalid_objects
    RETURN sys.odcivarchar2list PIPELINED
AS
    invalid_count NUMBER;
BEGIN
    SELECT COUNT(*) INTO invalid_count
      FROM dba_objects
     
WHERE status = 'INVALID';

    -- Any PL/SQL logic is allowed here
    PIPE ROW ('details:' || invalid_count || ' invalid objects');
    
PIPE ROW ('perfdata:invalid_objects=' || invalid_count || ';10;100');
    PIPE ROW (CASE WHEN invalid_count > 10 THEN 'exit:2' ELSE 'exit:0' END);
    RETURN;
END;
/

GRANT EXECUTE ON checkmk_invalid_objects TO checkmk;
----

Once this pipelined function is set up, you can have the agent plugin call it:

[{sql}]
----
SELECT column_value FROM TABLE(checkmk_invalid_objects)
----

If the function is in a different schema, the schema name must be prefixed: `TABLE(owner.checkmk_invalid_objects)`.

[#custom_sqls]
=== Custom SQL queries

Using the configuration key `custom_metrics`, you can define ad-hoc SQL queries whose output is evaluated on the {CMK} server by the Check plugin link:https://checkmk.com/integrations/oracle_sql[oracle_sql^].
Each entry is identified by an item name, which is displayed in {CMK} as part of the service name.

==== Basics and configuration

You can either pass the SQL queries directly as a string or load them from a file.
In the following example configuration, you will find an SQL query in the global section designated by the key `oracle.main`.
Under the key `oracle. main.instances`, you can specify a key `custom_metrics`, which is then, of course, executed only for these instances.

.mk-oracle.yml
[{yaml}]
----
- --
oracle:
  main:
    connection:
      hostname: localhost
    authentication:
      username: mymonitoringuser
      password: mypassword
      type: standard
    custom_metrics:
      - product_price: # Item name -> becomes the service "<SID> SQL PRODUCT_PRICE"
          
sql: "SELECT 'details:Price OK' FROM dual"
    instances:
      - service_name: FREE
        custom_metrics:
          - last_sessions: # Runs only against this specific instance
              sql: "SELECT 'details:per-instance' FROM dual"
----

* An instance always executes both globally defined SQL queries and its own instance-specific SQL queries.
* If a global entry and an instance-specific entry share the same item name, the instance-specific entry always takes precedence.

==== External SQL files (path:)

Instead of writing SQL queries directly into the agent plugin's configuration file via `sql:`, you can use `path:` to reference external `.sql` files.
This works for both `custom_metrics` and predefined sections.

===== Variants of the path specification

.mk-oracle.yml
[{yaml}]
----
custom_metrics:
  
# 1. Absolute path to a file
  - heavy_query:
      path: '/opt/checkmk/sql/heavy_query.sql'
  
# 2. Relative path
  # First searched for in MK_LIBDIR/... and then in MK_CONFDIR/...
  - product_price:
      path: 'queries/product_price.sql'

  # 3. Directory path
  
# The filename is automatically derived from the item name (here: "sessions_stats.sql")
  - sessions_stats:
      path: 'queries/'

  # 4. File with inline fallback
  # If the file cannot be resolved, the inline SQL is used
  - last_resort:
      path: 'queries/ last_resort.sql'
      sql: "SELECT 'details:fallback' FROM dual"
----


==== Resolution rules

Absolute vs. relative::
Absolute paths are adopted exactly as specified.
Relative paths are first searched for under `MK_LIBDIR/plugins/packages/mk-oracle/orasql/` and then under `MK_CONFDIR/orasql/`.
If the file exists in both directories, the file in `MK_LIBDIR` takes precedence.

File vs. directory::
A path can refer to a specific file (with or without a `.sql` extension) or to a directory.
If it refers to a directory, the filename is derived from the item name for `custom_metrics` and from the section name for predefined sections.

Version-dependent variants::
In addition to the base file (`<name>.sql`), you can provide Oracle-specific variants in the format `<name>@<min_version>.sql` (e.g., `sessions@12010000.sql`).
The plugin automatically selects the file with the highest `min_version` that is less than or equal to the version of the connected Oracle instance.
An 8-digit numeric format is used for versioning (`MMmmRRSSSS` for Major / Minor / Release / Patch).
Example: 12.1.0.2 → 12010002.

Fallback chain::
The order for determining the SQL query is: `path:` > (inline) `sql:` > included default code (only for predefined sections).
If `path:` fails and no `sql:` is defined, the section generates no output.


==== SQL parameters

You can define named parameters that are inserted into the SQL code before execution.
Each placeholder in the format `${<name>}` is replaced literally with the configured value.
This works for both inline SQL and `.sql` files.

.mk-oracle.yml
[{yaml}]
----
---
custom_metrics:
  - test:
      sql: 'SELECT ${parameter_1} FROM dual; SELECT ${parameter_2} FROM dual'
      sql_params:
        parameter_1: 'value_1'
        
parameter_2: '${ENV_VAR_1}'
----

* `${ENV_VAR_1}` is resolved from the environment variables.
* *Literal substitution (no bind variables)*: All values are inserted into the statement unchanged.
You can therefore also pass column or table names.
* *Environment variables*: A value can reference environment variables (format `$VAR` or `${VAR}`). These are resolved when the configuration is read.
If a referenced variable is not set, the parameter is skipped with a warning.
The placeholder remains in the SQL code (which usually results in an SQL error rather than executing a query with empty values).
* *Unused parameters*: Placeholders without a matching parameter value are ignored and remain unchanged in the code.

[#format_and_prefixes]
==== Output formatting and keywords

The `mk-oracle` agent plugin automatically inserts the section header `pass:[<<<]<<oracle_sql:sep(58)pass:[>>>]` as well as the subsection header `[[[<SID>|<item>]]]`.
The SQL to be executed is responsible solely for the body of the output.
Each SQL query must return rows with a single string column.
The value must begin with one of the following prefixes so that the Checkmk plugin can interpret it correctly:

* `details`:
Here you can specify what should be displayed in the [.guihint]#Summary# of the generated service.
The line begins with the keyword followed by a colon.
The rest of the line constitutes the output.

* `perfdata`:
Metrics are passed using this keyword.
Within a single line, you can specify any number of metrics—separated by a space.
You can also spread the metric output across multiple lines.
Simply start each line with the keyword `perfdata:`.

* `long`:
If you want the service to have a long output for the [.guihint]#Details# field, you can specify it here.
You can also use this keyword multiple times to generate several lines in the [.guihint]#Details#.

* `exit:`:
If the output should have a specific status, you can specify it here.
The familiar values `0`, `1`, `2`, `3` are available for the statuses {OK}, {WARN}, {CRIT}, {UNKNOWN}.
