[#introduction]
== Introduction

In this article, you will learn how to monitor Oracle databases using the new agent plug-in `mk-oracle-v2`.

If you are looking for information on our old agent plug-in `mk_oracle`, please see link:https://docs.checkmk.com/2.4.0/en/monitoring_oracle.html[the article of the same name in the 2.4.0 branch of the User Guide].

With the xref:glossar.html#agent_plugin[agent plug-in], you can not only retrieve tablespaces or the active sessions of a database, but also many other metrics.
You can find a complete list of monitoring options available with our xref:glossar#check_plugin[check plug-ins] in the link:https://checkmk.com/integrations?tags=oracle[Catalog of check plug-ins^].

The output of `mk-oracle-v2` is identical to that of the old plug-in, so the exact same check plug-ins continue to be used.


[TIP]
====
The new agent plug-in for monitoring Oracle is an executable binary.
It is available for IBM AIX (64-bit POWER), Linux (`x86_64`), Oracle Solaris (`x86_64`), and Windows (`x86_64`).
We will also offer the new agent plug-in for Linux on `aarch64` (64-bit ARM) in one of the upcoming versions of {CMK}.
Until then, you will need to continue using the old shell script on Linux architecture.
====

[#how]
=== How does Oracle monitoring work with {CMK}?

To monitor Oracle instances and their databases with {CMK}, you must install the {CMK} agent and the `mk-oracle-v2` agent plug-in on the respective host.
The agent plug-in requires a configuration file, which you must save as `mk-oracle.yml` in the xref:glossar#dir_conf[configuration directory].
In addition, the agent plug-in relies on libraries from the Oracle Instant Client (OIC).
Therefore, the Oracle Instant Client must also be available on the host.

For instructions on how to install the OIC, see the chapter xref:prerequisites_oracle_host[Setting up prerequisites on the Oracle host].


[#prerequisites_oracle_host]
== Setting up the prerequisites on the Oracle host

On each host where you want to monitor Oracle databases or instances, you must satisfy two prerequisites.

* The _Oracle Instant Client (OIC)_ client library must be made available to the agent plug-in.
For instructions on how to do this, see the relevant xref:install_oic[Deploying Oracle Instant Client (OIC)] chapter.
* The `mk-oracle-v2` agent plug-in must be granted access to your Oracle instances or databases. You have two options for doing this:
** You can create a user and password on the host that is used exclusively for monitoring by {CMK}.
We explain this method in the chapter xref:create_user[Create a database user].
** Alternatively, you can use the xref:oracle_wallet[Oracle Wallet].


[#install_oic]
=== Deploying Oracle Instant Client (OIC)

The `mk-oracle-v2` agent plug-in requires the Oracle Instant Client (OIC) libraries in order to function.
You have three options for deploying OIC.

* You can install OIC xref:#install_oic[exclusively for the agent plug-in]. This is the method we recommend, which we describe here.
* Alternatively, you can xref:#install_oic_globally[install OIC globally on the host].
* If OIC is already installed on the host and you want to use this installation for monitoring via {CMK}, you can tell the agent plug-in where to find OIC by adding an entry to the configuration. Link to the option in the rule.

First, download the package appropriate for your host from the page link:https://www.oracle.com/de/database/technologies/instant-client/downloads.html[Oracle Instant Client downloads] in ZIP format.

[.tabs]
====
[#tab_oic_linux]#Linux#::
+
--
For a Linux x86-64 system, for example, use this link:https://download.oracle.com/otn_software/linux/instantclient/2326200v2/instantclient-basiclite-linux.x64-23.26.2.0.0.zip[Basic Light Package (ZIP)].

Verify the name of the {CMK} agent's plug-in directory on your host:

[{shell-raw}]
----
{c-root} pluginsdir=$(cmk-agent-ctl dump | grep "^PluginsDirectory" | head -1 | awk '{print $2}')
{c-root} echo "$pluginsdir"
/usr/lib/check_mk_agent/plugins
----

Unzip the archive file into that very same plug-in directory:

[{shell-raw}]
----
{c-root} mkdir -p "${pluginsdir}/libexec/mk-oracle-v2/oic"
{c-root} unzip -j instantclient-basiclite-linux.x64-23.26.2.0.0.zip -d "${pluginsdir}/libexec/mk-oracle-v2/oic"
----

Since some ZIP files contain Oracle Linux user IDs, and an existing user with that ID could therefore become the owner of the client library, as a safety precaution you should change the owner and access permissions:

[{shell-raw}]
----
{c-root} chown -R root:root "${pluginsdir}/libexec/mk-oracle-v2/oic"
{c-root} chmod -R go-w "${pluginsdir}/libexec/mk-oracle-v2/oic"
----

--
[#tab_oic_windows]#Windows#::
+
--
For Windows, for example, use the link:https://download.oracle.com/otn_software/nt/instantclient/2326300/instantclient-basiclite-windows.x64-23.26.3.0.0.zip[Basic Light Package (ZIP)].

Extract the archive into the `libexec\mk-oracle-v2\oic` subdirectory of the xref:glossar#dir_plugins[plug-in directory].

By default, on a Windows host, the directory for the OIC would be `%PROGRAMDATA%\checkmk\agent\plugins\libexec\mk-oracle-v2\oic`.

[#allow_access]
=== Grant access rights for the agent plug-in

The agent plug-in `mk-oracle-v2` must be granted access to your Oracle instances or databases.
You can do this either through a database user or the Oracle Wallet.

[.tabs]
====
[#tab_simple_user]#Simple database user#::
+
--
[#create_user]
If you want to set up a regular user for monitoring, we recommend using that user exclusively for {CMK}.

First, connect to your Oracle host and switch to the user under whose account the Oracle database is running. This is usually `oracle`:

[{shell}]
----
{c-root} su - oracle
----

Store the instance that `sqlplus` should connect to in an environment variable:

[{shell}]
----
oracle@linux$ export ORACLE_SID=MYINST1
----

Start `sqlplus`.
Specify the role with which `sqlplus` should start.

[{shell}]
----
oracle@linux$ sqlplus / as sysdba
----

Now create a user that will be used exclusively for monitoring Oracle.
The permissions will apply to all existing and future databases.

[{sql}]
----
sqlplus> create user checkmk identified by myPassword;
sqlplus> alter user checkmk set container_data=all container=current;
sqlplus> grant select_catalog_role to checkmk container=all;
sqlplus> grant create session to checkmk container=all;
sqlplus> exit
----
--

[#tab_wallet]#Wallet#::
+
--

[#oracle_wallet]
As an alternative to specifying the user directly with a password in a configuration file, you can also use the _Oracle Wallet_.
This has the advantage that you no longer need to store the login credentials in cleartext on both the {CMK} server and the Oracle host.
Even if you have adapted the permissions for the configuration file on the Oracle host accordingly, the login credentials will still have left the server and will also be located on the {CMK} server,
provided you are using the agent bakery.

The Oracle Wallet, in turn, stores the credentials in an encrypted form on the host being monitored, so that they can be used without having to explicitly disclose any login credentials.
{CMK} can use this wallet, meaning that, in principle, only the database administrator (DBA) needs to know the credentials.
To do this, you—or the DBA—create a wallet on the relevant server and store it in the xref:glossar#dir_conf[configuration directory] in a file named `oracle_wallet`.

[{shell}]
----
{c-root} mkstore -wrl /etc/check_mk/oracle_wallet -create
----
The agent plug-in will later access this file whenever it needs to establish a connection to an instance.
To ensure that the necessary user data can be found, you must enter it into the wallet once.
In the following example, you add the user `checkmk` for the site `MYINST1`:

[{shell}]
----
{c-root} mkstore -wrl /etc/check_mk/oracle_wallet -createCredential MYINST1 checkmk myPassword
----

In order for the agent plug-in to know where to look for the wallet, it must locate two files.
The first file is `sqlnet.ora`, which specifies the location of the wallet.
The second file—`tnsnames.ora`—defines the instance's address so that it can also be accessed via its alias.
To ensure the agent plug-in finds these files, you can set the path on Linux, Solaris, and AIX using the `TNS_ADMIN` environment variable.
This is particularly useful if the files already exist.
Alternatively, you can create them explicitly.
On Windows, you must specify these paths manually.

First, create the `sqlnet.ora` file.
The agent plug-in searches this file for the connection credentials as a fallback, so you must specify the correct path to the wallet file you just created here.
Be sure to set the `SQLNET.WALLET_OVERRIDE` parameter to `TRUE`:

./etc/check_mk/sqlnet.ora
[{file}]
----
LOG_DIRECTORY_CLIENT = /var/log/check_mk/oracle_client
DIAG_ADR_ENABLED = OFF

SQLNET.WALLET_OVERRIDE = TRUE
WALLET_LOCATION =
 (SOURCE=
   (METHOD = FILE)
   (METHOD_DATA = (DIRECTORY=/etc/check_mk/oracle_wallet))
 )
----

The plug-in will now know which credentials to use.
To ensure it connects to the correct address, create a file named `tnsnames.ora`.
You can find the exact syntax in the Oracle documentation, but here is an example of what the file might look like:

./etc/check_mk/tnsnames.ora
[{file}]
----
MYINST1
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = 127.0.0.1)(PORT = 1521))
    (CONNECT_DATA =
      (SERVER = DEDICATED)
      (SERVICE_NAME = MYINST1_ALIAS)
    )
  )
----

You can, of course, add additional credentials to the wallet at a later time.
In that case, you may need to update the `tnsnames.ora` file.

Finally, change the permissions of the files and directories created manually in this section so that the access rights are set correctly when they are executed.
The agent plug-in, which runs as `root`, switches to the owner of the Oracle binaries (e.g., `$ORACLE_HOME/bin/sqlplus`) before executing them.
Therefore, at a minimum, the group of the Oracle binary owner requires read access to the manually created files in `/etc/check_mk/`.
In the following example, we assume that the group is `oinstall`.

The following commands change the group to `oinstall`:

[{shell}]
----
{c-root} chgrp oinstall /etc/check_mk/sqlnet.ora /etc/check_mk/tnsnames.ora
{c-root} chgrp -R oinstall /etc/check_mk/oracle_wallet
----

These commands ensure that the group can read the `oracle_wallet` directory and its contents:

[{shell}]
----
{c-root} chmod g+x /etc/check_mk/oracle_wallet
{c-root} chmod -R g+r /etc/check_mk/oracle_wallet
----

Afterward, the permissions should look something like this:

[{shell}]
----
{c-root} tree -ugpR /etc/check_mk
[drwxr-xr-x root     root    ]  /etc/check_mk
├── [drwxr-x--- root   oinstall ]  oracle_wallet
│   └── [-rw-r----- root   oinstall ]  cwallet.sso
│   └── [-rw-r----- root   oinstall ]  cwallet.sso.lck
│   └── [-rw-r----- root   oinstall ]  ewallet.p12
│   └── [-rw-r----- root   oinstall ]  ewallet.p12.lck
├── [-rw-r--r-- root   oinstall ]  sqlnet.ora
├── [-rw-r--r-- root   oinstall ]  tnsnames.ora
----

The command output shows only those files and directories that are relevant to the configuration of the Oracle Wallet.
--

[#manual_configuration]
=== Manually set up Oracle monitoring

This chapter is intended for anyone who uses {CRE} or wishes to avoid using the agent bakery.

Once you have met the xref:prerequisites_manual_configuration[prerequisites], you must xref:install_agent_plugin[install the agent plug-in on the Oracle host].
At this point, it is worth noting that this works a little differently than you might be used to with other agent plug-ins.

Last but not least, you will need to provide the agent plug-in with a xref:create_config[configuration].

First, we will go over the prerequisites again.


[#prerequisites_manual_configuration]
==== Prerequisites for a manual setup

Before you can begin the manual setup, verify that the following two prerequisites have been met:

* The {CMK} agent must already be installed and registered on the Oracle host.
We explain how to do this in the articles xref:agent_linux#install[Monitoring Linux] and xref:agent_windows#install[Monitoring Windows].
* You must also have already ensured that the xref:install_oic[Oracle Instant Client] is available on the host.

Once all prerequisites have been met, you can proceed to install the agent plug-in.


[#install_agent_plugin]
==== Installing the agent plug-in

The `mk-oracle-v2` agent plug-in comes with two helper programs, which are ultimately only there to launch `mk-oracle-v2` itself in either synchronous or asynchronous mode.
You must also install these two helper programs on the host, which we will demonstrate first.

[.tabs]
====
[#tab_install_linux]#Linux#::
+
--
ifdef::onprem[]
In addition to the `mk-oracle` agent plug-in, you will also need the `oracle_unified_sync` and `oracle_unified_async` files.
You can find all three files in {CRE} under [.guihint]#Setup > Agents > Other operating systems > Oracle#.
In the commercial editions, go to the [.guihint]#Setup# menu and select [.guihint]#Agents > Windows, Linux, Solaris, AIX# to first access the xref:wato_monitoringagents#bakery[agent bakery], where you will find the ready-made packages.
From there, you can access the list of agent files via the menu item [.guihint]#Related > Other operating systems#.

If you have file system access, you can find all the necessary files in the `~/lib/python3/cmk/plugins/oracle/agents/` directory of your {CMK} site.
endif::[]
ifdef::saas[]
In addition to the `mk-oracle` agent plug-in, you will also need the files `oracle_unified_sync` and `oracle_unified_async`.
In {CE}, go to the [.guihint]#Setup# menu and select [.guihint]#Agents > Windows, Linux, Solaris, AIX# to first access the xref:wato_monitoringagents#bakery[agent bakery], where you will find the baked packages.
From there, use the menu item [.guihint]#Related > Other operating systems# to access the list of agent files.
endif::[]

Transfer the three files to the Oracle host using any method of your choice.
If `wget` is available on the host, you could proceed as follows:

[{shell-raw}]
----
{c-root} wget -O /tmp/mk-oracle-v2 "http://myserver/mysite/check_mk/download_agent_plugin.py?path=/omd/sites/mysite/lib/python3/cmk/plugins/oracle/agents/mk-oracle"
{c-root} wget -O /tmp/mk-oracle-v2_sync "http://myserver/mysite/check_mk/download_agent_plugin.py?path=/omd/sites/mysite/lib/python3/cmk/plugins/oracle/agents/oracle_unified_sync"
{c-root} wget -O /tmp/mk-oracle-v2_async "http://myserver/mysite/check_mk/download_agent_plugin.py?path=/omd/sites/mysite/lib/python3/cmk/plugins/oracle/agents/oracle_unified_async"
----

[.admonition-important]
****
Attentive readers may notice here that the target files have different names than the source files.
This renaming is absolutely necessary and will be assumed as we proceed with this article.
Even if you transferred the files from your {CMK} server using a different method, you must rename them.
In future versions, the files we ship with {CMK} will already be named `mk-oracle-v2`, `mk-oracle-v2_sync`, and `mk-oracle-v2_async`.
****

Here, the three files get downloaded to the `/tmp` directory on the Oracle host.
The following steps will assume this storage location.

Install the plug-in on the Oracle host in the agent's xref:glossar#dir_plugins[plug-in directory] (by default, `/usr/lib/check_mk_agent/plugins`).
You can find the name of the plug-in directory on your host in the output from the {CMK} agent.
The following command sets the plug-in directory in the `pluginsdir` variable.
The subsequent commands will then also use `$pluginsdir`.
If the next command does not produce meaningful output for you—for example, because `awk` is not available—simply enter the actual plug-in directory into `pluginsdir` yourself so that you can continue working with the specified commands.

[{shell}]
----
pass:[#] Determine the plug-in path and store it to a variable
{c-root} export pluginsdir=$(cmk-agent-ctl dump | awk '/^PluginsDirectory:/ {print $2; exit}')
pass:[#] Test the result
{c-root} echo pass:[$]pluginsdir
/usr/lib/check_mk_agent/plugins
----

Now the necessary files are on the Oracle host, and the variable `$pluginsdir` specifies the location of the plug-in directory.
Finally install `mk-oracle-v2` on the host:

[{shell}]
----
{c-root} install -D -m 755 /tmp/mk-oracle-v2 "$pluginsdir/libexec/mk-oracle-v2/mk-oracle-v2"
{c-root} install -m 755 /tmp/mk-oracle-v2_sync "$pluginsdir/mk-oracle-v2_sync"
{c-root} install -D -m 755 /tmp/mk-oracle-v2_async "$pluginsdir/600/mk-oracle-v2_async"
----


In the example above, the `mk-oracle-v2_async` file was installed in the `600` subdirectory.
This means that `mk-oracle-v2_async` runs every 600 seconds.
Be sure to set the `cache_age` option in the configuration file to exactly the same value.
Specifically: If you install `mk-oracle-v2_async` in the `$pluginsdir/600` directory, the configuration file must contain the following:

.mk-oracle.yml
[{yaml}]
----
---
oracle:
  main:
    cache_age: 600
----

If you want a different interval, adjust both numbers to the same value.

The actual installation of the agent plug-in works a little differently than you might be used to with other plug-ins.

First, copy the three files from the {CMK} server to the host using any method you prefer, and place them in the destination paths listed in the table below.
Be sure to rename the files as specified:

[cols="3,5,3",options="header"]
|===
|File name on the {CMK} server |Directory | Target name
|`mk-oracle.exe` |`%ProgramData%\checkmk\agent\plugins\libexec\mk-oracle-v2\`|`mk-oracle-v2.exe`
|`oracle_unified_sync.ps1` |`%ProgramData%\checkmk\agent\plugins\`|`mk-oracle-v2_sync.ps1`
|`oracle_unified_async.ps1` |`%ProgramData%\checkmk\agent\plugins\`|`mk-oracle-v2_async.ps1`
|===

[.admonition-important]
****
This renaming is absolutely necessary and will be assumed throughout the rest of this article.
In future versions, the files we provide with {CMK} will be named `mk-oracle-v2.exe`, `mk-oracle-v2_sync.ps1`, and `mk-oracle-v2_async.ps1`.
****

Once the files are in place, you will need to provide the appropriate configuration to the file responsible for executing the asynchronous sections—that is, `mk-oracle-v2_async.ps1`.

It might look something like this:

.%PROGRAMDATA%\checkmk\agent\check_mk.user.yml
[{yaml}]
----
plugins:
    enabled: yes
    execution:
        - pattern: $CUSTOM_PLUGINS_PATH$\mk-oracle-v2_async.ps1
          async: yes
          cache_age: 600
----

When you xref:#create_config[create the configuration for the agent plug-in], you must ensure that `cache_age` has the same value there.

[#setup_custom_sqls]
== Setting Up custom SQL queries

Custom SQL queries cannot be defined using the [.guihint]#Oracle databases (Experimental)# rule.
You must perform the necessary configuration directly on the host from which you monitor your Oracle instances and databases.


[#custom_sqls_why]
=== Why custom SQL queries?

{CMK} already provides a large number of SQL queries through the agent plug-in, which you can use to monitor your database instances.
To ensure that these queries are suitable for as wide a range of technical and content-related requirements as possible, they are kept general.

To meet the individual requirements of each organization for monitoring a specific database, {CMK} offers the option to create your own custom SQL queries and have them executed by the agent plug-in.
These are then automatically recognized and monitored as services in {CMK}.

You have two options for providing your queries to the agent plug-in:

* Either write the queries directly into the configuration file `mk-oracle.yml`.
* Or, instead, specify in the configuration file where the agent plug-in can find the files containing your custom SQL queries.

The latter approach simplifies maintenance and also makes version control easier, since content is not mixed into the plug-in's configuration file.
However, if you are only dealing with a small number of queries anyway, you may want to skip the extra effort.

We will start by showing a simple example that is written directly into the plug-in's configuration file.


[#custom_sqls_simple]
=== Setting up simple user-defined SQL queries

We will start by showing a query that already returns real data from an Oracle instance.
This example is intended only to illustrate how easy it *can* be to incorporate user-defined SQL queries.
Exactly how useful this query is in day-to-day work remains to be seen.

Get a feel for a query that can later be used in production by first executing your ideas for SQL queries as `sysdba`.
To prevent potentially long-running queries from slowing down a production system, we recommend using a test instance.

[{shell}]
----
oracle@linux$ sqlplus / as sysdba
----

[{sql}]
----
sqlplus> SELECT 'details:Free memory: ' || ROUND(SUM(bytes)/1024/1024, 2) || ' MB' FROM v$sgastat WHERE name = 'free memory';
'DETAILS:FREEMEMORY:'||ROUND(SUM(BYTES)/1024/1024,2)||'MB'
----------------------------------------------------------------
details:Free memory: 230,86 MB
----

You can ignore this header's output—just as the agent plug-in does.
The important part is the keyword `details` used in the query.
The check plug-in on the {CMK} server will extract the line that begins this way and use it to generate the [.guihint]#Summary# for the service.
But how does {CMK} know what the service is actually supposed to be called?
You specify the name of the service when you transfer the SQL query to the configuration for the agent plug-in:

.mk-oracle.yml
[{yaml},highlight=10..12]
----
---
oracle:
  main:
    connection:
      hostname: localhost
    authentication:
      username: mymonitoringuser
      password: mypassword
      type: standard
    custom_metrics:
      - My service: 
          sql: "SELECT 'details:Free memory: ' || ROUND(SUM(bytes)/1024/1024, 2) || ' MB' FROM v$sgastat WHERE name = 'free memory'"
----

Our example illustrates three things:

* To include custom SQL queries, you always need a key named `custom_metrics`.
* This is followed by a list (here: `My service`).
In YAML, such a list begins with a `-`.
The name of this list becomes part of the service name in {CMK} and can be chosen freely.
* Next comes the line containing the query.
It must begin with `sql:`, and the query itself must be enclosed in double quotes.

After you have inserted this line into the agent plug-in's configuration file on your Oracle host, you can return to your {CMK} server.
There, perform a service discovery for the Oracle host.
You will then see this new service:

image::monitoring_oracle_custom_sql_discovery.png[]

The service name consists of several components:

* The name always begins with [.guihint]#ORA#.
* This is followed by the SID (here: [.guihint]#FREE#).
* The subsequent [.guihint]#SQL# indicates that this service was generated by a user-defined SQL query.
* This is followed by the string you were able to choose freely in the configuration file, in uppercase letters.

In the summary, you will already see data derived from the results of the SQL query.

There will certainly be cases where such a simple query is exactly what you need.
In that case, however, the service is probably still of little use.
That is why, in the chapter xref:custom_sqls_advanced[Advanced custom SQL queries], we will show you how to create a more comprehensive service in just a few simple steps.


[#custom_sqls_advanced]
=== Setting up advanced custom SQL queries

Building on the example shown in the chapter xref:custom_sqls_simple[Simple custom SQL queries], we will now show you how to retrieve a service with a metric in just a few steps.

To do this, it is a good idea to move the SQL query out of the agent plug-in's configuration file.
Instead, after the `custom_metrics` key, specify a file where the agent plug-in can find your SQL queries.

.mk-oracle.yml
[{yaml},highlight=10..12]
----
---
oracle:
  main:
    connection:
      hostname: localhost
    authentication:
      username: mymonitoringuser
      password: mypassword
      type: standard
    custom_metrics:
      - My advanced service:
          path: 'myadvancedservice.sql'
----

If you enter the file without specifying an absolute path, the agent plug-in will search through several directories in a specific order.
We explain which directories these are and exactly what happens during this process in the xref:reference[reference section] of this article.

Now, in the {CMK} agent's xref:glossar#dir_conf[configuration directory], create a subdirectory named `orasql` and create a file within it with the `.sql` extension, as specified after `path:`.

In this example, we assume that the configuration directory on a Linux host is named `/etc/check_mk/`.
First, create the absolutely necessary `orasql` subdirectory.

[{shell}]
----
{c-root} mkdir /etc/check_mk/orasql
----

Next, create the file `myadvancedservice.sql` in that directory.
You can now much more easily include multi-line SQL queries in that file.
It is important to ensure that the keywords for the check plug-in are included.

./etc/check_mk/orasql/myadvancedservice.sql
[{sql}]
----
SELECT 'details:Free memory: ' || REPLACE(ROUND(SUM(bytes) / 1024 / 1024, 2), ',', '.') || ' MB' FROM v$sgastat WHERE name = 'free memory'
UNION ALL
SELECT 'perfdata:free_ram_mb=' || REPLACE(ROUND(SUM(bytes) / 1024 / 1024, 2), ',', '.') FROM v$sgastat WHERE name = 'free memory'
UNION ALL
SELECT 'exit:0' FROM dual
----

In addition to the first line, which you already know from the simple example, the SQL script now outputs a line that begins with `perfdata`.
{CMK} will use this to generate a metric and automatically create a graph.
You can also use the `exit` keyword to control the service's state.
In this example, it is set to `0`, which stands for the {OK} state.
The check plug-in on the {CMK} server requires these keywords to generate services and metrics from the provided data.
We explain the four keywords `details`, `perfdata`, `long`, and `exit` in detail in the chapter xref:format_and_prefixes[Output formatting and keywords].

Once you have set all of this up and run a service discovery again, the old service will disappear and a new one—whose name ends with [.guihint]#MY ADVANCED SERVICE#—will be found instead.

== Migration from `mk_oracle` to `mk-oracle-v2`


[#migrate_configuration]
=== Migrating the agent plug-in's configuration

In {CMK} {v25}, the new agent plug-in `mk-oracle-v2` includes a feature that helps users of the existing `mk_oracle` migrate to the new agent plug-in.
To do this, deploy `mk-oracle-v2` to your Oracle host and run the agent plug-in with the `-M` option, followed by the name of a configuration file in the old format.
The agent plug-in will then read the configuration for the old `mk_oracle` and output it in the format expected by `mk-oracle-v2`.

This might look something like this, for example:

[{shell}]
----
{c-root}  /usr/lib/check_mk_agent/plugins/libexec/mk-oracle-v2/mk-oracle-v2 -M /etc/check_mk/mk_oracle.cfg
# --- Converted from /etc/check_mk/mk_oracle.cfg at 2026-06-29 19:00:00 UTC ---
# # Syntax
# # DBUSER='USERNAME:PASSWORD:ROLE:HOST:PORT:TNSALIAS'
# DBUSER='checkmk:myPassword'
# 
# DBUSER_MYINST1='cmk_specific1:myPassword1:SYSDBA:localhost:1521'
# DBUSER_MYINST2='cmk_specific2:myPassword2::localhost::INST2'
# 
# ASMUSER='cmk_asm:myASMPassword:SYSASM'
# --- Known environment variables defined in legacy config ---
# DBUSER_MYINST2 cmk_specific2:myPassword2::localhost::INST2
# ASMUSER cmk_asm:myASMPassword:SYSASM
# DBUSER checkmk:myPassword
# DBUSER_MYINST1 cmk_specific1:myPassword1:SYSDBA:localhost:1521
# --- Unified Config ---
---
oracle:
  main:
    connection:
      hostname: localhost
    authentication:
      username: "checkmk"
      password: "myPassword"
      type: standard
      asm_username: "cmk_asm"
      asm_password: "myASMPassword"
      asm_role: sysasm
    instances:
      - sid: $ORACLE_SID
        alias: $ORACLE_SID
      - sid: MYINST2
        alias: INST2
        connection:
          hostname: localhost
        authentication:
          username: "cmk_specific2"
          password: "myPassword2"
          type: standard
      - sid: MYINST1
        connection:
          hostname: localhost
          port: 1521
        authentication:
          username: "cmk_specific1"
          password: "myPassword1"
          type: standard
          role: sysdba
----

By default, `mk-oracle-v2` writes the migrated configuration to standard output.
We strongly recommend doing this as your first step so you can review the output first.
The output begins with your old configuration as a comment.
For reference purposes, it is a good idea to keep this comment for a while.

If everything looks good, you can use the `--migrate-output` option with `mk-oracle-v2` to have it write the output directly to a file.

[{shell}]
----
{c-root} /usr/lib/check_mk_agent/plugins/libexec/mk-oracle-v2/mk-oracle-v2 \
    -M /etc/check_mk/mk_oracle.cfg \
    --migrate-output /etc/check_mk/mk-oracle.yml
----

If the migration command is unable to migrate parts of your old configuration, this will be clearly indicated in the output as `#WARNING`.

The following table shows which configuration variables are translated by `mk_oracle` and how:

[cols="3,7",options="header"]
|===
|Old variable... | ...is migrated to:
| `DBUSER` (required) | Top-level `connection:` (host name, port) and `authentication:`, plus the first entry under `instances:`
| `DBUSER_<SID>` | One `instances:` entry for each `SID`, with `connection:` and `authentication:` entries per instance
| `ASMUSER` | `asm_username`, `asm_password`, `asm_role` under `authentication:`
| `REMOTE_INSTANCE_<ID>` | One `instances:` entry per ID, including `piggyback_host:` (Linux/AIX only)
| `SYNC_SECTIONS` / `ASYNC_SECTIONS` | `sections:` with the attribute `is_async: false` / `true`
| `SYNC_ASM_SECTIONS` / `ASYNC_ASM_SECTIONS` | `sections:` with the `affinity: "asm"` (`"all"`) attribute
| `CACHE_MAXAGE` | `cache_age:`
| `SQLS_MAX_CACHE_AGE` | `custom_metrics_cache_age:`
| `MAX_TASKS` | `options.threads:` (Only for values ≥ 2, up to a maximum of 8)
| `ONLY_SIDS` | `discovery.include:` (with `detect: true`)
| `SKIP_SIDS`, `EXCLUDE_<SID>="ALL"` | `discovery.exclude:` (with `detect: true`)
| `TNS_ADMIN` | `connection.tns_admin:`
| `OLRLOC` | `connection.oracle_local_registry:`
| `SQLS_SECTIONS` + `SQLS_*` per section | `custom_metrics:`
|===

The entries in the following table are not migrated automatically and must be manually updated to work with the new plug-in:

[cols="3,7",options="header"]
|===
| Old variable | Note on manual migration
| `SQLS_DBUSER`, `SQLS_DBPASSWORD`, `SQLS_DBSYSCONNECT` | Login credentials per user-defined SQL; use instance-specific overrides under the `authentication:` key instead
| `SQLS_PARAMETERS` | Passing SQL*Plus parameters is not supported.
| `EXCLUDE_<SID>="<section> ..."` | Exclusion of individual sections per SID; only `EXCLUDE_<SID>="ALL"` is converted
| `ORACLE_HOME`, `REMOTE_ORACLE_HOME` | The OIC runtime environment—specify `use_host_client` if necessary.
| `ID_BY` | Selects `SID=` over `SERVICE_NAME=` in the old connection configuration; use the instance fields `sid:` / `service_name:` instead
|===


[#migrate_sql_queries]
=== Migration of user-defined SQL queries

The old agent plug-in `mk_oracle` forwards user-defined SQL queries via the command-line tool `sqlplus`.
The new `mk-oracle-v2` plug-in, on the other hand, executes SQL queries directly using the Oracle Instant Client driver.
This change in the execution model has two major implications for existing SQL queries.


==== Basic restrictions and execution model


===== Non-SQL*Plus commands

* Commands such as `PROMPT`, `SET`, `COLUMN`, `SPOOL`, `EXEC`/`EXECUTE`, or `VAR`/`VARIABLE` are functions of the `sqlplus` client tool and are not part of the SQL database language.
They do not work under the OIC driver.
* No anonymous PL/SQL blocks: Anonymous blocks in the format `DECLARE/BEGIN {...} END;` cannot be executed directly as a script.
Only pure SQL statements are supported.

The agent plug-in in migration mode checks every referenced SQL file and, if discrepancies are found, issues a warning in the terminal as well as in the generated configuration file.
Although the affected sections are migrated, you must manually edit them; otherwise, the queries will fail at runtime.


===== Features of the new execution model

* Multiple statements: An SQL file can contain multiple top-level SQL statements separated by semicolons.
These are executed in sequence, and their results are concatenated.
* Each returned result must comply with the specifications for xref:format_and_prefixes[Output formatting and keywords].


==== Removing SQL*Plus commands

Formatting commands and interactive commands from `sqlplus` have no equivalent in the Oracle Instant Client driver.
You must therefore delete them without replacement.
The agent plug-in outputs each returned data row directly.

Next, we will first show an SQL file that still worked for `mk_oracle`:

[{sql}]
----
SET PAGESIZE 0
SET FEEDBACK OFF
COLUMN details FORMAT A80
PROMPT collecting session count ...
SELECT 'details:' || COUNT(*) || ' sessions' FROM v$session;
----

You must modify such a file for `mk-oracle-v2` as follows so that it works with OIC:

[{sql}]
----
SELECT 'details:' || COUNT(*) || ' sessions' FROM v$session
----


==== Converting PL/SQL blocks into pure SELECT queries

In most cases, anonymous PL/SQL blocks can be replaced with standard SQL constructions:
* PL/SQL variables become `WITH` clauses (Common Table Expressions).
* `IF/ELSIF` conditions are replaced by `CASE` statements.
* `DBMS_OUTPUT.PUT_LINE` outputs are represented using `UNION ALL`, or separate statements separated by semicolons.

The following example shows an SQL file that contains a PL/SQL block:

[{sql}]
----
SET SERVEROUTPUT ON
DECLARE
    invalid_count NUMBER;
BEGIN
    SELECT COUNT(*) INTO invalid_count
      FROM dba_objects
     WHERE status = 'INVALID';
    IF invalid_count > 10 THEN
        DBMS_OUTPUT.PUT_LINE('exit:2');
    ELSE
        DBMS_OUTPUT.PUT_LINE('exit:0');
    END IF;
    DBMS_OUTPUT.PUT_LINE('details:' || invalid_count || ' invalid objects');
END;
----

You must rewrite such a file into pure SQL for the new `mk-oracle-v2`.
For example, it might look like this:

[{sql}]
----
WITH invalid AS (
    SELECT COUNT(*) AS cnt
      FROM dba_objects
     WHERE status = 'INVALID'
)
SELECT 'exit:' || CASE WHEN cnt > 10 THEN '2' ELSE '0' END FROM invalid
UNION ALL
SELECT 'details:' || cnt || ' invalid objects' FROM invalid
----


==== Moving complex PL/SQL logic to stored functions

If the logic absolutely requires PL/SQL (e.g., for loops, complex error handling, or temporary states), it must itself be moved into the database as a pipelined function.

To do this, you must set up the pipelined function once in your database:

[{sql}]
----
CREATE OR REPLACE FUNCTION checkmk_invalid_objects
    RETURN sys.odcivarchar2list PIPELINED
AS
    invalid_count NUMBER;
BEGIN
    SELECT COUNT(*) INTO invalid_count
      FROM dba_objects
     WHERE status = 'INVALID';

    -- Beliebige PL/SQL-Logik ist hier erlaubt
    PIPE ROW ('details:' || invalid_count || ' invalid objects');
    PIPE ROW ('perfdata:invalid_objects=' || invalid_count || ';10;100');
    PIPE ROW (CASE WHEN invalid_count > 10 THEN 'exit:2' ELSE 'exit:0' END);
    RETURN;
END;
/

GRANT EXECUTE ON checkmk_invalid_objects TO checkmk;
----

Once you have set up this pipelined function, you can have the agent plug-in call it:

[{sql}]
----
SELECT column_value FROM TABLE(checkmk_invalid_objects)
----

If the function is in a different schema, the schema name must be prefixed: `TABLE(owner.checkmk_invalid_objects)`.

[#diagnostic]
== Diagnostic options

The `mk-oracle-v2` or `mk-oracle-v2.exe` agent plug-in provides you with various options for error diagnosis.
On Linux, Solaris, AIX and Windows, you call the respective binary with the same options.
The following sections explain how to run the agent plug-in manually, how to check which Oracle Instant Client and which Oracle instances it finds, and how to use logging.

[#manual_call]
=== Running the agent plug-in manually

During normal operation, the {CMK} agent does not call the binary itself, but the two helper programs for the synchronous and the asynchronous mode.
For diagnosis, you call the binary directly.
The agent plug-in then requires the same environment variables that the {CMK} agent otherwise provides:
`MK_CONFDIR` for the configuration directory, `MK_LIBDIR` for the directory that contains, among other things, the Oracle Instant Client provided with the agent plug-in, and `MK_LOGDIR` for the log file.

[.tabs]
====
[#tab_diagnostic_linux]#Linux, Solaris, AIX#::
+
--
Run the following commands as `root`.
In the example, we use the default paths of the {CMK} agent on Linux:

[{shell}]
----
{c-root} export MK_CONFDIR=/etc/check_mk MK_LIBDIR=/usr/lib/check_mk_agent MK_LOGDIR=/var/log/check_mk_agent
{c-root} $MK_LIBDIR/plugins/libexec/mk-oracle-v2/mk-oracle-v2 -c $MK_CONFDIR/mk-oracle.yml --no-spool
----
--

[#tab_diagnostic_windows]#Windows#::
+
--
Run the following commands in a PowerShell with administrator privileges:

[{powershell}]
----
PS C:\> $env:MK_CONFDIR="C:\ProgramData\checkmk\agent\config"; $env:MK_LIBDIR="C:\ProgramData\checkmk\agent"; $env:MK_LOGDIR="C:\ProgramData\checkmk\agent\log"
PS C:\> & "$env:MK_LIBDIR\plugins\libexec\mk-oracle-v2\mk-oracle-v2.exe" -c "$env:MK_CONFDIR\mk-oracle.yml" --no-spool
----
--
====

With the `--no-spool` option, the agent plug-in outputs all sections--both the synchronous and the asynchronous ones--without marking any data as cached.
You therefore receive the complete, current output.

If the agent plug-in cannot connect to an Oracle instance, you will find a line of the form `<SID>|FAILURE|<error message>` in the `+<<<oracle_instance:sep(124)>>>+` section.
If, on the other hand, only a single query fails, such a line replaces the result in the section concerned.
In both cases, the error message contains the Oracle error code (`ORA-xxxxx`), which helps you to quickly identify simple configuration problems, such as incorrect credentials or an unknown instance.


[#find_runtime]
=== Checking the Oracle Instant Client and instances

If the agent plug-in does not deliver any data at all, this is often because it cannot find a usable Oracle Instant Client.
With the `--find-runtime` option, the agent plug-in shows you which client library and which `ORACLE_HOME` it would use, without connecting to an Oracle instance:

[{shell}]
----
{c-root} $MK_LIBDIR/plugins/libexec/mk-oracle-v2/mk-oracle-v2 -c $MK_CONFDIR/mk-oracle.yml --find-runtime
----

The output consists of lines of the form `VARIABLE=value`: `LD_LIBRARY_PATH` (`PATH` on Windows) with the directory of the client library, `ORACLE_HOME` if applicable, and `RUN_AS` if applicable.

The `RUN_AS` line appears if the agent plug-in runs as `root` on Linux, Solaris or AIX and the client library belongs to another user--for example, `oracle` in a regular Oracle installation.
The agent plug-in then switches to this user before the first connection.
This user must therefore be able to read all files that the Oracle client accesses afterwards: `sqlnet.ora`, `tnsnames.ora`, the xref:oracle_wallet[Oracle Wallet] and your files with xref:custom_sqls[custom SQL queries].

Before loading the client library, the agent plug-in also checks its access rights.
If an unauthorized user can modify the library or one of its parent directories, the agent plug-in refuses to use it and states the reason in its output and in the log file.
In this case, correct the access rights.
With the `permissions_safe_entries` and `permissions_check` options in the configuration file, you can adjust this check or, as a last resort, disable it.

The `--detect-sids` option shows you which Oracle instances the agent plug-in finds on the local host:

[{shell}]
----
{c-root} $MK_LIBDIR/plugins/libexec/mk-oracle-v2/mk-oracle-v2 -c $MK_CONFDIR/mk-oracle.yml --detect-sids
----

The agent plug-in then lists the instances from the `oratab` file (from the registry on Windows) with SID, state, `ORACLE_HOME` and `ORACLE_BASE`.
On Linux, Solaris and AIX, the state also shows whether a PMON process is running for the instance.
On Windows, the state is not determined.


[#logging]
=== Logging

Each time it runs, the agent plug-in writes to the `mk-oracle.log` log file in the agent's log directory (`MK_LOGDIR`), which by default is `/var/log/check_mk_agent` on Linux and `C:\ProgramData\checkmk\agent\log` on Windows.
The log file is rotated as soon as it reaches 500,000 bytes. By default, 5 log files are kept.

By default, the agent plug-in logs at the `info` level.
You can set the level, the file size and the number of log files in the `system` section of the configuration file:

.mk-oracle.yml
[{yaml}]
----
system:
  logging:
    level: 'debug'
    max_size: 1000000
    max_count: 5
----

If you distribute the configuration via the agent bakery, `mk-oracle.yml` will be overwritten during the next agent update.
In this case, add the `system` section to the `mk-oracle.user.yml` file in the agent plug-in's directory (on Linux `/usr/lib/check_mk_agent/plugins/libexec/mk-oracle-v2/`).
The agent plug-in merges both files at startup, with your settings in `mk-oracle.user.yml` taking precedence.


[#debugging]
=== Debugging

For a single manual run, you can also set the logging level when xref:manual_call[calling] the agent plug-in and have the log messages output directly in the terminal:

[{shell}]
----
{c-root} $MK_LIBDIR/plugins/libexec/mk-oracle-v2/mk-oracle-v2 -c $MK_CONFDIR/mk-oracle.yml --no-spool -l -v
----

The `-l` option outputs the log messages to standard error instead of to the log file.
With `-v` you set the level to `debug`, with `-vv` to `trace`.
At the `debug` level, for example, the log names every SQL file used and every SQL query executed, and measures the duration of connections, sections and queries.
The `trace` level provides the most comprehensive output and should therefore only be used as a last resort.

[#custom_sqls]
=== Custom SQL queries

Using the `custom_metrics` configuration key, you can define ad hoc SQL queries whose output is evaluated on the {CMK} server by the check plug-in link: https://checkmk.com/integrations/oracle_sql[oracle_sql^].
Each entry is identified by an item name, which is displayed in {CMK} as part of the service name.


==== Basics and configuration

You can either pass the SQL queries directly as a string or load them from a file.
In the following example configuration, you will find an SQL query in the global section that is identified by the key `oracle.main`.
Under the key `oracle.main.instances`, you can specify a key `custom_metrics`, which is then, of course, executed only for those instances.

.mk-oracle.yml
[{yaml}]
----
---
oracle:
  main:
    connection:
      hostname: localhost
    authentication:
      username: mymonitoringuser
      password: mypassword
      type: standard
    custom_metrics:
      - product_price: # item name -> will generate service "<SID> SQL PRODUCT_PRICE"
          sql: "SELECT 'details:Price OK' FROM dual"
    instances:
      - service_name: FREE
        custom_metrics:
          - last_sessions: # will only be run for this specific instance
              sql: "SELECT 'details:per-instance' FROM dual"
----

* An instance always executes both globally defined SQL queries and its own instance-specific SQL queries.
* If a global entry and an instance-specific entry share the same item name, the instance-specific entry always takes precedence.


==== External SQL files (path:)

Instead of writing SQL queries directly into the agent plug-in's configuration file using `sql:`, you can use `path:` to reference external `.sql` files.
This works for both `custom_metrics` and predefined sections.


===== Variations in path specification

.mk-oracle.yml
[{yaml}]
----
custom_metrics:
  # 1. Absolute path for a file
  - heavy_query:
      path: '/opt/checkmk/sql/heavy_query.sql'

  # 2. Relative path
  # First searched in MK_LIBDIR/... and then in MK_CONFDIR/...
  - product_price:
      path: 'queries/product_price.sql'

  # 3. Path to a directory
  # The file name is automatically derived from the item name (here: "sessions_stats.sql")
  - sessions_stats:
      path: 'queries/'

  # 4. File with inline fallback
  # If the file cannot be read, the inline fallback is used
  - last_resort:
      path: 'queries/last_resort.sql'
      sql: "SELECT 'details:fallback' FROM dual"
----


==== Resolution rules

Absolute vs. relative::
Absolute paths are used exactly as they are specified.
Relative paths are first searched for under `MK_LIBDIR/plugins/libexec/mk-oracle-v2/orasql/` and then under `MK_CONFDIR/orasql/`.
If the file exists in both directories, the file in `MK_LIBDIR` takes precedence.

File vs. directory::
A path can refer to a specific file (with or without a `.sql` extension) or to a directory.
If it refers to a directory, the filename is derived from the item name for `custom_metrics` and from the section name for predefined sections.

Version-dependent variants::
In addition to the base file (`<name>.sql`), you can provide Oracle-specific variants in the format `<name>@<min_version>.sql` (e.g., `sessions@12010000.sql`).
The plug-in automatically selects the file with the highest `min_version` that is less than or equal to the version of the connected Oracle instance.
An 8-digit numeric format is used for versioning (`MMmmRRSSSS` for Major / Minor / Release / Patch).
Example: 12.1.0.2 → 12010002.

Fallback chain::
The order for determining the SQL query is: `path:` > (inline) `sql:` > included default code (only for predefined sections).
If `path:` fails and no `sql:` is defined, the section will generate no output.


==== SQL parameters

You can define named parameters that are inserted into the SQL code before execution.
Each placeholder in the format `${<name>}` is replaced, on a text-by-text basis, with the configured value.
This works for both inline SQL and `.sql` files.

.mk-oracle.yml
[{yaml}]
----
---
custom_metrics:
  - test:
      sql: 'SELECT ${parameter_1} FROM dual; SELECT ${parameter_2} FROM dual'
      sql_params:
        parameter_1: 'value_1'
        parameter_2: '${ENV_VAR_1}'
----

* `${ENV_VAR_1}` is resolved from the environment variables.
* *Textual substitution (no bind variables)*: All values are inserted into the statement unchanged.
This means you can also pass column or table names.
* *Environment variables*: A value can reference environment variables (format `$VAR` or `${VAR}`). These are resolved when the configuration is read.
If a referenced variable is not specified, the parameter is skipped with a warning.
The placeholder remains in the SQL code (which usually results in an SQL error rather than executing a query with empty values).
* *Unused parameters*: Placeholders without a matching parameter value are ignored and remain unchanged in the code.


[#format_and_prefixes]
==== Output formatting and keywords

The `mk-oracle-v2` agent plug-in automatically inserts the section header `pass:[<<<]<<oracle_sql:sep(58)pass:[>>>]` , as well as the subsection header `[[[<SID>|<item>]]]`.
The SQL to be executed is responsible solely for the body of the output.
Each SQL query must return rows with a single string column.
The value must begin with one of the following prefixes so that the {CMK} plug-in can interpret it correctly:

* `details`:
Here you can specify what should be displayed in the [.guihint]#Summary# of the generated service.
The line begins with the keyword followed by a colon.
The rest of the line constitutes the output.

* `perfdata`:
Metrics are passed using this keyword.
Within a single line, you can specify any number of metrics—separated by a space.
You can also spread the metric output across multiple lines.
Simply start each line with the keyword `perfdata:`.

* `long`:
If you want the service to have a long output for the [.guihint]#Details# field, you can specify it here.
You can also use this keyword multiple times to generate several lines in the [.guihint]#Details#.

* `exit`:
If the output should result in a specific state, you can specify it here.
You can use the standard mappings `0`, `1`, `2`, `3` for the states {OK}, {WARN}, {CRIT}, {UNKNOWN}.
