[#intro]
== Einleitung

Ein wichtiger Punkt, den Sie beim Aufbau einer verteilten Monitoring-Umgebung berücksichtigen müssen, ist der Versand von Benachrichtigungen.
Der Standardweg bei {CMK} ist, dass über Benachrichtigungen im Monitoring-Kern entschieden wird.
Der wird lokal in jeder Instanz ausgeführt, was demnach dezentrale Benachrichtigungen zum Default macht.

{cee-only}
Die kommerziellen Editionen von {CMK} bringen neben dezentralen Benachrichtigungen noch die Möglichkeit mit, alle Benachrichtigungen xref:centralized_notifications[an die Zentralinstanz weiterzuleiten].
Dort wird dann der Versand durchgeführt.

Beide Wege haben ihre Vor- und Nachteile.
Für den dezentralen Versand spricht:

* Dezentrale Benachrichtigungen sind einfach einzurichten.
* Eine lokale Zustellung funktioniert auch, wenn gerade keine Verbindung zur Zentralinstanz möglich ist.

Argumente für den Versand von der Zentralinstanz aus sind:

* Benachrichtigungen können an einer zentralen Stelle verarbeitet werden (z.B. für eine Weiterleitung in Ticketsysteme).
* Remote-Instanzen benötigen kein Setup für E-Mail auf Systemebene.
// MFS: Das ist doch ein Denkfehler, oder? Hardware-Modems nutzt man ja gerade, um Benachrichtigungen verschicken zu können, wenn der Uplink weg ist.
* Bei Versand von SMS über ein Hardware-Modem ist dieses nur einmal notwendig: an der Zentralinstanz.


[#decentralized_notifications]
== Dezentrale Benachrichtigungen

Für die Einrichtung dezentraler Benachrichtigungen sind keine besonderen Schritte notwendig, denn dies ist die Standardeinstellung.
Jede Benachrichtigung, die auf einer Remote-Instanz entsteht, durchläuft dort die xref:notifications#rule_analysis[Kette der Benachrichtigungsregeln].
// MFS: TBD, auf distributed_monitoring_basics verlinken, wenn der Artikel fertig ist
Falls Sie ein xref:distributed_monitoring_setup#[zentrales Setup] einsetzen, sind diese Regeln auf allen Instanzen gleich.
Aus den Regeln resultierende Benachrichtigungen werden wie üblich zugestellt, indem lokal die entsprechenden Benachrichtigungsskripte aufgerufen werden.

Sie müssen allerdings sicherstellen, dass die entsprechenden Dienste auf allen Instanzen korrekt arbeiten.
Das bedeutet:
Auf jedem Server muss das E-Mail-System korrekt konfiguriert sein und gegebenenfalls muss der Mailserver den Adressen Ihrer Remote-Instanzen vertrauen.
Bei der Verwendung der kommerziellen Editionen kann die xref:notifications#syncsmtp[nachvollziehbare Zustellung per SMTP] den Aufwand zumindest bezüglich der lokalen E-Mail-Systeme reduzieren.
Wenn Sie andere Benachrichtigungen -- beispielsweise über Ticketsysteme -- verwenden, sind möglicherweise Firewall-Einstellungen dahingehend anzupassen, dass die Remote-Instanzen die zum Versand verwendeten Server erreichen können.


[#centralized_notifications]
== Zentrale Benachrichtigungen

{cee-only}
Die kommerziellen Editionen bieten einen eingebauten Mechanismus für zentralisierte Benachrichtigungen.
Damit dieser zuverlässig funktioniert, muss das xref:distributed_monitoring_setup#[zentrales Setup] aktiv sein.

// ES: "Verteilung des Setups" muss allerdings umformuliert werden (siehe Kommentar in KNW-2366).
// MFS: Ich habe keinen Deeplink gesetzt, da es gefährlich sein kann, einfach mal so zentrale Konfiguration nachträglich zu aktivieren.
Die Weiterleitung von Benachrichtigungen kann dann für jede Remote-Instanz individuell konfiguriert werden.
Hieraus resultiert eine hohe Flexibilität, welche der Komplexität großer Monitoring-Umgebungen gerecht wird.

Ist eine Remote-Instanz auf Weiterleitung eingestellt, so werden alle Benachrichtigungen direkt, wie sie vom Kern kommen, in _Rohform_ oder als _Rohbenachrichtigungen_ an die Zentralinstanz weitergereicht.
Erst dort werden die Benachrichtigungsregeln ausgewertet, welche entscheiden, wer und wie überhaupt benachrichtigt werden soll.
Die dazu notwendigen Benachrichtigungsskripte werden auf der Zentralinstanz aufgerufen.

Da an diesem Punkt das _zentrale Setup_ bereits eingerichtet ist, müssen alle nachfolgend beschriebenen Einstellungen auf der Zentralinstanz vorgenommen werden.
Nehmen Sie Einstellungen, welche die Mehrzahl Ihrer Instanzen betreffen, in den [.guihint]#Global settings# im Abschnitt [.guihint]#Notifications# vor.

Für die beteiligten Instanzen, die davon abweichen, bearbeiten Sie die jeweiligen xref:distributed_monitoring_setup#sitespecific[instanzspezifischen globalen Einstellungen].


.[#collapsible_spooler_on_central]#Muss der zentrale Benachrichtigungs-Spooler auf der Zentralinstanz des Monitorings laufen?#
[%collapsible]
====
Nein.

Theoretisch kann der Benachrichtigungs-Spooler auf jeder Instanz in Ihrem verteilten Monitoring laufen.
Es ist auch möglich (und in Einzelfällen sinnvoll), eine eigene Instanz nur für den Versand von Nachrichten zu betreiben.
Zudem ist es ist nicht zwingend erforderlich, dass genau eine Instanz den Versand für alle anderen vornimmt.
In der Praxis ist es häufig so, dass verschiedene Remote-Instanzen einander nicht erreichen können, weswegen der Betrieb auf einer Remote-Instanz eher die Ausnahme ist.

Wenn im weiteren Verlauf dieses Kapitels von einer Zentralinstanz die Rede ist, ist immer die Instanz gemeint, von der die Benachrichtigungen schließlich verschickt werden.

[#centralized_notifications_roles]
=== Rollen zuweisen

Zuerst muss jede am zentralisierten Benachrichtigungssystem beteiligte Instanz eine _Rolle_ erhalten.
Die Rolle bestimmt, _welchen Weg_ die Benachrichtigungen nehmen.

[#centralized_notifications_role_remote]
==== Einstellungen für Remote-Instanzen

Alle Instanzen -- bis auf die eine, welche das zentrale Benachrichtigungssystem beherbergt -- verschicken ihre Benachrichtigungen zur Zentralinstanz.
Für diese Instanzen muss daher die Einstellung für [.guihint]#Notification spooling# auf [.guihint]#Forward to remote site by notification spooler# gesetzt sein.
Sie können diese Einstellung theoretisch für jede Remote-Instanz einzeln in deren instanzspezifischen globalen Einstellungen setzen.
Viel effektiver ist es aber, die globalen Einstellungen Ihrer Zentralinstanz zu verwenden.
Diese Einstellung wird dann später an alle Remote-Instanzen übertragen.
Abweichende Einstellungen der Zentralinstanz werden dann in ihren instanzspezifischen globalen Einstellungen gesetzt.

[#centralized_notifications_connection]
=== Verbindungsaufbau

Nachdem die Rollen zugewiesen wurden, müssen Sie sich Gedanken machen, in welcher Richtung die Verbindung aufgebaut wird.
Die Richtung des Verbindungsaufbaus für Livestatus und die Verteilung der Konfiguration ist immer von der Zentralinstanz zu den Remote-Instanzen.
In vielen Fällen ist der Aufwand für die Anpassung der Firewall-Konfiguration kleiner, wenn auch zentrale Benachrichtigungen diese Art des Verbindungsaufbaus nutzen.
Deshalb zeigen wir diese Richtung zuerst.

Allerdings erfordert die umgekehrte Richtung etwas weniger Aufwand beim Hinzufügen weiterer Remote-Instanzen und bietet bei unzuverlässigen Netzen eine etwas schnellere Behandlung von Problemen.

Setzen Sie dafür das Häkchen für [.guihint]#Accept incoming TCP connections#.

// === Einrichten der TCP-Verbindungen

Die Benachrichtigung-Spooler von entfernter und zentraler (Benachrichtigungs-)Instanz tauschen sich untereinander per TCP aus.
Benachrichtigungen werden von der Remote-Instanz zur Zentralinstanz gesendet.
Die Zentrale quittiert empfangene Benachrichtigungen an die Remote-Instanz, was verhindert, dass Benachrichtigungen verloren gehen, selbst wenn die TCP-Verbindung abbrechen sollte.

Für den _Aufbau_ der TCP-Verbindung haben Sie zwei Möglichkeiten:

. TCP-Verbindung wird von Zentralinstanz zur Remote-Instanz aufgebaut.
Hier ist die Remote-Instanz der _TCP-Server_.
. TCP-Verbindung wird von Remote-Instanz zur Zentralinstanz aufgebaut.
Hier ist die Zentralinstanz der _TCP-Server_.

Somit steht dem Weiterleiten von Benachrichtigungen auch dann nichts im Wege, wenn aus Netzwerkgründen der Verbindungsaufbau nur in eine bestimmte Richtung möglich ist.
Die TCP-Verbindungen werden vom Spooler mit einem Heartbeat-Signal überwacht und bei Bedarf sofort neu aufgebaut -- nicht erst im Falle einer Benachrichtigung.

Da Remote-Instanz und Zentralinstanz für den Spooler unterschiedliche globale Einstellungen brauchen, müssen Sie diese für _alle_ Remote-Instanzen xref:sitespecific[instanzspezifische Einstellungen] machen.
Die Konfiguration der Zentrale geschieht über die normalen globalen Einstellungen.
Beachten Sie, dass diese automatisch an alle Remote-Instanzen vererbt wird, für die Sie _keine_ spezifischen Einstellungen definiert haben.

Betrachten Sie zuerst den Fall, dass die Zentralinstanz die TCP-Verbindungen zu den Remote-Instanzen aufbauen soll.

Schritt 1: Editieren Sie *bei der Remote-Instanz* die instanzspezifische globale Einstellung [.guihint]#Notifications > Notification Spooler Configuration# und aktivieren Sie [.guihint]#Accept incoming TCP connections#.
Als TCP-Port wird 6555 vorgeschlagen.
Sofern nichts dagegen spricht, übernehmen Sie diese Einstellung.

image::distributed_monitoring_notification_spooler_configuration.png[]

Schritt 2: Setzen Sie nun ebenfalls nur *auf der Remote-Instanz* die Einstellung [.guihint]#Notification Spooling# auf den Wert [.guihint]#Forward to remote site by notification spooler#.

image::distributed_monitoring_notification_spooling.png[]

Schritt 3: Auf der *Zentralinstanz* -- also in den normalen globalen Einstellungen -- richten Sie nun zu der Remote-Instanz (und später dann auch eventuell zu weiteren Remote-Instanzen) die Verbindungen ein:

image::distributed_monitoring_notification_spooler_central_configuration.png[]

Schritt 4: Setzen Sie die globale Einstellung [.guihint]#Notification Spooling# auf [.guihint]#Asynchronous local delivery by notification spooler#,
damit auch die Meldungen der Zentrale über den gleichen zentralen Spooler abgewickelt werden.

image::distributed_monitoring_notification_spooling_central.png[]

Schritt 5: Aktivieren Sie die ausstehenden Änderungen.


// === Verbindungsaufbau von der Remote-Instanz aus

Soll die TCP-Verbindung von der Remote-Instanz aus aufgebaut werden, so ist das Vorgehen identisch,
bis auf die Tatsache, dass Sie die oben gezeigten Einstellungen einfach zwischen Zentralinstanz und Remote-Instanz vertauschen.

Auch eine Mischung ist möglich. In diesem Fall muss die Zentrale so aufgesetzt werden, dass sie sowohl auf eingehende Verbindungen lauscht, als auch Verbindungen zu entfernten Instanzen aufbaut.
Für jede Beziehung zwischen Zentralinstanz und Remote-Instanz darf aber _nur einer von beiden_ die Verbindung aufbauen!
////

[#monitor_spooling]
=== Überwachung des Spoolings

Nachdem Sie alles wie beschrieben konfiguriert haben, führen Sie für Zentral- und Remote-Instanzen die Service-Erkennung durch.
Sowohl auf der Zentralinstanz als auch auf den Remote-Instanzen werden zwei Services gefunden:

* [.guihint]#OMD mysite Notification Spooler# überwacht jeweils den lokalen Benachrichtigungs-Spooler.
* [.guihint]#OMD mysite Notification Spooler connection to othersite# überwacht jeweils die Verbindung zur anderen Instanz. Die Verbindung wird dabei von beiden Seiten aus überwacht.

Nehmen Sie die neuen Services auf jeden Fall ins Monitoring auf, um Probleme früh zu erkennen.

.Zwei Services pro Host informieren über Zustand von Notification Spooler und Verbindungen.
image::distributed_monitoring_notification_services.png[alt="Service-Suche mit den Diensten 'OMD sitename Notification Spooler' und 'OMD sitename Notification spooler connection' jeweils für Zentral- und Remote-Instanz."]
