[#intro]
== Einleitung

Ein wesentliches Paradigma des Monitorings über Livestatus ist, dass nur Daten von den Remote-Instanzen angefordert werden, die zur Ansicht in der Zentralinstanz benötigt werden.
Es ist sogar möglich, ein verteiltes Monitoring einzurichten, bei dem eine Zentralinstanz gar keine Daten selbst auswertet, sondern nur Statusdaten anderer Instanzen anzeigt.
Die übertragenen Datenmengen sind dabei deutlich kleiner, als sie für die Übertragung von Agentendaten wären.
Daraus folgen recht moderate Anforderungen an die benötigte Bandbreite.

Allerdings werden die Daten genau dann angefordert, wenn gerade jemand sie im Monitoring ansehen möchte.
Führt eine Ansicht oder ein Dashboard die Daten von mehreren Remote-Instanzen zusammen, kann die Anzeige erst erfolgen, wenn die letzte geantwortet hat.
Daher können Netzwerklatenzen oder Paketverluste einen entscheidenden Einfluss auf das Nutzungserlebnis haben.

[discrete]
[#why]
=== Warum lesen Sie diesen Artikel?

* Sie verwenden eine der kommerziellen Editionen und Ihnen hat _irgendjemand irgendwann_ gesagt, dass Sie bei der Verwendung von Livestatus _über das Internet_ immer Tuning-Maßnahmen anwenden müssen.
Das ist -- zumindest, wenn Sie den als Standard aktiven Livestatus-Proxy einsetzen -- bei kleinen und mittleren Umgebungen selten der Fall.
Höchstwahrscheinlich werden Sie kein Tuning benötigen.
Lesen Sie in diesem Fall gerne weiter, wenn Sie mehr über die Konzepte erfahren wollen.
* Sie nutzen eine der kommerziellen Editionen in einer mittlerweile sehr großen Umgebung, wo immer wieder die GUI für einige Sekunden hängt.
In diesem Fall erfahren Sie in diesem Artikel, wie Sie Timeouts und die Zahl zulässiger Verbindungen passend einstellen.
* Sie arbeiten mit {RE} in einer über größere Entfernungen verteilten Umgebung (aus netzwerktopologischer Sicht).
Dann ist es oft sinnvoll, proaktiv xref:status_hosts[Maßnahmen zu treffen], damit schon bei der _ersten_ Nicht-Erreichbarkeit einer Remote-Instanz das verteilte Monitoring gut nutzbar bleibt.


[#livestatusproxy]
== Der Livestatus-Proxy

{cee-only}
Die kommerziellen Editionen verfügen mit dem _Livestatus-Proxy_ über einen ausgeklügelten Mechanismus, um langsame oder tote Verbindungen zu erkennen und diese adäquat zu behandeln.
Außerdem optimiert er die Performance vor allem bei Verbindungen mit hohen Roundtrip-Zeiten.
Eigenschaften des Livestatus-Proxys sind:

* Nicht antwortende Instanzen werden sehr schnell erkannt.
* Anfragen, die statische Daten liefern, können lokal zwischengespeichert werden. 
* Durch die Nutzung persistenter TCP-Verbindungen sind weniger Roundtrips notwendig. Daraus resultieren viel schnellere Antworten von weit entfernten Instanzen (z.B. USA ⇄ China).
* Eine präzisere Kontrolle der maximal nötigen Livestatus-Verbindungen ist möglich.
* Zudem ermöglicht der Livestatus-Proxy die Nutzung der xref:inventory#[HW-/SW-Inventur] in verteilten Umgebungen.


[#configure_liveproxyd]
=== Einrichtung

In den kommerziellen Editionen ist der Livestatus-Proxy xref:cmk_processes[per Default aktiviert], und er wird auch als Standard-Verbindungsmethode verwendet.
Allerdings kann es erforderlich sein, die Standardeinstellungen auf Netzwerkeigenschaften und schlicht die Größe Ihrer Umgebung anzupassen.

[#number_channels]
===== Number of channels to keep open

Alle Anfragen der GUI teilen sich den TCP-Verbindungspool.
Die maximale Anzahl der Verbindungen begrenzt die Zahl der gleichzeitig in Bearbeitung befindlichen Anfragen.
Dies beschränkt indirekt die Anzahl der gleichzeitigen Browser-Sitzungen.
In Situationen, in denen alle Kanäle belegt sind, kommt es nicht sofort zu einem Fehler.
Die GUI wartet eine gewisse Zeit auf einen freien Kanal.
Die Beantwortung der meisten Anfragen benötigt nämlich nur wenige Millisekunden.

[TIP]
====
Die gezeigte Standardeinstellung von 20 gleichzeitig erlaubten eingehenden Livestatus-Verbindungen auf der Remote-Instanz und fünf vom Livestatus-Proxy der Zentralinstanz zur Remote-Instanz offen gehaltenen Verbindungen ist ideal, wenn die Mehrheit der Logins, um Dashboards zu betrachten, auf der Remote-Instanz stattfindet.
Findet die Mehrheit der Logins auf der Zentralinstanz statt, nähern Sie beide Werte stärker einander an.
Wird hingegen auf der Zentralinstanz vor allem Konfiguration vorgenommen, können Sie die Zahl der Kanäle des Livestatus-Proxy weiter absenken.
====

[#regular_heartbeat]
===== Regular heartbeat

Der [.guihint]#Regular heartbeat# sorgt für eine ständige aktive Überwachung der Verbindungen direkt auf Protokollebene.
Dabei sendet der Proxy regelmäßig eine einfache Livestatus-Anfrage, welche von der Remote-Instanz in der eingestellten Zeit (Default: 2 Sekunden) beantwortet sein muss.
So werden auch Situationen erkannt, wo der Zielserver und der TCP-Port zwar erreichbar sind, aber der Monitoring-Kern nicht oder sehr langsam antwortet.

[#regular_waiting]
===== Timeout waiting for a free channel

Falls die GUI länger als der Wert für [.guihint]#Timeout waiting for a free channel# auf so einen Kanal warten muss, wird die Anfrage abgebrochen und die gerade ins Monitoring guckende Person erhält eine Fehlermeldung.
In so einem Fall sollten Sie die Anzahl der Verbindungen erhöhen.
Beachten Sie dabei jedoch, dass auf der Gegenseite (der Remote-Instanz) genügend gleichzeitige eingehende Verbindungen erlaubt sein müssen.
Per Default sind 20 gleichzeitige eingehende Verbindungen eingestellt.
Sie können diese Einstellung in den (instanzspezifischen) globalen Einstellungen unter [.guihint]#Monitoring core > Maximum concurrent Livestatus connections# anpassen.

[#total_query_timeout]
===== Total query timeout

Mit dieser Einstellung definieren Sie den maximalen Timeout insgesamt.
Nach Ablauf dieser Zeit gilt eine Anfrage endgültig als gescheitert.

[#cooling_period]
===== Cooling period

Bleibt die Antwort auf eine _Heartbeat-Anfrage_ aus, so werden alle Verbindungen zur betreffenden Remote-Instanz als tot betrachtet und erst nach einer Cooldown-Zeit (Default: 4 Sekunden) wieder neu aufgebaut.
Dies geschieht proaktiv -- also _ohne_, dass die Person an der Maus irgendwo klicken müsste.
So werden Ausfälle schnell erkannt und bei einer Wiedergenesung die Verbindungen sofort wieder aufgebaut.
Monitoring-Daten stehen dann im besten Fall schnell wieder zur Verfügung, ohne dass der zwischenzeitliche Ausfall überhaupt spürbar wird.

[#enable_caching]
===== Enable caching

Das [.guihint]#Caching# sorgt dafür, dass statische Anfragen nur einmal von der Remote-Instanz beantwortet werden müssen und ab dem Zeitpunkt direkt lokal ohne Verzögerung beantwortet werden können.
Ein Beispiel dafür ist die Liste der überwachten Hosts, welche von der Suche gebraucht wird.


[#per_connection]
==== Via Verbindungseinstellung

Selbstverständlich können Sie die globale Einstellung auch für einzelne Livestatus-Verbindungen abändern.
Das kann beispielsweise sinnvoll sein, um eine kleine Remote-Instanz, auf deren Livestatus-Informationen seltener zugegriffen wird, zu entlasten.
Wählen Sie in den Verbindungseinstellungen für die gewünschte Remote-Instanz im Dropdown-Menü für [.guihint]#Parameters# den Wert [.guihint]#Use custom connection parameters#.
Ihnen wird dann die Möglichkeit angeboten, jede der xref:liveproxyd_global_settings[global voreingestellten] Einstellungen individuell zu überschreiben.

.In den Verbindungseinstellungen können Sie für die Verbindung zu einzelnen Remote-Instanzen abweichende Parameter definieren.

== Status-Hosts

Die Konfiguration von _Status-Hosts_ ist der bei {CRE} empfohlene Weg, problematische Verbindungen zuverlässig zu erkennen.

// Die Idee dahinter ist einfach:
// MFS: Gnihihi.
// Die Idee dahinter war einfach:
Die Idee dahinter ist:
Die Zentralinstanz überwacht selbst aktiv die Verbindung zu jeder einzelnen Remote-Instanz.
Sie haben ja ein Monitoring-System zur Verfügung.
Die GUI erkennt dann nicht erreichbare Instanzen, kann sie als icon:icon_status_label_down[width=70px] werten und zunächst nicht weiter versuchen, Daten von diesen Instanzen abzufragen.
Timeouts werden so vermieden.

So richten Sie einen Status-Host für eine Verbindung ein:

. Nehmen Sie den Host, auf dem die Remote-Instanz läuft, auf der Zentralinstanz ins Monitoring auf.
Dies muss kein vollwertiges Monitoring mit einem Agenten sein.
Ein xref:host_checks#ping[Host-Check], beispielsweise [.guihint]#Ping (active check with ICMP echo request)#, genügt.
. Tragen Sie diesen Host nun bei der Verbindung zur Remote-Instanz als Status-Host ein.

.Der Zustand des eingetragenen Status-Hosts bestimmt, ob überhaupt versucht wird, die dort laufende Remote-Instanz abzufragen.
image::distributed_monitoring_status_host.png[]

Eine ausgefallene Verbindung zur Remote-Instanz kann jetzt nur noch für kurze Zeit zu einem Hängen der GUI führen -- nämlich solange, bis das Monitoring das erkannt hat.

Bei Verwendung von Status-Hosts werden weitere Verbindungszustände möglich.
Diese xref:distributed_monitoring_reference#connection_state_status_host[erläutert der Referenzartikel fürs verteilte Monitoring].

.[#status_host_fine_tuning]#Feintuning bei Status-Hosts#
[%collapsible]
====
Bei der Verwendung eines Status-Hosts ist weitere Konfiguration oft sinnvoll.
Angenommen, Sie haben einzelne Remote-Instanzen, die zwar häufig, dann aber nur für wenige Minuten oder sogar weniger als eine Minute ausfallen.

In solchen Fällen führt das Standardintervall für Host-Checks von einer Minute dazu, dass Betrachtende Ihrer Zentralinstanz immer wieder mit Timeouts konfrontiert sind, ohne dass die Verwendung von Status-Hosts signifikante Linderung brächte.
Hier können Sie mit verkürzten Intervallen für Host-Checks arbeiten.

Da beim Host-Check [.guihint]#Ping (active check with ICMP echo request)# nur wenige Parameter angepasst werden können, lohnt es sich meist, einen separaten xref:active_checks#[aktiven Check] (`check_icmp` oder `check_ping`) zu konfigurieren.
Stellen Sie diesen so ein, dass beispielsweise alle fünf Sekunden mit nur einem Paket und einem Timeout von ein oder zwei Sekunden der Zustand des Hosts ermittelt wird.
Ändern Sie abschließend die Regel [.guihint]#Host check command# für den Status-Host auf [.guihint]#Use the status of the service# und weisen Sie den jetzt präzise konfigurierten aktiven Check zu.
Damit erfassen Sie auch kurze Zeiten der Nicht-Erreichbarkeit.
====


[#persistent]
== Persistente Verbindungen

Mit der Checkbox [.guihint]#Use persistent connections# können Sie die GUI dazu veranlassen, einmal aufgebaute Livestatus-Verbindungen zu Remote-Instanzen permanent aufrecht zu erhalten und für weitere Anfragen wieder zu verwenden.
Gerade bei Verbindungen mit einer längeren Paketlaufzeit (zum Beispiel interkontinentale) kann diese Einstellung die GUI deutlich reaktiver machen.

[TIP]
====
Verwenden Sie persistente Verbindungen nur in Umgebungen mit hohen Latenzen und niedrigem Paketverlust.
In anderen Szenarien wird unnötig viel Arbeitsspeicher gebunden.
====

Die GUI von {CMK} wird durch mehrere parallele Apache-Prozesse bereitgestellt.
Bei Verwendung persistenter Verbindungen ist pro Apache-Prozess und damit pro aktiver Monitoring-Sitzung eine Livestatus-Verbindung notwendig.
Gleichen Sie daher die maximale Zahl der Apache-Prozesse und die Zahl gleichzeitiger Livestatus-Verbindungen aneinander an.
Oft bedeutet dies, die Zahl der Livestatus-Verbindungen anzuheben und die Zahl der Apache-Prozesse zu reduzieren.
Beide Einstellungen können Sie in den [.guihint]#Global settings# vornehmen.
Bei der Konfiguration der Apache-Prozesse hilft der xref:cmk_processes#apache[Handbuchartikel zu den Instanzdiensten].
