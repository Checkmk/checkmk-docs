[#intro]
== Einleitung

Ein wesentliches Paradigma des Monitorings über Livestatus ist, dass nur Daten von den Remote-Instanzen angefordert werden, die zur Ansicht in der Zentralinstanz benötigt werden.
Es ist sogar möglich, ein verteiltes Monitoring einzurichten, bei dem eine Zentralinstanz gar keine Daten selbst auswertet, sondern nur anzeigt.
Die übertragenen Datenmengen sind dabei ein vielfaches kleiner als sie für die Übertragung von Monitoringdaten wären.
Daraus folgen recht moderate Anforderungen an die benötigte Bandbreite.

Allerdings werden die Daten genau dann angefordert, wenn gerade jemand sie im Monitoring ansehen möchte.
Führt eine Ansicht oder ein Dashboard die Daten von mehreren Remote-Instanzen zusammen, kann die Anzeige erst erfolgen, wenn die letzte geantwortet hat.
Daher können Netzwerklatenzen oder Paketverluste einen entscheidenden Einfluss auf das Nutzungserlebnis haben.

[#livestatusproxy]
== Der Livestatus-Proxy

{cee-only}
Die kommerziellen Editionen verfügen mit dem _Livestatus-Proxy_ über einen ausgeklügelten Mechanismus, um langsame oder tote Verbindungen zu erkennen und diese adäquat zu behandeln.
Außerdem optimiert er die Performance vor allem bei Verbindungen mit hohen Roundtrip-Zeiten.
Eigenschaften des Livestatus-Proxys sind:

* Nicht antwortende Instanzen werden sehr schnell erkannt.
* Anfragen, die statische Daten liefern, können lokal zwischengespeichert werden. 
* Durch die Nutzung persistenter TCP-Verbindungen sind weniger Roundtrips notwendig. Daraus resultieren viel schnellere Antworten von weit entfernten Instanzen (z.B. USA ⇄ China).
* Eine präzisere Kontrolle der maximal nötigen Livestatus-Verbindungen ist möglich.
* Zudem ermöglicht der Livestatus-Proxy die Nutzung der xref:inventory#[HW-/SW-Inventur] in verteilten Umgebungen.

===== Number of Channels to keep open

Alle Anfragen der GUI teilen sich den TCP-Verbindungspool.
Die maximale Anzahl der Verbindungen begrenzt die Zahl der gleichzeitig in Bearbeitung befindlichen Anfragen.
Dies beschränkt indirekt die Anzahl der gleichzeitigen Browser-Sitzungen.
In Situationen, in denen alle Kanäle belegt sind, kommt es nicht sofort zu einem Fehler.
Die GUI wartet eine gewisse Zeit auf einen freien Kanal.
Die Beantwortung der meisten Anfragen benötigt nämlich nur wenige Millisekunden.

===== Regular heartbeat

Der [.guihint]#Regular heartbeat# sorgt für eine ständige aktive Überwachung der Verbindungen direkt auf Protokollebene.
Dabei sendet der Proxy regelmäßig eine einfache Livestatus-Anfrage, welche von der Remote-Instanz in der eingestellten Zeit (Default: 2 Sekunden) beantwortet sein muss.
So werden auch Situationen erkannt, wo der Zielserver und der TCP-Port zwar erreichbar sind, aber der Monitoring-Kern nicht oder sehr langsam antwortet.

===== Timeout waiting for a free channel

Falls die GUI länger als der Wert für [.guihint]#Timeout waiting for a free channel# auf so einen Kanal warten muss, wird die Anfrage abgebrochen und die gerade ins Monitoring guckende Person erhält eine Fehlermeldung.
In so einem Fall sollten Sie die Anzahl der Verbindungen erhöhen.
Beachten Sie dabei jedoch, dass auf der Gegenstelle (der Remote-Instanz) genügend gleichzeitige eingehende Verbindungen erlaubt sein müssen.
Per Default sind 20 gleichzeitige eingehende Verbindungen eingestellt.
Sie können diese Einstellung in den (instanzspezifischen) globalen Einstellungen unter [.guihint]#Monitoring core > Maximum concurrent Livestatus connections#.

===== Cooling period

Bleibt die Antwort auf eine _Heartbeat-Anfrage_ aus, so werden alle Verbindungen zur betreffenden Remote-Instanz als tot betrachtet und erst nach einer Cooldown-Zeit (Default: 4 Sekunden) wieder neu aufgebaut.
Dies geschieht proaktiv -- also _ohne_, dass die Person an der Maus irgendwo klicken müsste.
So werden Ausfälle schnell erkannt und bei einer Wiedergenesung die Verbindungen sofort wieder aufgebaut.
Monitoring-Daten stehen dann im besten Fall schnell wieder zur Verfügung, ohne dass die Person mit Hand auf der Maus und Augen am Monitor den Ausfall mitbekommen hätte.

===== Enable caching

Das [.guihint]#Caching# sorgt dafür, dass statische Anfragen nur einmal von der Remote-Instanz beantwortet werden müssen und ab dem Zeitpunkt direkt lokal ohne Verzögerung beantwortet werden können.
Ein Beispiel dafür ist die Liste der überwachten Hosts, welche von der Suche gebraucht wird.

.[#status_host_fine_tuning]#Feintuning bei Status-Hosts#
[%collapsible]
====
Bei der Verwendung eines Status-Hosts ist weitere Konfiguration oft sinnvoll.
Angenommen, Sie haben einzelne Remote-Instanzen, die zwar häufig, dann aber nur für wenige Minuten oder sogar weniger als eine Minute ausfallen.

In solchen Fällen führt das Standardintervall für Host-Checks von einer Minute dazu, dass Betrachtende Ihrer Zentralinstanz immer wieder mit Timeouts konfrontiert sind, ohne dass die Verwendung von Status-Hosts signifikante Linderung brächte.
Hier können Sie mit verkürzten Intervallen für Host-Checks arbeiten.

Da beim Host-Check [.guihint]#Ping (active check with ICMP echo request)# nur wenige Parameter angepasst werden können, lohnt es sich meist, einen separaten aktiven Check (`check_icmp` oder `check_ping`) zu konfigurieren.
Stellen Sie diesen so ein, dass beispielsweise alle fünf Sekunden mit nur einem Paket und einem Timeout von ein oder zwei Sekunden der Zustand des Hosts ermittelt wird.
Ändern Sie abschließend die Regel [.guihint]#Host check command# für den Status-Host auf [.guihint]#Use the status of the service# und weisen Sie den jetzt präzise konfigurierten Active Check zu.
Damit erfassen Sie auch kurze Zeiten der Nicht-Erreichbarkeit.
