[#intro]
== Einleitung

In diesem Artikel führen wir Sie Schritt für Schritt durch die komplette Einrichtung eines xref:distributed_monitoring_basics#[verteilten Monitorings] mit _zentralem Setup_.
Die Einrichtung eines _verteilten Monitorings mit autonomem Setup_ auf den Remote-Instanzen beschreibt der Artikel xref:distributed_monitoring_watchonly#[Verteiltes Monitoring ohne zentrales Setup einrichten].

Die Einrichtung eines verteilten Monitorings mit zentralem Setup geschieht in folgenden Schritten:

. Sie xref:setting_up_central_site[richten die Zentralinstanz] zunächst ganz normal wie eine Einzelinstanz ein.
. Dann xref:create_remote[richten Sie die Remote-Instanzen ein] und xref:start_livestatus[geben Livestatus per Netzwerk frei].
. Auf der Zentralinstanz xref:connect_remote_sites[binden Sie anschließend die Remote-Instanzen] über [.guihint]#Setup > General > Distributed monitoring# ein.
. Bei xref:distribute_objects[Hosts und Ordnern legen Sie fest], von welcher Instanz aus diese überwacht werden sollen.
. Für xref:move_hosts[umgezogene Hosts] führen Sie die Service-Erkennung neu durch.

Bei Verwendung des zentralen Setups raten wir dazu, _frisch eingerichtete_ Remote Sites zu verwenden.
Es werden sowieso alle Einstellungen überschrieben und die Zentralinstanz kümmert sich um die Zuweisung der überwachten Hosts.


[#setting_up_central_site]
== Zentralinstanz vorbereiten

Bei Einrichtung einer Zentralinstanz für ein verteiltes Monitoring mit zentralem Setup -- also Verteilung der Konfiguration -- empfehlen wir, mit einer frisch installierten Instanz zu starten.
Der Grund:
Globale Einstellungen der Zentralinstanz werden nach der Aktivierung der Verteilung der Konfiguration an die Remote-Instanzen verteilt.
Sind hier Einstellungen vorhanden, die für eine einzelne für sich stehende Instanz oder Zentralinstanz Sinn ergeben haben, aber nicht für eine Remote-Instanz, kann dies bei Aktivierung der Verteilung der Konfiguration zu Problemen führen.

[#piggyback_global]
=== Piggyback global aktivieren

Aktivieren Sie auf der Zentralinstanz unter [.guihint]#Setup > General > Global settings# im Abschnitt [.guihint]#Site management# den Piggyback-Hub.
Diese Einstellung stellt sicher, dass die korrekte xref:piggyback#distributed_piggyback[Verarbeitung von Piggyback-Daten] im gesamten verteilten Monitoring -- auf der Zentralinstanz und allen Remote-Instanzen -- aktiviert wird.
Auch wenn Sie diesen Schritt einmal bei der Vorbereitung einer Remote-Instanz vergessen, wird der Piggyback-Hub dort dann nach der Verteilung der Konfiguration zu dieser Instanz gestartet.
Nachdem Sie diese Einstellung vorgenommen haben, aktivieren Sie die ausstehenden Änderungen.

.Den Piggyback-Hub können Sie komfortabel in den [.guihint]#Global settings# aktivieren.

[#create_remote]
== Remote-Instanzen vorbereiten

Die Remote-Instanzen erzeugen Sie zunächst als neue Instanzen wie üblich mit `omd create`.
Dies geschieht dann natürlich auf dem (entfernten) Server, der für die jeweilige Remote-Instanz vorgesehen ist.

[TIP]
====
* Verwenden Sie für die Remote-Instanzen Namen, die in Ihrem verteilten Monitoring _eindeutig_ sind und die Identifizierung erleichtern.
* Die {CMK}-Version (z.B. {current}) der Remote- und Zentralinstanz muss exakt dieselbe sein -- ein xref:update#updatedistributed[Mischbetrieb] wird nur für die leichtere Durchführung von Updates unterstützt.
* Auch die verwendete {CMK}-Edition (z.B. {CE}) der Remote- und Zentralinstanz muss übereinstimmen, ein Mischbetrieb ist nicht möglich.
// ES: Stimmt das denn? In upgrade#editiondistributed sagen wir explizit "Ein Mischbetrieb ist möglich, wenn: ..." Evtl. findest du eine schwächere Formulierung hier ("nicht vorgesehen", "nicht empfohlen", "bietet sich nicht an" o.ä.)
* Da {CMK} mehrere Instanzen auf einem Server unterstützt, darf die Remote-Instanz auch auf dem selben Server laufen.
====

Sie können auch mehrere Remote-Instanzen auf einmal vorbereiten oder neue Remote-Instanzen jederzeit nachträglich zu einem bestehenden verteilten Monitoring hinzufügen.

Executing post-create script "01_create-sample-config.py"...[green]#OK#

[#start_livestatus]
=== Livestatus über TCP und Piggyback-Hub aktivieren

[#livestatus_tcp]
==== Livestatus über TCP aktivieren

Die Livestatus-Schnittstelle stellt den Zugriff auf die Monitoring-Daten her.
Sie muss per TCP im Netzwerk freigegeben werden.

[TIP]
====
Beachten Sie dabei, dass Livestatus zwar SSL verwendet, um Einblicke in übertragene Daten zu verhindern, aber keinen Zugriffsschutz bietet.
Jeder Teilnehmer eines Netzwerks, der den Livestatus-Port einer Remote-Instanz erreichen kann, hat die Möglichkeit, Monitoring-Daten abzufragen.
Eine grundsätzlich empfohlene Sicherheitsmaßnahme ist daher die Verwendung der Einstellung `LIVESTATUS_TCP_ONLY_FROM` zur Zugriffsbeschränkung auf bestimmte IP-Adressen.
Noch sicherer ist die Einschränkung über entsprechende Firewall-Regeln und gegebenenfalls die Verwendung eines VPN.
====

Die Aktivierung der Netzwerkfreigabe von Livestatus nehmen Sie als Instanzbenutzer bei noch gestoppter Instanz per `omd config` vor:

[{shell}]
----
{c-root} omd su myremote1
{c-myremote1} omd config set LIVESTATUS_TCP on
{c-myremote1} omd config set LIVESTATUS_TCP_TLS on
----

Um sich zu vergewissern, dass alle Einstellungen korrekt angewandt wurden, können Sie sich die für Livestatus relevanten Einstellungen anzeigen lassen.
Notieren Sie den angezeigten Port, Livestatus verwendet als Default 6557:

[{shell}]
----
{c-myremote1} omd config show | grep LIVESTATUS
LIVESTATUS_TCP: on
LIVESTATUS_TCP_ONLY_FROM: 0.0.0.0
LIVESTATUS_TCP_PORT: 6557
LIVESTATUS_TCP_TLS: on
----


[#activate_piggyback]
==== Piggyback-Hub aktivieren

Da der Piggyback-Hub recht sparsam mit Systemressourcen umgeht, empfehlen wir die Aktivierung in jeder Instanz.
Die Aktivierung können Sie direkt in der Shell-Sitzung vornehmen, in der Sie eben Livestatus über TCP aktiviert haben:

[{shell}]
----
{c-myremote1} omd config set PIGGYBACK_HUB on
----

Um sich zu vergewissern, dass alle Einstellungen korrekt angewandt wurden, können Sie sich die für den Piggyback-Hub relevanten Einstellungen anzeigen lassen.
Notieren Sie den angezeigten Port, der Piggyback-Hub verwendet als Default 5672:

[{shell}]
----
{c-myremote1} omd config show | grep 'PIGGYBACK_HUB\|RABBITMQ_PORT'
PIGGYBACK_HUB: on
RABBITMQ_PORT: 5672
----

[TIP]
====
Lassen Sie sich nicht verwirren: Der [.guihint]#Message broker port# ist hier als Variable `RABBITMQ_PORT` hinterlegt, weil RabbitMQ die von {CMK} konkret verwendete Message Broker Software ist.
====


==== Instanz starten

Nach dem Speichern starten Sie die Instanz wie gewohnt mit `omd start`:

[{shell}]
----
{c-myremote1} omd start
Starting agent-receiver...OK
Starting mkeventd...OK
Starting liveproxyd...OK
Starting mknotifyd...OK
Starting rrdcached...OK
Starting redis...OK
Starting automation-helper...OK
Starting ui-job-scheduler...OK
Starting cmc...OK
Starting apache...OK
Starting dcd...OK
Starting rabbitmq...OK
Starting stunnel...OK
Starting piggyback-hub...OK
Starting xinetd...OK
Starting crontab...OK
----

Die Remote-Instanz ist jetzt bereit.
Kontrollieren Sie zur Sicherheit abschließend, ob alle Einstellungen erfolgreich angewendet wurden.

==== Kontrolle der Ports

Eine Kontrolle mit `ss` zeigt, dass die Ports 6557 und 5672 geöffnet sind.
Der gezeigte `grep`-Befehl findet auch die beiden nächsthöheren Ports, für den Fall, dass Ihre Instanz sich den Server mit anderen Instanzen teilt.
Die Bindung an Port 6557 geschieht mit einer Instanz des Internet Superservers `xinetd`, welcher direkt in der Instanz läuft.

[{shell-raw}]
----
{c-myremote1} ss -tulpn | grep ':655[789]\|:567[234]'
tcp   LISTEN 0      128                      *:5672             *:*    users:(("beam.smp",pid=32639,fd=40))     
tcp   LISTEN 0      64                       *:6557             *:*    users:(("xinetd",pid=33374,fd=6))
----

Bleiben Sie an dieser Stelle noch in der als Instanzbenutzer geöffneten Shell.
Sie benötigen diese später noch, um etwas nachzuschlagen.

[#connect_status]
=== Livestatus-Zugriff aktivieren

Legen Sie jetzt mit icon:icon_new[] [.guihint]#Add connection# die Verbindung zur ersten Remote-Instanz an.
Im Abschnitt [.guihint]#Basic settings# tragen Sie als [.guihint]#Site ID# den Namen ein -- exakt so, wie Sie diesen bei `omd create` vergeben haben.
Den Alias können Sie frei vergeben und auch später ändern.

.Die [.guihint]#Site ID# muss dem Namen der Remote-Instanz exakt entsprechen
image::distributed_monitoring_basic_settings.png[alt="Die Basiseinstellungen für die Remote-Instanz."]

Bei den Einstellungen der [.guihint]#Status connection# legen Sie fest,
wie die Zentralinstanz den Status der Remote-Instanzen per Livestatus abfragt.
Wichtig ist der Livestatus-Port, der dem auf der Remote-Instanz ermittelten entsprechen muss.
Das Beispiel im Screenshot zeigt eine Verbindung mit dem Livestatus-Proxy-Daemon (Standard bei den kommerziellen Editionen).
Bei {RE} ist die direkte Verbindung Standard.
Direktverbindungen sind für stabile Verbindungen mit kurzen Latenzzeiten sehr gut geeignet (in einem LAN oder zwischen schnell angebundenen Standorten).
Anpassungen für WAN-Verbindungen mit höheren Latenzen und Tuning des Livestatus-Proxy-Daemons erklärt ein xref:distributed_monitoring_performance#[weiterführender Artikel].


.Im Regelfall müssen Sie hier nur [.guihint]#Host# und [.guihint]#URL Prefix# eintragen und den [.guihint]#Port# überprüfen.
image::distributed_monitoring_status_connection.png[alt="Eingabe der Statusdaten."]

Der Eintrag bei [.guihint]#URL Prefix# enthält die Basis-URL Ihrer Instanz: Protokoll, Hostname und Instanzname.
Wenn Sie grundsätzlich per [#https_inline]#HTTPS# auf {CMK} zugreifen, dann ersetzen Sie im Protokollteil `http` durch `https`.
Eine Verbindung mit HTTPS ist empfehlenswert, setzt aber voraus, dass der Webserver der Remote-Instanz HTTPS unterstützt.
Dies muss auf Linux-Ebene des Servers Ihrer Remote-Instanz xref:omd_https#[konfiguriert werden].
Bei der {CMK} Appliance kann xref:appliance_usage#ssl[HTTPS über die webbasierte Konfigurationsoberfläche eingerichtet] werden.

[#livestatus_tls]
=== SSL-Zertifikat prüfen und vertrauen

Nachdem Sie die Remote-Instanz hinzugefügt haben, werden Sie in der Spalte, welche Details zur [.guihint]#Status connection# zeigt, zwei Dinge bemerken:

Zum einen wird die Verbindung durch das Schildsymbol icon:icon_encrypted[] als verschlüsselt markiert.
Und zum anderen wird {CMK} Ihnen mit einem weißen Kreuz auf rotem Grund icon:icon_cross[] anzeigen, dass der CA der Remote-Instanz (noch) nicht vertraut wird.
Instanzzertifikate werden bei der Einrichtung einer Instanz erzeugt.
Um dem Zertifikat der Remote-Instanz wirklich vertrauen zu können, müssen Sie sicherstellen, dass die der Zentral-Instanz präsentierten Zertifikate den in der Remote-Instanz hinterlegten entsprechen.
Hierfür vergleichen Sie die Fingerprints der Zertifikate.


[#get_certificate]
==== SSL-Zertifikate auslesen (Remote-Instanz)

Die Fingerprints können Sie auf zwei Arten auslesen:
Auf der Befehlszeile als Instanzbenutzer oder in der GUI.

Besonders schnell geht es in der offen gelassenen Shell als Instanzbenutzer der Remote-Instanz mit dem Befehl `openssl`:

[{shell-raw}]
----
{c-myremote1} openssl x509 -noout -fingerprint -sha256 -inform pem -in etc/ssl/sites/*.pem
sha256 Fingerprint=D3:CA:FB:AD:23:42:F8:62:09:FA:B3:22:08:48:58:AC:9A:12:0C:03:F1:19:84:C0:76:3F:50:6D:36:1D:D7:EC
{c-myremote1} openssl x509 -noout -fingerprint -sha256 -inform pem -in etc/ssl/ca.pem
sha256 Fingerprint=DE:AD:B3:3F:01:61:55:0B:F2:E5:EC:C9:93:71:76:49:7A:6B:20:67:89:72:29:02:D5:CC:52:5A:D9:79:F0:F2
----

Alternativ können Sie die GUI nutzen:
Loggen Sie sich an der Remote-Instanz mit dem dort für den Administrationsbenutzer vergebenen Nutzername und Passwort ein und gehen dann mittels [.guihint]#Setup > Maintenance > Certificate overview# zur xref:certificates#[Zertifikatsübersicht].
Achten Sie dort auf die [.guihint]#Fingerprints# der Zertifikate, deren Verwendungszweck in der Spalte [.guihint]#Purpose# als [.guihint]#Signing the site certificate# (CA-Zertifikat) und [.guihint]#The site certificate# (Site-Zertifikat) bezeichnet werden.

Vergleichen Sie die beiden auf der Remote-Instanz ausgelesenen Fingerprints mit den angezeigten.
Stimmen diese überein, klicken Sie auf den gehobenen Daumen icon:icon_trust[], um dem CA-Zertifikat zu vertrauen.

.Um eine Verbindung zu Livestatus der Remote-Instanz herzustellen, müssen Sie dem CA-Zertifikat vertrauen.

Danach werden beide Zertifikate als vertrauenswürdig gelistet, was in der Übersicht durch ein Häkchen auf grünem Grund icon:icon_checkmark[] symbolisiert wird.


[#remote_login]
=== Login an der Remote-Instanz

Auch in den Details zur Spalte [.guihint]#Configuration connection# zeigen zwei Symbole, dass noch nicht alle nötigen Schritte abgeschlossen sind:

Hier weist das weiße Kreuz auf rotem Grund icon:icon_cross[] darauf hin, dass noch kein [.guihint]#Login# auf der entfernten Instanz von {CMK} stattgefunden hat.
Bei diesem Login tauscht die Zentralinstanz mit der Remote-Instanz ein Anmeldegeheimnis aus, über das dann in Zukunft alle weitere Kommunikation abläuft.
Das Konto `cmkadmin` auf der Instanz wird dann deaktiviert.

Klicken Sie auf das Schlüsselsymbol icon:icon_authok[] der anzubindenden Instanz.
Im folgenden Formular verwenden Sie als [.guihint]#Login credentials# `cmkadmin` und das beim Anlegen der Remote-Instanz vergebene Passwort.
Bestätigen Sie an dieser Stelle noch mit der Checkbox [.guihint]#Confirm overwrite#, dass Sie die Einstellungen wirklich überschreiben wollen.

.Die erste Kontaktaufnahme zur Verteilung des Setups erfolgt mit Nutzername und Passwort.
image::distributed_monitoring_login_credentials.png[alt="Eingabe des Logins für die Remote-Instanz."]

Bei einem erfolgreichen Login werden Sie direkt in die Übersichtsseite weitergeleitet, wo ein Schlosssymbol icon:icon_autherr[] und das Häkchen auf grünem Grund icon:icon_checkmark[] den Erfolg anzeigen.


.[#troubleshooting]#Wenn das Login an der Remote-Instanz fehlschlägt#
[%collapsible]
====
Sollte es zu einem Fehler bei der Anmeldung kommen, kann dies verschiedene Gründe haben, unter anderem:

* Die Remote-Instanz ist gerade gestoppt
* Die [.guihint]#URL of remote site# ist nicht korrekt eingestellt
* Die Remote-Instanz ist unter dem in der URL eingestellten Hostnamen _von der Zentralinstanz aus_ nicht erreichbar (DNS- oder Routing-Probleme)
* Zentralinstanz und Remote-Instanz haben inkompatible {CMK}-Versionen oder Editionen
* Benutzer und/oder Passwort sind falsch

Gerade Probleme auf Routing-, DNS- oder Firewall-Ebene erfordern eine strukturierte Ursachensuche.
Ist sichergestellt, dass die Remote-Instanz läuft, können Sie im Browser testen, ob diese erreichbar ist -- oder irgendwo auf dem Weg eine Firewall blockiert.
Klappt der Zugriff hier, können Sie sich per SSH auf der Zentralinstanz einloggen.
Suchen Sie dort mit `curl -v pass:[http://remoteserver/myremote1]` nach Hinweisen, was das Login blockiert.
====

[#sitespecific]
=== Instanzspezifische globale Einstellungen

Ein xref:distributed_monitoring_basics#central_setup[zentrales Setup] bedeutet zunächst, dass alle Instanzen eine gemeinsame und -- bis auf die überwachten Hosts -- identische Konfiguration haben.
Allerdings werden Sie in vielen Fällen abweichende Einstellungen benötigen.
Vielleicht haben Sie Ihr Monitoring nach Standorten gegliedert und die Netzwerke and den verschiedenen Standorten sind unterschiedlich groß.
Dann werden Sie kleinere Instanzen auf schwächerer Hardware betreiben und größere Instanzen auf stärkerer Hardware.
Beides erfordert unterschiedliche xref:core_tuning#[Einstellungen der kernnahen Prozesse].

Für solche Fälle gibt es instanzspezifische globale Einstellungen.
Zu diesen gelangen Sie über das Zahnradsymbol icon:icon_configuration[] in der Instanzübersicht ihres verteilten Monitorings ([.guihint]#Setup > General > Distributed monitoring#):

.Jede Remote-Instanz verfügt über eigene globale Einstellungen.
image::distributed_monitoring_site_specific_global_configuration.png[]

Alles, was Sie jetzt einstellen, gilt nur für die ausgewählte Instanz.
Auch die optische Hervorhebung für eine Abweichung vom Standard bezieht sich hier nur auf diese Instanz:

.Wenn Sie Einstellungen ändern, können Sie diese sowohl mit den Standards der Zentralinstanz als auch den Werkseinstellungen vergleichen.
image::distributed_monitoring_site_specific_global_configuration_2.png[]

[TIP]
====
Ist Ihnen aufgefallen, dass auch die Zentralinstanz über instanzspezifische globale Einstellungen verfügt?

Der Grund dafür ist, dass Sie häufig Einstellungen vornehmen wollen, die für alle oder wenigstens die Mehrzahl der Remote-Instanzen gelten, aber eben nicht für die Zentralinstanz.
Sie nehmen diese Einstellungen dann in den globalen Einstellungen für alle Instanzen (auf der Zentralinstanz unter [.guihint]#Setup > General > Global settings#) vor.
Überschreiben Sie noch vor der Aktivierung der ausstehenden Änderungen diese für die Zentralinstanz durch deren instanzspezifische globale Einstellungen unter [.guihint]#Setup > General > Distributed Monitoring#.
====

[#add_move_hosts]
=== Hosts neu aufnehmen oder umziehen

Beachten Sie hinsichtlich der Aufnahme von Hosts mit Agenten auch den Artikel zur xref:agent_deployment#central_setup[Verteilung von Agentenpaketen].

[#add_hosts]
==== Hosts aufnehmen

Das Aufnehmen von Hosts funktioniert wie gewohnt.
Bis auf die Tatsache, dass die Überwachung und auch die Service-Erkennung von der jeweiligen Remote-Instanz durchgeführt wird, gibt es nichts Spezielles zu beachten.

[#move_hosts]
==== Hosts umziehen

Beim _Umziehen_ von Hosts von einer zu einer anderen Instanz gibt es einige Dinge zu beachten.
Es werden _weder aktuelle noch historische Statusdaten_ dieser Hosts übernommen.
Lediglich die Konfiguration des Hosts bleibt erhalten -- ganz, als würden Sie den Host auf einer Instanz entfernen und auf der anderen _neu anlegen_.
Das bedeutet unter anderem:

* Automatisch erkannte Services werden nicht übernommen.
Führen Sie daher nach dem Umziehen eine xref:glossar#service_discovery[Service-Erkennung] durch.

* Host und Services befinden sich auf der Instanz, zu der sie umgezogen sind, zunächst im Zustand {PEND}.
Zu eventuell aktuell vorhandenen Problemen werden neue Benachrichtigungen erzeugt und gegebenenfalls versendet.

* Historische xref:graphing#[Metriken] gehen verloren.
Dies können Sie vermeiden, indem Sie betroffene RRD-Dateien von Hand kopieren.
Hinweise zum Umgang mit diesen Dateien finden Sie im xref:rrds#[Artikel zu RRDs].

* Daten zur Verfügbarkeit und zu historischen Ereignissen gehen verloren.
Eine Migration dieser Daten ist nicht möglich.

Wenn die Kontinuität der Historie für Sie wichtig ist, sollten Sie schon beim Aufbau des Monitorings genau planen, welcher Host von wo aus überwacht werden soll.

Es gibt für die Seitenleiste das Snapin [.guihint]#Site status#, welches Sie mit icon:button_sidebar_add_snapin[[alt="Symbol zum Anzeigen aller Snapins."] einbinden können.
