[#intro]
== Einleitung

Nachdem Sie sich mit den xref:distributed_monitoring_basics#[Vor- und Nachteilen eines verteilten Monitorings vertraut gemacht] haben, wollen Sie eines einrichten. In diesem Artikel führen wir Sie durch diese Aufgabe.

Die Einrichtung eines verteilten Monitorings mit zentralem Setup geschieht in folgenden Schritten:

. Sie xref:setting_up_central_site[richten die Zentralinstanz] zunächst ganz normal wie eine Einzelinstanz ein.
. Dann xref:create_remote[richten Sie die Remote-Instanzen ein] und xref:start_livestatus[geben Livestatus per Netzwerk frei].
. Auf der Zentralinstanz xref:connect_remote_sites[binden Sie anschließend die Remote-Instanzen] über [.guihint]#Setup > General > Distributed monitoring# ein.
. Bei xref:distribute_objects[Hosts und Ordnern legen Sie fest], von welcher Instanz aus diese überwacht werden sollen.
. Für xref:move_hosts[umgezogene Hosts] führen Sie die Service-Erkennung neu durch.

Bei Verwendung des zentralen Setups raten wir dazu, _frisch eingerichtete_ Remote Sites zu verwenden.
Es werden sowieso alle Einstellungen überschrieben und die Zentralinstanz kümmert sich um die Zuweisung der überwachten Hosts.

Wenn Sie entfernte Instanzen nur mittels Live-Status einbinden wollen und diese autonom administriert werden sollen, sollten diese natürlich bereits Hosts im Monitoring haben.
Dann sind folgende Schritte durchzuführen:

. Sie xref:create_remote[richten die Remote-Instanzen ein] und xref:start_livestatus[geben Livestatus per Netzwerk frei].
. Auf der Zentralinstanz xref:connect_remote_sites[binden Sie die Remote-Instanzen] über [.guihint]#Setup > General > Distributed monitoring# ein.

[#setting_up_central_site]
== Zentralinstanz einrichten

An die Zentralinstanz werden keine speziellen Anforderungen gestellt.
Je nach Szenario werden Sie zwei optionale Einstellungen vornehmen wollen.
Eine Umwidmung einer bereits länger betriebenen Solo-Instanz zu einer Zentralinstanz im verteilten Monitoring stellt kein Problem dar.

Beide Einstellungen werden unter [.guihint]#Setup > General > Global settings# im Abschnitt [.guihint]#Site management# vorgenommen:

* Wenn Sie ein verteiltes Monitoring von Grund auf neu aufbauen und die Zentralinstanz ausschließlich der Konfiguration und der Übersicht dient, aber keine Hosts direkt überwacht, können Sie über die Einstellung [.guihint]#Monitoring core: No monitoring core# den Monitoring-Kern ganz abschalten.
Belassen Sie den Monitoring-Kern, wenn die Zentralinstanz selbst Hosts überwacht.
* Für die korrekte xref:piggyback#distributed_piggyback[Verarbeitung von Piggyback-Daten] sollten Sie den Piggyback-Hub aktivieren.
Da der Piggyback-Hub recht sparsam mit Systemressourcen umgeht, empfehlen wir die Aktivierung in jeder Instanz.

.Den Piggyback-Hub können Sie komfortabel in den [.guihint]#Global settings# aktivieren.
image::distributed_monitoring_site_management.png[alt="Die Option 'Enable piggyback-hub' in den globalen Einstellungen."]

Anschließend xref:glossar#activate_changes[aktivieren Sie die ausstehenden Änderungen], da jede der beschriebenen Änderungen Neustarts von Diensten erfordert.

[#create_remote]
== Remote-Instanzen vorbereiten

Die Remote-Instanzen werden zunächst als neue Instanzen wie üblich mit `omd create` erzeugt.
Dies geschieht dann natürlich auf dem (entfernten) Server, der für die jeweilige Remote-Instanz vorgesehen ist.

[TIP]
====
* Verwenden Sie für die Remote-Instanzen IDs, die in Ihrem verteilten Monitoring _eindeutig_ sind und die Identifizierung erleichtern.
* Die {CMK}-Version (z.B. {current-major}) der Remote- und Zentralinstanz muss dieselbe sein -- ein xref:update#updatedistributed[Mischbetrieb] wird nur für die leichtere Durchführung von Updates unterstützt.
* Da {CMK} mehrere Instanzen auf einem Server unterstützt, darf die Remote-Instanz auch auf dem selben Server laufen.
====

[#create_site]
=== Remote-Instanzen einrichten

Die Einrichtung der Remote-Instanz unterscheidet sich nicht von der einer Einzelinstanz.
Hier ist ein Beispiel für das Anlegen einer Remote-Instanz mit dem Namen `myremote1` und dem Passwort `t0p53cr3t` für den Instanz-Administrator `cmkadmin`:

[{shell}]
----
{c-root} omd create --admin-password t0p53cr3t myremote1
Adding /opt/omd/sites/myremote1/tmp to /etc/fstab.
Creating temporary filesystem /omd/sites/myremote1/tmp...[green]#OK#
Updating core configuration...
Generating configuration for core (type cmc)...
Starting full compilation for all hosts
 Creating global helper config...[green]#OK#
 Creating cmc protobuf configuration...OK
Executing post-create script "01_create-sample-config.py"...[green]#OK#
Executing post-create script "02_cmk-compute-api-spec"...[green]#OK#
Executing post-create script "03_message-broker-certs"...[green]#OK#
Restarting Apache...[green]#OK#
Created new site myremote1 with version {current}.pro.

  The site can be started with pass:q[*omd start myremote1*].
  The default web UI is available at pass:q[*http://myserver/myremote1/*]

  The admin user for the web applications is *cmkadmin* with password: *t0p53cr3t*
  For command line administration of the site, log in with *'omd su myremote1'*
  After logging in, you can change the password for cmkadmin with *'cmk-passwd cmkadmin'*.
----

Merken Sie sich das Passwort für `cmkadmin`.
Sie benötigen es mindestens einmal: um die Verbindung der Zentral- zur Remote-Instanz herzustellen.
Sobald die Remote-Instanz der Zentralinstanz untergeordnet wurde,
werden sowieso alle Benutzer durch die von der Zentralinstanz ausgetauscht.


[#start_livestatus]
=== Livestatus über TCP und Piggyback-Hub aktivieren

[#livestatus_tcp]
==== Livestatus über TCP aktivieren

Livestatus stellt den Zugriff auf die Monitoring-Daten her.
Dieses muss per TCP im Netzwerk freigegeben werden.

[TIP]
====
Beachten Sie dabei, dass Livestatus zwar SSL verwendet, um Einblicke in übertragene Daten zu verhindern, aber keinen Zugriffsschutz bietet.
Jeder Teilnehmer eines Netzwerkes, der den Livestatus-Port einer Remote-Instanz erreichen kann, hat die Möglichkeit, Monitoring-Daten abzufragen.
Wir empfehlen daher zusätzliche Sicherheitsmaßnahmen wie entsprechende Firewall-Regeln und gegebenenfalls die Verwendung eines VPN.
====

Die Aktivierung der Netzwerkfreigabe von Livestatus geschieht als Instanzbenutzer bei noch gestoppter Instanz per `omd config`:

[{shell}]
----
{c-root} omd su myremote1
{c-myremote1} omd config set LIVESTATUS_TCP on
{c-myremote1} omd config set LIVESTATUS_TCP_TLS on
----

Um sich zu vergewissern, dass alle Einstellungen korrekt angewandt wurden, können Sie sich die für Livestatus relevanten Einstellungen anzeigen lassen.
Notieren Sie den angezeigten Port, Livestatus verwendet als Default 6557:

[{shell}]
----
{c-myremote1} omd config show | grep LIVESTATUS
LIVESTATUS_TCP: on
LIVESTATUS_TCP_ONLY_FROM: 0.0.0.0
LIVESTATUS_TCP_PORT: 6557
LIVESTATUS_TCP_TLS: on
----

[TIP]
====
Wenn Sie die grafische Konfiguration bevorzugen, können Sie beide Einstellungen auch unter [.guihint]#Setup > General > Global settings > Site management# vornehmen.
Aber wenn man schon in der Befehlszeile unterwegs ist...
====

[#activate_piggyback]
==== Piggyback-Hub aktivieren

Da der Piggyback-Hub recht sparsam mit Systemressourcen umgeht, empfehlen wir die Aktivierung in jeder Instanz.
Die Aktivierung können Sie direkt in der Shell-Sitzung vornehmen, in der Sie eben Livestatus über TCP aktiviert haben:

[{shell}]
----
{c-myremote1} omd config set PIGGYBACK_HUB on
----

Um sich zu vergewissern, dass alle Einstellungen korrekt angewandt wurden, können Sie sich die für den Piggyback-Hub relevanten Einstellungen anzeigen lassen.
Notieren Sie den angezeigten Port, der Piggyback-Hub verwendet als Default 5672:

[{shell}]
----
{c-myremote1} omd config show | grep 'PIGGYBACK_HUB\|RABBITMQ_PORT'
PIGGYBACK_HUB: on
RABBITMQ_PORT: 5672
----

[TIP]
====
Lassen Sie sich nicht verwirren: Der [.guihint]#Message Broker Port# ist hier als Variable `RABBITMQ_PORT` hinterlegt, weil RabbitMQ die von {CMK} konkret verwendete Message Broker Software ist.
====


==== Instanz starten

Nach dem Speichern starten Sie die Instanz wie gewohnt mit `omd start`:

[{shell}]
----
{c-myremote1} omd start
Starting agent-receiver...OK
Starting mkeventd...OK
Starting liveproxyd...OK
Starting mknotifyd...OK
Starting rrdcached...OK
Starting redis...OK
Starting automation-helper...OK
Starting ui-job-scheduler...OK
Starting cmc...OK
Starting apache...OK
Starting dcd...OK
Starting rabbitmq...OK
Starting stunnel...OK
Starting piggyback-hub...OK
Starting xinetd...OK
Starting crontab...OK
----

Die Instanz ist jetzt bereit.

==== Kontrolle der Ports

Eine Kontrolle mit `ss` zeigt, dass die Ports 6557 und 5672 geöffnet sind.
Die Bindung an Port 6557 geschieht mit einer Instanz des Internet Superservers `xinetd`, welcher direkt in der Instanz läuft:

[{shell-raw}]
----
{c-myremote1} ss -tulpn | grep ':6557\|:5672'
tcp   LISTEN 0      128                      *:5672             *:*    users:(("beam.smp",pid=32639,fd=40))     
tcp   LISTEN 0      64                       *:6557             *:*    users:(("xinetd",pid=33374,fd=6))
----

[#remote_login]
=== Login an der Remote-Instanz

Auch in der Spalte [.guihint]#Configuration connection# zeigen zwei Icons, dass noch nicht alle nötigen Schritte abgeschlossen sind:

Hier weist das weiße Kreuz auf rotem Grund icon:icon_cross[] darauf hin, dass noch kein [.guihint]#Login# auf der entfernten Instanz von {CMK} stattgefunden hat.

[#troubleshooting]
==== Fehlerbehandlung

Sollte es zu einem Fehler bei der Anmeldung kommen, kann dies verschiedene Gründe haben, unter anderem:

* Die Remote-Instanz ist gerade gestoppt
* Die [.guihint]#URL of remote site# ist nicht korrekt eingestellt
* Die Remote-Instanz ist unter dem in der URL eingestellten Hostnamen _von der Zentralinstanz aus_ nicht erreichbar (DNS- oder Routing-Probleme)
* Zentralinstanz und Remote-Instanz haben inkompatible {CMK}-Versionen oder Editionen
* Benutzer und/oder Passwort sind falsch

Die ersten beiden Punkte können Sie einfach testen, indem Sie die URL der Remote-Instanz in Ihrem Browser aufrufen.

[#sitespecific]
=== Instanzspezifische globale Einstellungen

Ein xref:distributed_monitoring_basics#central_setup[zentrales Setup] bedeutet zunächst einmal, dass alle Instanzen eine gemeinsame und (bis auf die Hosts) gleiche Konfiguration haben.
Allerdings werden Sie in vielen Fällen abweichende Einstellungen benötigen.
Haben Sie das Monitoring beispielsweise nach Standorten gegliedert, werden Sie die kleinere Instanzen auf schwächerer Hardware betreiben wollen, größere Instanzen auf stärkerer Hardware.
Beides erfordert unterschiedliche xref:core_tuning#[Einstellungen am Monitoring-Kern].

Für solche Fälle gibt es instanzspezifische globale Einstellungen.
Zu diesen gelangen Sie über das Zahnradsymbol icon:icon_configuration[] in der Instanzübersicht ihres verteilten Monitorings ([.guihint]#Setup > General > Distributed monitoring#):

.Jede Remote-Instanz verfügt über eigene globale Einstellungen.
image::distributed_monitoring_site_specific_global_configuration.png[]

Alles, was Sie jetzt einstellen, gilt nur für die ausgewählte Instanz.
Auch die optische Hinterlegung für eine Abweichung vom Standard bezieht sich hier nur auf diese Instanz:

.Wenn Sie Einstellungen ändern, können Sie diese sowohl mit den Standards der Zentralinstanz als auch den Werkseinstellungen vergleichen.

[#distribute_objects]
== Zuordnung von Objekten zu Instanzen

Alle Zugriffe auf einen überwachten Host geschehen konsequent von der Instanz aus, der dieser Host zugeordnet ist.
Das betrifft nicht nur die eigentliche Überwachung, sondern auch die xref:glossar#service_discovery[Service-Erkennung,] die xref:wato_monitoringagents#diagnosticpage[Diagnoseseite,] die xref:glossar#notification[Benachrichtigungen,] xref:alert_handlers#[Alert Handler] und alles andere.

[#hosts_and_folders]
=== Hosts und Ordnern Instanzen zuordnen

Nachdem Ihre verteilte Umgebung eingerichtet ist, können Sie beginnen, diese zu nutzen.
Eigentlich müssen Sie jetzt nur noch für jeden Host festlegen, von welcher Instanz aus dieser überwacht werden soll.
Als Standard ist immer die Zentralinstanz eingestellt.

Das nötige Attribut dazu heißt [.guihint]#Monitored on site#.

[#add_move_hosts]
=== Hosts neu aufnehmen oder umziehen

[#add_hosts]
==== Hosts aufnehmen

Das Aufnehmen von Hosts funktioniert wie gewohnt.
Bis auf die Tatsache, dass die Überwachung und auch die Service-Erkennung von der jeweiligen Remote-Instanz durchgeführt wird, gibt es nichts Spezielles zu beachten.

[#move_hosts]
==== Hosts umziehen

Beim *Umziehen* von Hosts von einer zu einer anderen Instanz gibt es einige Dinge zu beachten.
Denn es werden _weder aktuelle noch historische Statusdaten dieser Hosts übernommen._
Lediglich die Konfiguration des Hosts bleibt erhalten.
Es ist quasi, als würden Sie den Host auf einer Instanz entfernen und auf der anderen _neu anlegen_.
Das bedeutet unter anderem:

* Automatisch erkannte Services werden nicht übernommen.
Führen Sie daher nach dem Umziehen eine xref:glossar#service_discovery[Service-Erkennung] durch.

* Host und Services beginnen wieder bei {PEND}.
Zu eventuell aktuell vorhandenen Problemen werden neue Benachrichtigungen erzeugt und gegebenenfalls versendet.

* Historische xref:graphing#[Metriken] gehen verloren.
Dies können Sie vermeiden, indem Sie betroffene RRD-Dateien von Hand kopieren.
Die Lage der Dateien finden Sie im xref:rrds#[Artikel zu RRDs].

* Daten zur Verfügbarkeit und zu historischen Ereignissen gehen verloren.
Eine Migration dieser ist nicht möglich.

Wenn die Kontinuität der Historie für Sie wichtig ist, sollten Sie schon beim Aufbau des Monitorings genau planen, welcher Host von wo aus überwacht werden soll.

[#site_status_snapin]
=== Site status Snapin

Es gibt für die Seitenleiste das Snapin [.guihint]#Site status#, welches Sie mit icon:button_sidebar_add_snapin[[alt="Symbol zum Anzeigen aller Snapins."] einbinden können.
Dieses zeigt den Status der einzelnen Instanzen.
Außerdem bietet es die Möglichkeit, vorübergehend eine einzelne Instanz durch einen Klick auf den Status zu deaktivieren und wieder zu aktivieren -- oder auch gleich alle Instanzen auf einmal durch Klick auf [.guihint]#Disable all# oder [.guihint]#Enable all#.

image::distributed_monitoring_snapin_site_status.png[width=42%]

Deaktivierte Instanzen werden mit dem Status icon:icon_status_label_disabled[width=70px] angezeigt.
Sie können so auch eine Instanz, die icon:icon_status_label_dead[width=70px] ist und somit Timeouts erzeugt, deaktivieren und die Timeouts damit vermeiden.
Diese Deaktivierung entspricht *nicht* dem Abschalten der Livestatus-Verbindung über die Verbindungskonfiguration im [.guihint]#Setup#.
Das Abschalten hier ist lediglich für den aktuell angemeldeten Benutzer wirksam und hat eine rein optische Funktion.
Ein Klick auf den Namen einer Instanz bringt Sie zur Ansicht aller Hosts dieser Instanz.
